## 2. Final root modes are part of the immutable plan

The planner describes the complete SQL effect and authorization dependency of each account **before any lock is acquired**. It picks a final mode per root, deduplicates IDs, and takes each root once. A stronger already-planned mode can satisfy a weaker dependency. It must never acquire weaker first and upgrade later. Discovery of another account, key, child mutation or stronger dependency causes rollback and fresh planning, even if a local upgrade seems uncontended.

| Planned effect/dependency                                                                                  | Final account mode   | Application cases and constraints                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Delete an existing User or update a key column covered by an FK-eligible unique index                      | `FOR UPDATE`         | Fold drop; first X bind; fold keep receiving `xId`. Include any future key/index changes in the schema-derived classifier. User IDs are immutable. A key-column assignment in ORM SQL is conservatively strong even if its intended value equals the old value.                                |
| Update non-key User fields                                                                                 | `FOR NO KEY UPDATE`  | Suspension, handle/role refresh, rotation timestamps. Existing reconnect assigns `xId`, so remains strong until a reviewed conditional branch emits non-key-only SQL.                                                                                                                          |
| Serialize an account-wide identity aggregate without changing User                                         | `FOR NO KEY UPDATE`  | Additional-link limits/first participant provisioning, revoke plus enumeration/invalidation, primary link/rotation, X disconnect. This prevents concurrent aggregate writers and blocks authorization readers using SHARE. It is compatible with pure FK KEY SHARE consumers.                  |
| Read non-key account authority/status that must remain stable through session issuance or an identity read | `FOR SHARE`          | Existing-account wallet sign-in with no User mutation; authenticated X start when User is read-only. Suspension's NO KEY UPDATE conflicts with SHARE. If the command also updates a non-key field, plan NO KEY UPDATE instead. Preserve child locks for connected X and old-session authority. |
| Existence/key-only reference, no mutation or non-key permission predicate                                  | `FOR KEY SHARE`      | Pure FK insertion/provisioning dependency already authorized through another valid boundary. Not sufficient by itself for sign-in's `suspended` predicate, account-level link counts, or restriction-sensitive business commands.                                                              |
| New User whose ID did not exist                                                                            | No existing-row lock | Plan its ID in advance; serialize X/wallet uniqueness under the appropriate advisory keys, insert User before FK children, and own its write lock. A discovered existing owner changes the plan; do not switch owners mid-command.                                                             |

Fold direction and possible recipient key changes are planned from observations. A plan permitting either direction must give both candidate roots their maximum needed strength upfront. A cheaper single-direction plan is allowed only if changed emptiness/direction aborts and re-plans. A callback is not strong merely because folds are globally possible: an observed conflict/new binding determines its effect, and changed observation triggers re-plan. No extra strength is discovered inside `absorbAccount`.

Weaker locks are an optimization with a permission contract, not the sole X1/X2 fix. A fold still deletes a root and therefore still conflicts with FK KEY SHARE. Every participating writer must take its full ordered account set before child rows/FK insertions. X2 requires actual finance/campaign consumers to comply too. If an incompatible consumer cannot be converted or isolated, the fold gate remains closed and global safety is not claimed.

## 3. Shared protocol and cross-account planning

Introduce one transaction plan/helper contract, with trusted storage adapters and explicit host dependencies (PostgreSQL READ COMMITTED, transaction ownership, key derivation, clock, authority observer, rollback/error classification). The host owns external signature/provider verification and retries. The helper owns acquisition, phase tracking and guarded revalidation. No in-process mutex substitutes for cross-process DB locks.

**Unlocked observation phase:** before entering acquisition, read initiating account/session, credential owners, permanent X IDs, old/new primary addresses, related links, prospective fold accounts/direction, operation/actor IDs and financial exclusions. Reads are hints, never authorization. Plan every account affected or referenced by a new FK, including audit actors if an FK exists. Compute complete old/new X and wallet sets for both fold accounts. A resolver observes ownership without locking, then takes the planned subject/root set and re-reads; it never takes a new root after a child or opportunistically enters a fold from a linked result.

**Acquisition phase, sequential and transaction-scoped:**

1. Declared global advisory exclusions, then all required balance exclusions. Keep the existing global-before-balance rule; merge takes balance exclusions for both keep/drop to compose with activity/payout guards. Every finance/campaign adapter must declare its additional prefix and prove no later lower-class lock acquisition. Fixed 729102–729104 consumers belong in this inventory, not an unreviewed new policy. Source inspection also finds `finance:<launchId>` and `reward:<launchId>` in `src/lib/rewards.ts`, and 729103 in `src/lib/campaigns.ts`; any such helper reachable in a composed transaction must be registered with a final global-exclusion ordering before balance/identity resources. This inventory/classification is a review gate, not a claim that those current paths already conform.
2. Wallet commands alone may claim **one** stored WalletChallenge after their required global/balance prefix and before subjects/X/roots/children. Rotation retains balance-before-claim. Prevalidate immutable digest, address, actor and purpose to select the same prefix for any command able to claim that digest. No other command purpose may claim it; no second challenge; no later claim. Cleanup/challenge deletion is an independent autocommit leaf. This exception must be proved with same-digest/rotation races; it is not a generic lower-order acquisition exemption.
3. All wallet-subject advisory locks, then all x-auth advisory locks. Include old primary, replacement primary, all addresses moved by merge, additional credential subjects touched by resolve/link/revoke, and every existing/requested X subject. The subject is address-wide across WalletIdentity/WalletLink and networks, matching current uniqueness/trigger behavior; never add a network to the lock label alone. Reacquisition by a trigger of the identical held key is allowed; discovery of an unplanned key is not.
4. All existing User roots, ascending **JavaScript code-unit** ID order, final modes from §2. Use one parameterized SELECT per ID, sequentially awaited. No `Promise.all` or multi-row SQL `ORDER BY` substitutes for the acquisition order. Missing rows/changed owner sets trigger guarded re-plan or terminal denial as appropriate.
5. Re-read owner/key/address/account/plan membership under those locks before locking children. Restriction changes are authorization denials; harmless changed plans are retried. If the same account no longer has the anticipated X/wallet relationship, never append its new keys. Check fold emptiness under financial/root exclusions and reject any canonical participant or protected activity. Guard against new FK activity created by conforming writers.
6. Enumerate and prelock **all existing child rows** to be read as authority, mutated, moved or deleted: OAuthAttempt → XAccount → Session → WalletIdentity → Participant → WalletLink. Within each class sort PKs in JS code-unit order and lock one ID at a time. An existing child to be updated/deleted gets FOR UPDATE up front; authority-only rows get FOR SHARE; never SHARE then DELETE the same Session. Session replacements prelock the old owned session for UPDATE, X link reads precede Session reads, and revoke/suspension prelock their enumerated matching sessions for UPDATE. Plan/account serialization prevents new conflicting children while enumeration runs. Leaf cleanup can remove rows; revalidate required presence after each wait.
7. Observe live session/account/X/revocation and DB wall-clock **after acquisition/waits**, before authorization/mutation. Reject expired, foreign, restricted, missing/disconnected or wrong-intent authority. Do not use transaction-start `now()` as proof of live authority after a long wait. Only after all required existing rows are held may mutation start. New child rows use the same class order and covered FK roots/unique namespaces. Final audit/receipt/outbox effects are append-only; any newly discovered dependency requires rollback, not a late lock.

The entire set and final modes are fixed before acquisition. Child enumeration under protected roots refines row IDs within declared predicates, not account/key/effect membership. Revalidation cannot add a stronger effect or undeclared predicate. Uniqueness, cascades and triggers must be audited alongside explicit locks; prelocking existing rows does not prove every implicit insertion wait benign. In particular any final insert that can wait on a unique receipt/proof must have a covered semantic namespace and no later backwards acquisition. This is an implementation-review obligation.

Nested merge accepts only the validated same-transaction capability; it acquires no new advisory/root/child resources. It changes no payout records, deletes no Participant/WalletLink history, and retains existing emptiness/collision restrictions. Moving an additional credential would violate current immutable account/participant relations and is denied. All User delete cascades must be represented by prelocked child rows and audited current schema; a new referencing table invalidates that plan's review.

**Advisory builder:** one shared resource descriptor factory produces exact labels `balance:<accountId>`, `wallet-subject:<canonicalBase58Address>`, `x-auth:<permanentXId>` and the fixed integer-key registry. Hash using PostgreSQL `hashtextextended(label,0)` in the owning transaction; represent its signed 64-bit result losslessly (bigint/string, never JS Number). No locale comparison, normalization, whitespace or client-supplied lock namespace. Sort by class then canonical descriptor in code-unit order and acquire sequentially. Contract tests compare canonical label bytes and actual bigint key/pg_locks identity to the installed wallet exclusivity trigger for insert/address change, and confirm the same key space as fixed bigint calls. The trigger still does not protect reassignment: explicit merge subject locks are required.

Deduplicate identical descriptors. Different descriptors that produce an identical bigint within a plan or alias a known fixed key are a STORAGE_CONTRACT failure before acquisition; do not retry as a benign race. Hash equality across separate plans can remain undetected. The approximate pairwise 2^-64 estimate assumes uniform unrelated inputs, is not a birthday bound, and is not a cryptographic/adversarial guarantee. Class/label order is conditional on no undetected cross-resource alias, and on all host writers conforming. We accept that bounded operational assumption for this proposal, with monitoring/review; we do not claim a general proof. A collision-resistant redesign would require coordinated trigger/host/finance compatibility work, not a silent seed or key-space change.

## 4. Cleanup batches and leaf exceptions

Expired Session, OAuthAttempt and WalletChallenge sweeps each run as a separate autocommit SQL statement: a MATERIALIZED CTE selects PKs in declared order with `FOR UPDATE SKIP LOCKED` and a strictly positive bounded LIMIT, then `DELETE ... USING` those PKs with the same expiry predicate. Preserve worker `< cutoff` versus X-start `<= cutoff`. Freeze cutoff per invocation. Do not put all batches inside one enclosing transaction or append start/identity work to a batch.

Proposed implementation default: 100 rows per batch and at most 10 batches per invocation, under a bounded time budget; these are tunable operational defaults requiring backlog testing, not owner-approved production capacity. Continue while rows were deleted and budget remains, otherwise defer to the next job. Zero selected does not mean no expired rows: locked rows may have been skipped. Metrics distinguish deleted, deferred/contended, failed and remaining backlog; test starvation recovery once holders release. Tuple skipping does not avoid table/DDL waits. Re-audit cascade/trigger effects on migration changes; Session deletes currently cascade nothing and OAuthAttempt has no FK.

Narrow leaf allow-list: logout's one-session-PK DELETE; OAuth attempt's one-PK atomic claim and callback-finally cancellation DELETE; bounded standalone expiry statements; challenge creation with no later acquired locks. Each has no subsequent lock-taking work in that transaction. A leaf that gains a FK/trigger or is composed into a larger transaction loses the exemption. Attempt completion/disconnect/merge deletion are not leaf exceptions. No blanket deleteMany or file-level exemption.

## 6. Safe bounded re-planning and side effects

Use a typed internal PLAN_CHANGED distinction for benign observed membership/owner/required-mode changes. Roll back the **whole** attempt, release all locks, make fresh unlocked observations and build a new complete plan. Never retry just a final INSERT or keep locks across attempts. Proposed default is three total DB attempts, small randomized backoff and an overall request deadline; configure/document the deadline with the host, and bound individual lock/transaction time too. Budget exhaustion returns a sanitized retryable unavailable result (503/RETRY_TRANSACTION for this host), no owner/constraint/SQL details. It is not permission to acquire a missing lock late.

`40P01`/`40001` and positively classified transient DB failures can consume this bounded budget with telemetry, but deterministic deadlocks are protocol defects, not successful concurrency evidence. Tests disable automatic retry or assert zero deadlock/retry counters for schedules intended to prove ordering. Do not indiscriminately retry every uniqueness error: after rollback reobserve a known semantic race; a foreign/revoked reservation, reused proof, invalid signature, expired/cancelled attempt, suspension or changed permanent X identity is terminal under its documented domain error. A two-tab callback to the same permitted identity can re-plan; a cancelled initiating session cannot be replaced with a different session to make it pass.

Keep request/operation ID, immutable payload digest, signed challenge bytes, verified signature/profile and candidate session token stable across internal DB attempts. Wallet challenge consumption, old-session deletion, new-session creation, mapping/link/revoke and audit commit together; failed attempts roll them all back. Successful proof consumption prevents replay; never reset an acknowledged challenge. After revoke, sign-in cannot launder the credential into a fresh null-attribution session. A command receipt, where required for request-level replay, is bound to actor+kind+ID+payload digest and committed with its outcome; a different payload conflicts. Its wait namespace/placement is part of the plan review, not an assumed unlocked extra write.

OAuth claim is durable before provider exchange; DB completion retries reuse that claimed attempt and verified profile without re-claiming or re-exchanging the provider code. Completion must recheck retained claimed row, expiry, cancellation and own original session after waits, and delete the claimed attempt only within successful completion. Callback-finally cleanup runs only after internal retries terminate. No external provider, cookie/header response, notification or other irreversible effect occurs inside retryable DB code. Emit the cookie once after confirmed commit; unknown commit results require receipt/state reconciliation, not blind replay with another token. Durable cross-request/unknown-commit recovery remains an implementation contract to verify, not a feature already present.

## 7. Standalone and already-locked identity-module contracts

Preserve today's public IdentityTransaction port (PostgreSQL, READ COMMITTED, parameterized query, explicit host transaction lifetime/error mapping) and its standalone commands. Introduce a versioned optional lock context through the port/public command contract, not an undocumented boolean. Default standalone link/resolve/revoke uses the shared planner and conservative account NO KEY UPDATE serialization; it must remain usable without RAID imports, globals or a pre-existing plan. The planner/SQL adapter is an explicit module dependency delivered with it, with no hidden singleton.

An already-locked capability contains protocol version, live transaction identity, validated plan identity/phase, covered canonical subject/X resources, account IDs and final modes, declared child predicates/IDs/modes, and the permitted command effect. Only the shared acquisition helper/compatible trusted adapter can mint it after revalidation/prelocking. Bind issuance/lifetime to a transaction-local registry (e.g. opaque object plus WeakMap in the host adapter); invalidation on rollback/commit prevents reuse. A TypeScript brand is developer assistance, not proof of real locks: host contract suites must verify SQL acquisition and correct port lifetime. The public module must deny inadequate context before mutation, not silently acquire more locks or use standalone fallback halfway through a host transaction.

Prelocked mode skips only already-satisfied acquisitions. It still validates account/actor/proof/network/policy, rereads required current state, checks restriction, current live own session/X authority and post-wait clock, and enforces uniqueness/limits/revocation. A capability is never wallet proof or authorization. A read-only resolver can accept a sufficient SHARE root; aggregate mutation requires NO KEY UPDATE or planned FOR UPDATE. No request body can supply a capability.

`observeAuthority` is read-only over declared prelocked rows and injected DB clock; it cannot take an undeclared/lower-order lock, mutate identity or call a provider. Hosts must declare XAccount and Session observations and final strengths in advance, fixing today's Session-before-X ordering. Standalone use must supply a transaction-current authority observer or a declared host observation with equivalent locking/lifetime; stale observations cannot satisfy the link boundary. If a host already holds other locks, it must provide a conforming plan, not invoke standalone acquisition out of order. Revoke's host must observe a live self-session under this boundary too; an early session snapshot is insufficient after a wait.

Preserved module invariants: own actor/account equality; fresh one-use proof bound to intent/domain/network/destination; no cross-account credential alias; no primary promotion/revoke; immutable HUMAN participant/account mapping; revoked address reservation remains; no payout/history/capacity change; no auth widening; audit and matching-session invalidation commit with revoke before acknowledgement. Lookup/resolution is internal ownership context, never authentication or a public account-discovery DTO. List/read APIs expose only authorized own data.

Deliver two independent minimal consuming examples and shared contract suites: standalone module on a declared real PostgreSQL adapter, and host-composed multi-account/prelocked use through public ports. Test missing/foreign transaction, expired capability, wrong mode/account/subject/version/phase, authority changing while waiting, revoked proof/session, rollback atomicity, and an alternate compatible query adapter. Record genuine RED/GREEN/REFACTOR and observed example results in the future slice; none is verified by this design.

## 8. Credential attribution, visible destination and pre-enable gates

**Attribution proposal:** nullable server-written `Session.walletLinkId`, indexed, same-account composite FK `(walletLinkId,userId)` → `WalletLink(id,accountId)` with the required referenced unique constraint. This additive DDL is proposed only. Populate from the credential actually verified in this command when it grants wallet authority; primary wallet and X authority use null. Do not copy client metadata or the previous session's attribution. Preserve existing wallet reauth semantics that retain live own X authority: that replacement remains X authority with null attribution. X completion explicitly writes null; additional-wallet authority writes its exact link ID. Test every replacement path for laundering in both directions.

Revoke atomically holds subject/root/ordered children, changes ACTIVE→REVOKED, deletes only Sessions with that link ID and same account, writes durable audit and commits. Unrelated primary/X/other-wallet sessions survive. The revoking own session is deleted if it is attributed to that credential. If sign-in commits first, revoke sees/removes its attributed session; if revoke wins, sign-in's locked reread denies. Revoke may not use an obsolete unlocked session observation or acknowledge before invalidation/audit. Suspension remains a distinct all-session action; no suspended self-service exception is introduced.

**Wallet-attribution pre-enable check:** Claude reports staging WalletLink=0, Session=2, wallet-authenticated Session=0, with links disabled/unwired and fixed 7-day session TTL in both wallet/X creators. This is environment-specific evidence, not a claim about every database or current future state. Before migration/enablement, inventory each target's WalletLink and potentially unattributed wallet sessions, inspect all token creation/extension paths and TTL, and record timestamp/source/instance coverage. If WalletLink=0 and linking stayed closed, no existing session could have used an additional credential: keep nulls and do not backfill. If any additional link exists or historical enablement cannot be ruled out, require forced reauthentication of potentially unattributed wallet sessions, or a complete 7-day drain from the last legacy writer/token issuance with no renewal/laundering and all legacy instances gone. Stale null-attribution replacements cannot extend the drain. A different TTL invalidates the seven-day reasoning. Migration tooling must assert the selected compatibility precondition rather than silently accepting unknown provenance.

Attribution-writing and linked-wallet resolution must run on every web/worker/fixture/session writer before the first new link is created. Keep the server linking gate closed through migration, version/drain verification, selective-revoke review and consent/Phantom evidence. A zero-link migration check alone does not certify future enablement or a mixed-version window. No guessed backfill, no permanent blanket account sign-out in place of the owner's selective policy, and no gate/deployment change in this task.

**SIWS Resources binding:** append to additional-link messages only, after Expiration Time, preserving the original single-line statement and lines 0–10:

```text
Resources:
- urn:useraid:account:<canonical-account-id>
- https://x.com/<validated-handle-snapshot>
```

These are schematic placeholders, not bytes to sign. The canonical Resources list has exactly these two ordered absolute URIs, constructed from authenticated server account/X state. Validate the account using the existing AccountId contract (`src/contracts/ids.ts`, opaque ASCII IDs, not an invented UUID constraint), and encode its entire URI component canonically; verify by decoding then requiring canonical re-encoding and exact account equality. Validate X handle `^[A-Za-z0-9_]{1,15}$`, forbid controls/newlines and serialize deterministically. Do not fetch the resource URLs or treat them as callback/redirect destinations. The [Phantom SIWS reference](https://github.com/phantom/sign-in-with-solana) specifies URI resource lines; grammar compatibility does not prove signer-visible rendering.

Verify signature/digest over the exact stored message, parse and validate its canonical Resources (missing/duplicate/reordered/extra/invalid account resources denied), and compare its account ID to both WalletChallenge.userId and the command's live authenticated self-account. Verify own live X-authority session, still-connected XAccount and stable permanent X identity consistency under locks. Preserve the signed handle snapshot; do not compare it to a renamed live handle or rewrite signed bytes. A rename with the same permanent X ID is compatible; disconnect or changed permanent identity is denied. Binding uses only server-created challenge bytes, not returned client Resources or a new live message. Existing sign-in/link/rotation bytes remain unchanged.

Pending target-less additional-link challenges fail as invalid; five-minute TTL bounds their lifetime and disabled linking means none is expected, but verify rather than infer. The current parser reads statement at line3 and chain at line7; appending preserves those indices. It still requires a new purpose-aware Resources parser/verification contract and reference-grammar round-trip tests. Do not describe the old parser alone as sufficient destination verification. Test malformed/newline/Unicode data, URI substitutions, digest tampering, account A→B replay, handle rename, X disconnect, old challenges, adapter substitution and all legacy intents.

**Phantom outstanding:** real wallet rendering of BOTH destination account ID and X handle in Resources is NOT VERIFIED. Before DEC-04 satisfaction, record Phantom version/platform, exact candidate/source/config, devnet connection, visible consent screenshot/manual observations, accept/reject signing, returned bytes and successful/denied command behavior using synthetic identities. If Resources are hidden, the requirement is unmet; redesign consent serialization with review, not a waiver. The owner's earlier staging Phantom invalid-format issue and devnet/mainnet network correction still need real wallet retest. This design adds no claim that the existing deployed fix works or that a grammar test substitutes for Phantom. No funds/chain transaction is needed for signature-only consent tests; live enablement/release remains separately gated.

## 9. Proposed regression plan and independent review order

Use disposable declared PG16 storage, deterministic barriers with backend blocker observations/timeouts and transactions on separate connections. Assert authority, final ownership, nonce/attempt state, session count/provenance, participant/history preservation and exactly-one audit, not just absence of errors. Test both queue orders. Disable internal retries when proving ordering; deadlock victim selection is not part of the assertion. Preserve existing RED tests; new genuine failing behavior tests must precede implementation.
