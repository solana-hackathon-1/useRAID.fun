## Counter-schedules found (executed unless marked)

- **X1 — strong root makes any root-less Session writer deadlock (executed).** Writer A: `DELETE Session(old)` then `INSERT Session` for user D (FK ⇒ `KEY SHARE` on D). Merge: lock D, then `DELETE Session WHERE userId=D`. With the baseline `FOR NO KEY UPDATE` root: both succeed. With the amended `FOR UPDATE` root: **`40P01`**. The amendment is therefore only safe if _every_ writer that deletes/creates `Session`, `XAccount`, `WalletIdentity` or `OAuthAttempt` takes the root first.
- **X2 — any transaction inserting FK rows for two users in non-sorted order deadlocks against sorted `FOR UPDATE` roots (executed).** `NO KEY UPDATE` roots: no deadlock; `FOR UPDATE` roots: **`40P01`**. A grep of `rewards.ts` found payouts keyed by `xId`, not `User` FKs, and no multi-user FK writer was identified; the inventory is not exhaustive (finance/campaign paths **NOT RUN** under real interleavings).
- **X3 — LP03 confirmed (executed).** After `FOR NO KEY UPDATE`, a non-key `UPDATE "User" SET handle` succeeds while a `KEY SHARE` holder is open, but `UPDATE "User" SET "xId"` blocks (`55P03` at my 600 ms `lock_timeout`).
- **X4 — merge's wallet move holds zero advisory locks (executed).** `walletIdentity.updateMany({userId})` fires no `wallet-subject:<address>` key (trigger is INSERT / UPDATE OF address only). A resolver that decided ownership under the subject key can be invalidated by a merge that never took that key. Not a deadlock; a correctness/serialization gap.
- **Mixed-version rollout (source reasoning, not executed).** Watchtower replaces web and worker separately. During the window an old worker's waiting sweeps (cycle 3) and old root-less writers coexist with new strong-root merges (X1). Folds are default-off in staging, which limits exposure, but the release note must say so.

## Findings and required amendments (numbered)

**R1 (blocking before implementation) — Do not use uniform `FOR UPDATE` roots.** X1/X2 show the cost: strong roots create wait edges with every FK-inserting or root-less writer. Specify root strength per planned effect, decided _at plan time_ (never upgrade after acquiring):
`FOR UPDATE` only when the transaction deletes the row or changes `User.xId` (first-X bind, fold drop and fold keep that receives an X id); `FOR NO KEY UPDATE` when it mutates non-key columns (suspension, handle, role); `FOR KEY SHARE` for session-creating sign-in that mutates no `User` column. Fold-capable paths plan `FOR UPDATE`; a path that discovers it needs more strength after locks aborts and re-plans, it does not upgrade. This keeps LP03's xId rule and the drop-delete rule without serializing ordinary sign-ins. Prove with X1/X2 as regressions and a mutation that restores uniform `FOR UPDATE`.

**R2 (blocking) — Convert all writers in one slice and fence regressions.** Add a static architecture test that every write to `Session`, `XAccount`, `WalletIdentity`, `OAuthAttempt`, `WalletLink`, `Participant` in `src/` goes through the shared plan helper (allow-list the autocommit leaf statements), so a future root-less writer fails CI. Include sandbox/studio fixtures (`studio-sandbox.ts` upserts are separate autocommit statements today; keep them isolated to `STUDIO_SANDBOX`). Release note: the combined deploy is not atomic; pause Watchtower or accept a documented brief window while folds/links stay off.

**R3 — Merge plan must include the subject keys of every wallet it moves (X4)**, class order global → balance → subject → x-auth, or document why revalidation under roots is sufficient and test the resolver-vs-merge schedule. Either is acceptable; silence is not.

**R4 — LP08 hash/collation.** Confirmed `hashtextextended(...,0)` (64-bit) in `account-merge.ts:6`, `usdc.ts:69`, `identity-link/index.ts:42` and the wallet-links trigger (`'wallet-subject:'||address`). Accept the 2⁻⁶⁴ alias assumption (fixed integer keys 729102–729104 share the same key space). Require one shared key-builder module plus a contract test that the application key equals the trigger's key byte-for-byte; today they are separate string builders. Acquire in JS code-unit order with one statement per id; do not rely on database collation `ORDER BY` (current `ORDER BY id IN (...)` single statement in `account-merge.ts:44` must go).

**R5 — LP06 sweeps.** Accept materialized `ORDER BY pk FOR UPDATE SKIP LOCKED` then `DELETE ... USING` as its own autocommit statement. Add `LIMIT` batches (e.g. loop until none) so a large expired backlog is not locked in one transaction, and keep `< now` (worker) vs `<= now` (start) semantics. Re-verify "no delete-side FK/trigger" on any later migration (today `Session` deletes cascade nothing; `OAuthAttempt` has no FK).

**R6 — LP01/LP02/LP04/LP05/LP07 dispositions.** LP01 accepted (`wallet-auth.ts:171–182`: a linked result throws or proceeds without entering the fold at 183–209; keep the regression). LP02 accepted: only rotation takes `balance` before the challenge claim, no path claims a challenge while holding another identity lock; keep a test that two same-digest commands cannot form a cycle. LP04 accepted (one concrete child order, prelock before mutate). LP05 accepted, but a changed plan must trigger a bounded **re-plan from fresh unlocked reads**, not a user-visible failure for benign races like two tabs; fail closed only after the retry budget. LP07 accepted with X2.

**R7 — Prelocked module contract.** Public `identity-link` ports must keep working standalone (NO KEY UPDATE today). Add an explicit host-supplied "already locked" mode with contract tests and a consuming example; root strength changes alone are not a verified host composition. Reuse of the module in another host must still be correct when it does _not_ provide the plan.

**R8 — Required regressions (adds to the amendment's list).** X1 and X2 schedules in both queue orders; sign-in/rotation/revoke/merge of the same wallet; sweep versus new-version merge; every ordering/skip/revalidation/root-strength mechanism removed by a fault injection that must be killed.

## Selective session revocation (DEC-2026-10-12-03) — ACCEPT WITH AMENDMENTS

- Schema: nullable server-populated `Session.walletLinkId` with a same-account FK (composite `(walletLinkId, userId)` → `WalletLink(id, accountId)`), indexed; never client-supplied. Revoke = `ACTIVE→REVOKED` + delete matching sessions + audit in one transaction under the same plan/roots; sign-in after revoke denies, sign-in that won first is removed by the revoke.
- Provenance: attribution is derived from the credential _verified in this command_, never carried from the previous session. Wallet reauth with credential W keeps `via='x'` where the old session was X (existing rule) and records attribution only when authority actually comes from W. X completion and any session-replacing path must set attribution explicitly (null for X) and be tested for laundering both ways.
- **Rollout (resolves the open treatment, with evidence).** An unattributed session cannot have been authenticated by an additional credential unless such a credential exists. Linking has no route/UI and is disabled; staging has 0 `WalletLink` rows and 0 wallet-authenticated sessions. So existing null-attribution sessions are provably non-additional. Make that a **precondition gate**, not a guess: the enablement check (and the migration) requires `count(WalletLink)=0` _or_ (if any exist) a drain of 7 days (sessions are fixed 7-day tokens, `wallet-auth.ts:241`, `x-oauth.ts:266`) or forced reauthentication; and attribution-writing code must be deployed on every instance before the first link is created. No backfill.
- **Suspended self-revoke:** moot for sessions — suspension deletes all sessions and blocks sign-in, so a suspended account cannot authenticate to revoke. Operator-initiated revoke is a separate audited path; do not add a suspended self-service exception.

## Visible signed destination (DEC-2026-10-12-04) — ACCEPT WITH AMENDMENTS

- The server already binds the challenge to the account via `WalletChallenge.userId` (checked in `consumeChallenge`); DEC-04 adds _signer-visible_ consent. Derive both values server-side from the authenticated account.
- **Serialization:** the current parser is positional (`message.split('\n')[3]` statement, `[7]` chain). Put the destination in the SIWS `Resources:` section at the end (valid ABNF `- <URI>` lines, e.g. `urn:useraid:account:<id>` and `https://x.com/<handle>`), leaving lines 0–7 and the exact-statement match unchanged; keep the statement single-line. Validate handle against `^[A-Za-z0-9_]{1,15}$` and the account id against its format before interpolation (newline injection). Add parser round-trip tests with the SIWS reference grammar — the owner just hit Phantom "invalid formatting", so a malformed message is a real risk.
- **Verification:** compare the account ID in the _stored signed message_ with the command's session account and `challenge.userId`; require X still connected. Do **not** compare the live handle to the signed one: handles rename (`handle` is rewritten on each X login) while `User.xId` is permanent; the signed snapshot is preserved and failure is for account mismatch or disconnected X, not renames.
- Pending target-less `link-additional` challenges: reject as invalid (5-minute TTL; linking disabled so none should exist).
- **Real Phantom display of Resources: NOT VERIFIED** — whether Phantom shows the `Resources` lines to the signer must be checked on devnet before DEC-04 is called satisfied.
