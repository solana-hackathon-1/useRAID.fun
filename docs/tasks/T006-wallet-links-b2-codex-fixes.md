## Root causes

- **CR-B2-01 (expired session still links).** `observeLinkAuthority` read `clock_timestamp()` inside the `Session ... FOR SHARE` select. PostgreSQL computes the select list in the scan before the row-lock node, so when the lock wait is long the clock predates the wait. The XAccount `FOR SHARE` wait came after that reading, and the same early `now` also fed the module's proof check. A session expiring during either wait was judged live.
- **CR-B2-02 (merge / X reconnect deadlock).** The earlier N1 fix made `absorbAccount` lock `User` rows first, then take the `x-auth:<xId>` advisory lock. `completeConnection` takes that advisory lock first and then updates `User`. User→advisory versus advisory→User is a cycle (SQLSTATE `40P01`, observed as `Process … waits for ExclusiveLock on advisory lock … blocked by …`).

## Writer audit (reviewer asked to include other writers)

By inspection of every caller of `lockIdentity`, `absorbAccount` and every row/advisory lock in `src` (grep inventory), plus the interleaving tests above:

- `completeConnection`: advisory → OAuthAttempt → User/XAccount/Session; consistent with the order. `startAttempt`, `disconnectX`: advisory plus attempt/X rows only, no User row locks, so no cycle with merge or link.
- `absorbAccount` (reconnect fold and wallet fold): advisory → Users → X/Session/wallet. Moving `WalletIdentity.userId` does not fire the address-exclusivity trigger (`UPDATE OF address` only), so it takes no wallet-subject lock.
- `linkAdditionalWallet` / linked sign-in: subject advisory → User → Session/XAccount `FOR SHARE`; takes no `x-auth` lock. `rotateWallet`: balance advisory → subject lock (trigger), no User row lock.
- Suspension, logout and expiry sweep: single-row writers; they wait for an in-flight link and never wait on one while holding a lock the link needs.

This is analysis plus targeted tests. It is not an exhaustive interleaving proof (Codex also said it did not exhaust them); wallet-fold-versus-reconnect, rotation and suspension interleavings have no dedicated database test. One limitation is new: a merge can now fail closed with a generic `Error` (surfacing as a 500 on the wallet-fold path) if the dropped account connected X during its own lock wait. It is rare and fail-safe; mapping it to a sanitized status is left to B2c route work.

## Victim-signed challenge (item E) — assessment only, no policy change

Mechanism (re-read, not re-run; Codex reproduced it): the `link-additional` signed text has a fixed statement and the target wallet address but does not name the destination account. An attacker with an X-authority session on their account A can request a challenge for any public address, get the holder of that wallet to sign the server-issued text, and submit it; the address then links to A. After B2b, that wallet's sign-in resolves to A with a `via='wallet'` session. The reviewer verified the primary payout wallet of existing accounts is not redirected, and the reproduction needs a previously unclaimed address.

Impact on enablement: this is a social-engineering account-confusion and address-squatting risk. A plausible follow-on, which has **not** been exercised or tested, is that the victim then uses what they believe is their own account, so balances or deposits are attributed to A. It does not need a forged signature or a stolen key. **It blocks enablement of linking, and no route or switch is allowed to expose it until the owner decides a design.** It does not change the dormant-slice review (default-off, no route), matching Codex's disposition. Options for the owner (none selected, none implemented): (a) name the destination account in the signed statement (changes the shared challenge vocabulary bytes for `link-additional` only; the wallet display is the only user-visible defense); (b) require the signature to be produced in a session that is authenticated as the destination account's owner and show the destination handle at signing time; (c) a wallet-owner-initiated revoke or recovery path (O11) so a mis-linked address can be removed by its signer; (d) any combination. Canonical identity policy, the statement text and revoke scope are the owner's and Codex's to settle; this document redefines none of them. The existing owner questions (revoke session scope, suspended-account revoke, item E) stay open and blocking for B2c.
