# T006 identity lock protocol — design proposal for independent challenge

Status: **PROPOSED, not implemented.** Author: Claude Opus 5.5, 2026-10-11. **SELF-EVALUATED.** No production code, test, schema or configuration was changed for this document. Wallet linking stays disabled. B2c and B3 are not started. Nothing is committed. Codex is asked to challenge this design **before** any implementation; candidate 4 will be built only from an accepted (or amended) version.

Why a design first: candidates 2 and 3 each fixed the interleaving the previous review reproduced, and each review found the next cycle in the same graph (CR-B2-02 → CR-B2-05 → CR-B2-06/07). The cause is structural: identity writers acquire locks on overlapping resources in orders chosen locally, and multi-row statements acquire rows in unspecified order. This document replaces per-interleaving patches with one protocol that every writer follows, so the absence of cycles follows from the rules rather than from tested schedules.

## 3. The three open cycles, restated as protocol violations

- **CR-B2-06 (callback vs merge; two callbacks).** W3 takes its _claimed_ attempt (an arbitrary row of the drop's set) before W6 takes the drop's attempts in sorted order. Sorting the second acquisition cannot order a row already held. Violation: a row from a set is taken before the set's ordered acquisition, and the set is the wrong root anyway — attempts belong to an account, so the account should serialize them.
- **CR-B2-07 (expired sweep vs merge).** W1/W13 delete expired attempts across all accounts in physical order and _wait_ on rows held by others. Violation: a global multi-row writer participates in waiting at all.
- **CR-B2-05 (fixed in c3) and CR-B2-02 (fixed in c2)** were the same violation class: two writers ordered {X key, attempt, User} differently.

## 4. Proposed protocol

### 4.1 Levels (acquire in strictly non-decreasing level; never go back to a lower level)

| Level | Resources                                                                                                                         | Within-level order                                                                                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| L0    | Single-row command claim: `WalletChallenge` consume (the first statement of a wallet command)                                     | one row per transaction                                                                                                                                |
| L1    | Advisory locks, by class: `729103` → `balance:*` → `wallet-subject:*` → `x-auth:*`                                                | within a class, sorted key string; at most the keys known before L2                                                                                    |
| L2    | **Account roots: `User` rows of every account whose identity rows the transaction will read for a decision, mutate or delete**    | sorted by `id`, acquired by explicit `SELECT … WHERE id = $1 FOR {mode}` statements issued one id at a time in ascending order (mode per row, see 4.3) |
| L3    | Account-owned rows of accounts locked at L2: `OAuthAttempt`, `XAccount`, `Session`, `WalletIdentity`, `WalletLink`, `Participant` | per table in this order; multi-row sets acquired by an explicit ordered `SELECT … ORDER BY <pk> FOR UPDATE` before any DELETE/UPDATE of that set       |
| —     | Global sweeps (expired attempts, sessions, challenges)                                                                            | `FOR UPDATE SKIP LOCKED` in a materialized CTE; **never wait** (4.4)                                                                                   |
| —     | Single-row autocommit statements (claim, route `finally`, logout, affiliation)                                                    | allowed outside the levels: hold nothing while waiting                                                                                                 |

**Root rule (the key change).** An `OAuthAttempt`, `Session`, `XAccount` or `WalletIdentity` row of account A may be locked or deleted by a multi-statement transaction only while that transaction holds A's `User` row (L2), except by single-row autocommit statements and non-waiting sweeps. The account row, not the attempt row, is the synchronization point for the account's identity state. This makes the order of attempt rows irrelevant for correctness among protocol writers (they are mutually excluded per account) and keeps per-row order as defense in depth.

**Revalidation rule.** Any decision taken from unlocked reads before L2 — which X key to lock at L1, which accounts to lock at L2, the drop's X id, the owner of `profile.id` — is re-read after L2. If it changed, the transaction fails closed (existing guard text / existing `OAuthError('identity'|'state')`) without mutation. No retry.

**Stability argument for L1→L2 choice.** `User.xId` is written only by W3 and W6, both of which hold `x-auth:<that xId>` (W3: `profile.id`/`owner.xId`; W6: `drop.xId` moved to keep). So under `x-auth:<P>` the account owning `P` cannot change; the account set a callback must lock at L2 is therefore stable once L1 is held, except for the owner's own `xId` (null→Q by a different key), which the revalidation rule catches.

### 4.3 Lock modes

- Drop account in W6/W3-fold: `FOR UPDATE` at L2 because the row is deleted later. Taking `NO KEY UPDATE` and upgrading at DELETE (current code) can wait on any concurrent `FOR KEY SHARE` holder (FK inserts referencing the drop, `ensureHumanParticipant`) while holding the keep row and the drop's L3 rows. `FOR UPDATE` up front also blocks new FK-referencing activity for the drop during the merge, so the emptiness check stays true until delete.
- Keep account and all other L2 rows: `FOR NO KEY UPDATE` (does not block FK inserts on unrelated activity of the keep account).
- Session/XAccount reads for authority in W9: `FOR SHARE` (unchanged).

### 4.4 Non-waiting global sweeps

`WITH doomed AS MATERIALIZED (SELECT pk FROM T WHERE "expiresAt" < $now ORDER BY pk FOR UPDATE SKIP LOCKED) DELETE FROM T USING doomed WHERE T.pk = doomed.pk`

- `SKIP LOCKED` means the sweep never waits on a row lock, so it cannot be an edge in a wait-for cycle; rows it skips are left for the next run. It can still be waited on, which is harmless because it never waits afterwards.
- `MATERIALIZED` forces the locking subquery to complete before the DELETE, so the DELETE only touches rows already held (verify with `EXPLAIN` and a NOWAIT probe; do not assume).
- Applies to W1's expired-attempt deletion and W13's attempt, session and challenge sweeps.

### 4.5 Deterministic multi-row acquisition

Every in-protocol multi-row lock is a separate `SELECT … ORDER BY <pk> FOR UPDATE` followed by the DELETE/UPDATE of exactly that set by the same predicate. PostgreSQL applies `ORDER BY` below `LockRows`, so rows are locked in sort order (documented consequence: such a query may return rows out of order under READ COMMITTED). This will be proven per statement with a `NOWAIT` probe test (block the lowest row; assert a higher row is still lockable `NOWAIT`) rather than assumed. `DELETE … WHERE id IN (subquery FOR UPDATE)` is not used, because the join strategy decides when rows are locked.

## 5. Proof sketch and residuals

5.1 **No cycle among protocol writers.** Every transaction acquires resources in non-decreasing level; within L1 by class then key, within L2 by id, within L3 by table then pk. Single-row autocommit statements hold no lock while waiting. Sweeps never wait. A wait-for cycle needs some transaction to wait on a resource ordered before one it holds, which the rules forbid. Re-entrant acquisitions (nested absorb) do not wait.

5.2 **Mapping of known cycles.** CR-B2-02: L1 before L2 in both. CR-B2-05: callback takes L2 owner before touching attempts. CR-B2-06: both callbacks and the merge serialize on L2 of the drop (and keepers in id order) before any attempt row; the claimed attempt is no longer taken first. CR-B2-07: sweep never waits.

5.3 **Serialization cost.** Only accounts named in the operation are locked at L2. Unrelated accounts, unrelated X ids and sweeps proceed. Added contention: a callback now locks owner/user `User` rows before the attempt DELETE instead of shortly after; disconnect now takes the user's row. Both are the accounts being modified anyway.

5.4 **Residuals to challenge.**

- `OAuthAttempt` has no FK to `User`. W1 can insert an attempt for an account a merge is about to delete (W1 does not lock L2). Effect: an orphan attempt whose later callback fails closed (`session`/`state`). Proposal: accept and document (no deadlock, no mutation); alternative is W1 taking L2 `FOR KEY SHARE` on its user, which a dropping merge's `FOR UPDATE` would serialize.
- Writers not in the inventory: anything outside `src/` that writes these tables (scripts, migrations, manual operations). Out of scope; listed for completeness.
- Non-identity writers holding `User` locks (finance, campaigns) are unchanged; they do not take identity L1 keys after `User`. To be confirmed by grep during implementation.
- Lock-wait starvation, load and multi-instance behaviour are not proven by this analysis.

## 6. Questions for the independent challenge (Codex)

1. Is the **account-root rule** (identity child rows locked only under the account's `User` row) sound and complete for W1–W16, or is there a writer that must touch another account's attempts/sessions without its root?
2. Is the **stability argument** (only W3/W6 write `User.xId`, both under the matching `x-auth` key) correct, including admin tooling and sandbox fixtures?
3. Rotation takes `balance` (L1) before the L0 challenge consume. Should L0 be redefined as "a single-row claim may occur at any point because nothing else waits for that row while holding other identity locks", or should rotation be reordered?
4. Are `FOR UPDATE SKIP LOCKED` sweeps acceptable operationally (rows skipped under contention, deleted next run) and is the materialized-CTE form sufficient to keep the DELETE from waiting?
5. Is `FOR UPDATE` on the drop at L2 (instead of upgrade at delete) acceptable given it blocks the drop's new FK-referencing activity during a merge?
6. W7 B2b ordering: the linked-sign-in resolver takes L1 subject then L2 owner; the fold path takes L1 `x-auth` with no L2 held. Confirm no path holds L2 and then requests an L1 key. (PR #188's `lookupWalletLink` would violate this on its fold path, see §8.)
7. Is the per-statement `NOWAIT` probe the right way to prove ordered acquisition, and which statements must have one?

## 8. PR #188 implications (recorded, not acted on)

Under this protocol, PR #188's `lookupWalletLink` on every `verifyWalletChallenge` takes L1 `wallet-subject` then L2 `User(link owner)`; on its fold path `absorbAccount` then requests L1 `x-auth:<drop.xId>` while L2 is held — an L2→L1 regression that a W3 callback (L1 `x-auth` → L2) can close into a cycle. Any reconciliation must either take the fold's `x-auth` key before the lookup's L2 or reject linked credentials before taking L2. Its whole-transaction retry does not change this analysis.
