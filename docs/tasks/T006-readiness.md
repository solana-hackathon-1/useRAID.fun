## Actor, transition and concurrency contract for implementation

| Actor / action / resource / state                          | Required result and authority                                                                                                                                                                                                                               |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Visitor signs in with unused valid proof                   | Resolve known account/participant or create a new account and its unique HUMAN participant atomically. Connection alone is insufficient; reject replay, expired/wrong-domain/network/purpose/account proof.                                                 |
| Authenticated subject links a second wallet to own account | Explicit account-bound fresh control proof; resolve the existing canonical participant and preserve history/current commitment. Link grants no role, rank, extra capacity or beneficiary change.                                                            |
| Different account claims already verified provider subject | Conflict under persistent uniqueness and current proof/ownership policy. Shared display name/IP/token holdings are insufficient for merge. Historical/revoked subject treatment requires its declared policy, not an implicit reassignment.                 |
| Account requests recovery / merge                          | Explicit proof and independent scoped review of both identities and retained rights. No automatic movement of claims or accepted snapshots. Reject two active engagements; do not close either, release capacity or delete records to make a merge succeed. |
| Suspended/restricted subject                               | Contain new participation as policy requires; preserve a separately authorized safe claim/evidence channel. No support-driven payout redirect or erased entitlement.                                                                                        |
| Token holder / wrong Guild / ungranted actor / self-review | Login/linking supplies no Guild administration, private artifact access, assessment or self-acceptance authority. Existing scoped grant/role commands remain authoritative.                                                                                 |
| Scoped operations reviewer                                 | Only approved case-specific inspection/repair with audit; cannot sign as account owner, absorb arbitrary accounts or set paid/beneficiary state. Developer role supplies no live audit permission.                                                          |

Proposed transitions, still unimplemented: unlinked → proof pending → verified link; verified → revoked credential with history/claims/participant retained; recovery requested → evidence/review → approved or rejected command; rejected/conflicting proof makes no session/link/merge mutation. A successful second link changes credential state only. Profile deletion/anonymization requires O11 and outstanding-rights disposition; restrictive FKs and guard denial are prerequisite protection, not a retention-policy decision.

Link/merge/participant creation must atomically claim command receipt (actor + command + key), compare request digest, recheck proof/session/ownership/revision, persist identity mapping and audit/outbox. Same key with changed payload conflicts. Nonce remains one-use; do not silently redefine existing replay behavior as successful auth. Provider calls occur outside database locks; their proof observations are revalidated when consumed.

Coordinate account/subject locks with the section 13 order for source/terms → operators → sorted participants before acceptance, replacement, closure, recovery or merge. The concrete common identity lock hierarchy must be designed and reviewed with work/treasury owners before implementation; this readiness review does not claim the current provider/balance locks compose safely. Race tests must include link/link, subject claim/subject claim, merge/link, merge/accept, merge/financial write and deletion/new rights. Lock/retry the complete transaction; delayed closure may release only its own participant+engagement. No provider wait inside those transactions. Refuse conflicting two-engagement merges; one busy identity must not acquire a fresh free participant through link/rotation/recovery.
