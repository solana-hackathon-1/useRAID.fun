## 1. Outcome and requirement map

User outcome (AC01): a signed-in user who already has a verified wallet and history verifies **a second wallet**; the account keeps the **same canonical participant, history and (later) active-engagement capacity**, and the second wallet can subsequently sign in to the same account. Linking never changes the payout/funding destination, never creates a second participant or work slot, and never silently merges two accounts.

## 2. Current facts (verified by inspection of `origin/main`)

1. `prisma/schema.prisma`: `WalletIdentity { address @id, userId @unique, verifiedAt, previousAddress?, rotatedAt? }` — **`userId` is unique, so at most one wallet per `User`**. `User.wallet WalletIdentity?` is a single optional relation. `Participant` (HUMAN, unique `accountId`, immutable by trigger) exists but nothing in login/link code provisions it; there is no backfill, no `active_commitments`, no engagement table.
2. `src/lib/wallet-auth.ts` `verifyWalletChallenge(digest, signature, address, currentUserId?, sessionHash?)`: with a signed-in `currentUserId` and an address **not** already known, it looks up `walletIdentity.findUnique({ where: { userId } })` and, if present, throws `HttpError(409, 'Account already has a wallet.')`. This is exactly how AC01 fails today. With an address already owned by another account it either folds an empty wallet-only account into the caller (`absorbAccount`) or throws `409`.
3. `rotateWallet` is the only way to change the wallet: it requires X, takes `lockBalance`, forbids pending deposits/withdrawals, enforces a 7-day cooldown, deletes and re-creates the single row, and later `usdc.ts` pauses withdrawals 24 hours. Rotation therefore **is** the payout-destination change.
4. **The single `WalletIdentity` row is overloaded**: it is the login credential _and_ the funding/payout wallet. Readers that rely on `findUnique({ where: { userId } })`: `usdc.ts` (deposit source, withdrawal `walletAddress`), `raid-funding.ts` (funding signer match), `studio-campaigns.ts` (funding gate), `api/launch/[id]/enroll` (snapshot into `RewardEnrollment.walletAddress`), `x-oauth.ts` (fold guard), `account-merge.ts` and the account page. Dropping `@unique` on `userId` would make every one of those calls ambiguous and non-compilable under Prisma.
5. `WalletChallenge(digest, address, message, userId?, expiresAt, consumedAt?)` is consumed with an atomic `updateMany` in the same transaction as the link; the worker prunes expired rows (`worker-jobs.ts`), so a durable replay marker cannot be a foreign key to it. Purposes today: `signin | link | rotate` bound by statement text. Message hard-codes `Chain ID: mainnet`; `issuedAt` exists only inside the message text.
6. Legacy merge (`absorbAccount`) already refuses a mapped drop account (`hasHumanParticipant`) and the `Participant` FK/trigger fence blocks deletion; an unmapped empty source may still merge into a mapped keeper.
7. Preflight (`src/identity/inspectVerifiedLink`) requires a HUMAN participant snapshot with `revision`, `status` (ACTIVE/RESTRICTED) and `activeEngagementId`, an ownership observation, a proof observation and a policy. The repository has **no `revision` store, no restriction field except `User.suspended`, and no engagement store**.

**How AC01 fails today:** (a) legacy path returns `409 Account already has a wallet.`; (b) even if a second row could be written, there is no participant-keyed link store, no cross-table address exclusivity, and sign-in with the second address would create a brand-new wallet-only `User` (a fresh identity with empty history) because `verifyWalletChallenge` resolves only `WalletIdentity.address`.

## 3. Design decision

**Keep `WalletIdentity` exactly as is: it is the single payout/funding-bound "primary" wallet. Add one new table `WalletLink` for additional verified wallet credentials keyed to the account's HUMAN `Participant`.** A link is login/identity evidence only.

Why this is the smallest compatible change:

- Zero change to the six legacy readers, to rotation semantics, to `RewardEnrollment`/`UsdcTransfer`/`BalanceEntry` destinations or to the 24h/7d protections. Payout is unchanged by linking (16.13); a user who wants a different payout wallet still uses reviewed rotation. The readiness doc already requires "separate default payout selection from multi-wallet login".
- All additive: one table, one anchor index on `Participant`, three triggers; no existing row is mutated; no backfill.
- Cross-table exclusivity is enforced where old binaries cannot bypass it: DB triggers on both tables that take the same advisory lock the application takes (§5, SQL §4).

Rejected alternatives:

| Alternative                                                     | Why rejected                                                                                                                                                                                                |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Drop `WalletIdentity.userId @unique`, add `isPrimary`           | Breaks six `findUnique({where:{userId}})` readers, rotation delete/create, merge logic and the account page in one change; silently blurs credential vs payout destination. Large blast radius.             |
| Mirror all `WalletIdentity` rows into the new table (backfill)  | Needs data mutation of live rows for no gain once triggers give cross-table exclusivity; rewrites history-bearing identity records; rollback harder. See §7.                                                |
| Store extra wallets as `JSON`/array on `User` or `Participant`  | No uniqueness, no FK, no per-link state; `Participant` is immutable by design.                                                                                                                              |
| Make a link the payout destination                              | Violates 16.13; would change `RewardEnrollment`/withdrawal behavior; needs treasury review (O05–O07).                                                                                                       |
| Wait for the full blueprint `identity_links`/`wallet_links` set | Provider links (X) and recovery are separate owners; this slice needs only wallet subjects now. `WalletLink` can later be re-pointed by a reviewed migration; naming keeps blueprint `wallet_links` intent. |

## 4. Data model summary (exact DDL in the proposal file)

`WalletLink`: `id uuid`, `accountId` (FK `User` RESTRICT), `participantId` + `accountId` composite FK to `Participant(id, accountId)` RESTRICT (new unique index `Participant_id_accountId_key`, so a link can only name its own account's participant), `networkIdentity` text (opaque canonical string from injected policy), `address` (base58 check; **unique on address alone** — conservative superset of the blueprint `(network, address)` subject because legacy `WalletIdentity.address` is network-less), `status ACTIVE|REVOKED` with `revokedAt` consistency check, `proofRef` unique (durable replay barrier; today the `WalletChallenge.digest`; no FK because the worker prunes challenges), `verifiedAt`, `linkActorAccountId` (= `accountId`) and `linkRequestId` provenance. Guard trigger: never deleted; only `ACTIVE → REVOKED`; reactivation impossible (recovery policy is OPEN O11). Exclusivity triggers on `WalletLink` insert and on `WalletIdentity` insert/`UPDATE OF address` use `pg_advisory_xact_lock(hashtextextended('wallet-subject:' || address, 0))` and raise SQLSTATE `23505` with constraint `raid_wallet_subject_exclusive_v1`.

Prisma additions (later, with the migration): `model WalletLink` with relations `account User` and `participant Participant @relation(fields: [participantId, accountId], references: [id, accountId])`, `Participant @@unique([id, accountId])`, reverse lists `User.walletLinks`, `Participant.walletLinks`. `prisma migrate diff` must report no drift.

Derived, not stored: **identity revision** = `1 + count(WalletLink rows of account) + count(REVOKED rows)` (monotone because rows are never deleted). Status `RESTRICTED` iff `User.suspended`. `activeEngagementId` is `null` until an engagement store exists (gap G1). Reviewer question Q3 covers an explicit stored revision instead.

## 5. Command design: `linkVerifiedWallet`

New module `src/identity-link/` (pure SQL through the existing `IdentityTransaction` port, READ COMMITTED only, no Next/Prisma/global imports), composed in `src/lib/wallet-auth.ts` as `linkAdditionalWallet(userId, digest, signature, address, requestId)` behind a new challenge purpose `link-additional` whose statement says the wallet is added for sign-in and **the payout wallet does not change**.

### 5.1 Sequence (one host interactive transaction; no provider/chain/LLM waits inside)

1. Host authenticates the session (`currentUser()`; CSRF/origin/rate limit as existing routes) and passes `actorAccountId = accountId`. The module re-checks equality before any SQL (`WRONG_ACTOR`), mirroring `ensureHumanParticipant`.
2. Host runs `consumeChallenge(... purpose 'link-additional')` (existing signature + exact-purpose + atomic `updateMany`) **inside the same transaction**. Any later failure rolls the consumption back (legacy behavior preserved). The host then builds `LinkProofObservation` (VERIFIED, intent `LINK`, domain/URI from policy, `proofRef` = digest) and a session observation; T007 later replaces these internals (§6).
3. **Lock order:** (a) `pg_advisory_xact_lock` on `wallet-subject:<address>` (same key as the triggers; re-entrant), (b) `SELECT … FROM "User" WHERE id=$1 FOR NO KEY UPDATE` (serialises concurrent links/revokes and legacy `user.update` merges for this account while still allowing FK `KEY SHARE` checks), (c) participant ensure (`ensureHumanParticipant`, `ON CONFLICT DO NOTHING`, first actor/request never overwritten), (d) `WalletLink` insert. Receipt claim (T019) will precede (a) per `planCapacityLocks` (`receipt` first). No two-account locks are taken by this command, so the only multi-lock hazard is deadlock against legacy paths; PostgreSQL detects it as `40P01` and the host retries the whole callback (bounded, same `requestId`/proof).
4. Read, under those locks: ownership of the address across `WalletLink` **and** `WalletIdentity` (`UNCLAIMED`, `LINKED(accountId)`, `REVOKED(accountId)`); the account's `suspended` flag; link count/revision; existing participant.
5. **No-op short circuits** (before creating a mapping): address is the account's own primary or own ACTIVE link → `ALREADY_LINKED` with the existing record; proof consumption still commits with nothing else written (so a stale tab cannot be replayed).
6. Otherwise ensure the participant (creating the immutable mapping only now; a later failure in the same transaction rolls the mapping back), build the snapshot, call `inspectVerifiedLink` with the injected policy (domain, URI, `walletNetworks`, no providers). Any `BLOCKED` code throws a typed error and rolls everything back, **including the participant mapping and challenge consumption**.
7. Enforce the DEFAULT per-account cap (EXAMPLE value 5 active additional links; configurable; reviewer Q5) under the account lock, insert the link, write nothing else. Existing session rotation behavior of `verifyWalletChallenge` is preserved for the new route (no widening of the current session).
8. Return `{ linkId, participantId, address, networkIdentity, status, alreadyLinked }`; the HTTP DTO omits `participantId`/`accountId` (internal context, not displayed).

### 5.2 Outcomes and error mapping

| Situation                                                             | Result (preflight code → typed storage/HTTP)                                                                     | Effects                                                     |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Fresh proof, unclaimed address, ACTIVE account                        | new ACTIVE link; same participant                                                                                | link row; mapping created if absent; challenge consumed     |
| Address is another account's primary or link (ACTIVE or REVOKED)      | `IDENTITY_CONFLICT` → 409 (generic text, no owner hint)                                                          | full rollback; **no silent merge, no `absorbAccount` call** |
| Own REVOKED link                                                      | `IDENTITY_REVOKED` → 409                                                                                         | full rollback; reactivation = undefined recovery (O11)      |
| Suspended account                                                     | `ACCOUNT_RESTRICTED` → 403                                                                                       | full rollback; claims/case channels untouched               |
| Expired/consumed/wrong-purpose/forged proof, wrong account/domain/URI | `PROOF_INVALID` → 401                                                                                            | full rollback                                               |
| Unsupported network                                                   | `UNSUPPORTED_IDENTITY` → 422                                                                                     | full rollback                                               |
| Stale client revision (if the client sends one)                       | `REVISION_CHANGED` → 409                                                                                         | full rollback                                               |
| Same proof replayed (race/duplicate request)                          | unique `proofRef` violation on same account+address → idempotent `ALREADY_LINKED`; otherwise `IDENTITY_CONFLICT` | no second row                                               |
| `40001` / `40P01` / Prisma `P2034`                                    | `RETRY_TRANSACTION`; host retries the **whole callback**, bounded                                                | none persisted from failed attempt                          |
| Wrong isolation / malformed rows                                      | `STORAGE_CONTRACT`                                                                                               | stop; investigate                                           |

### 5.3 Sign-in and legacy interplay (changes the legacy file minimally; T007-neutral)

- `verifyWalletChallenge` sign-in lookup resolves the address through `WalletIdentity` **or** `WalletLink` (ACTIVE) and issues the session for the owning account — so the second wallet signs in to the same account instead of creating a new one. A REVOKED link cannot sign in. Suspended-owner check unchanged. `via` stays `wallet`; X-only privileged paths (admin requires X session) unchanged.
- The legacy "wallet-only account fold" branches are never reached for an address held in `WalletLink` (the owner is mapped, hence non-empty by `isEmptyAccount`); the result is `409` as for any other owner.
- `rotateWallet` to an address present in `WalletLink` (own or foreign) returns the existing `409 Wallet belongs to another account.`-style error (new explicit lookup) instead of a `23505` 500. Promoting an own secondary link to payout is **out of scope** (treasury/recovery review).
- **Old binary during rolling deploy:** a pre-feature binary signing in with a linked address attempts `WalletIdentity` insert → trigger `23505` → fails closed (error, no duplicate account). Pre-feature binaries never see links; they cannot link. Keeping the triggers on application rollback is mandatory.
- Merge: `isEmptyAccount` already returns false for mapped accounts, and `WalletLink` FKs make `User` deletion impossible. A merge that would move an unmapped drop account's primary wallet onto a keeper cannot collide with the keeper's links because the address is globally exclusive.

### 5.4 Idempotency and the T019 seam

Today's natural idempotency: one-use challenge + unique `proofRef` + unique `address`. A lost HTTP response followed by a client retry hits `409 Wallet challenge already used` although the link exists; the UI re-fetches the link list. **T019 (command receipts, parallel branch `claude/t019-command-receipts`) integration point:** claim `(actor, 'LinkWallet', Idempotency-Key)` with request digest `(accountId, subjectKey, proofRef)` as the first statement of the transaction (receipt is the first lock in `planCapacityLocks`, `COMMANDS.LinkWallet` is already declared in `src/contracts/ownership.ts`); same key + same digest returns the stored result (`ALREADY_LINKED`-shaped), same key + different digest → `IDEMPOTENCY_KEY_REUSED`. This slice must not import T019; it exposes `requestId`/`proofRef` and a single receipt hook so the later change is additive. Until T019 lands, AC69 remains unverified for this command.

## 6. Boundary with T007 (#49)

T006 (this plan) owns **after a proof has been accepted**: durable subject ownership, `WalletLink`, participant provisioning, exclusivity, conflict/revoked semantics, atomic link-with-consumption, sign-in resolution through links, DB-level `proofRef` replay barrier, and the `link-additional` purpose string/statement (minimal intent text).

T007 owns **proof verification quality**: nonce store/format and entropy, binding of domain/URI/**Chain ID to the configured network** (legacy hard-codes `mainnet`), `issuedAt`/expiry/skew policy, strict SIWS message parsing, session rotation/fixation hardening, per-IP/per-account rate limits, log redaction of signatures/messages, AC02 replay/domain-change tests. The seam is one function that returns a `LinkProofObservation` + session observation from the host's challenge store; T006 ships a thin adapter over the existing `consumeChallenge`, T007 replaces it without touching the storage module. T006 must not weaken or fork the legacy checks; T007 must not change link storage. Overlap tests (replay of a link nonce, wrong domain on link) are authored by T007; T006 only asserts that a rolled-back link leaves the challenge unconsumed and a committed link leaves it consumed.

## 7. Migration, backfill, rollout, rollback

- Forward migration: the proposal SQL under the orchestrator-assigned prefix `202610090003_` (renumber at merge if another migration lands first). Order of operations: apply migration → deploy app that writes links → enable feature flag. **Feature flag `wallet_links_enabled` (server and UI, default off)** gates the route/UI; disabling it blocks new links but keeps sign-in through existing links and keeps triggers.
- **No automatic backfill.** Justification: (1) existing `WalletIdentity` rows already satisfy cross-table exclusivity through triggers; (2) mirroring would mutate live identity data with no behavioral need; (3) participants are provisioned lazily at the first successful new link (consistent with the accepted storage rule "no login auto-provision"); (4) T003 §3 still requires a named custodian/audit before any data-mutating migration — the app is undeployed, so no deployed target is touched either way. Unlinked/unmapped accounts behave exactly as before.
- Rollback: application rollback keeps table, FKs and all triggers (else a second account could claim a linked wallet and linked wallets cannot sign in). A lossy drop is documented in the SQL footer; no money is affected either way. Restore: link rows ride the database restore; reconcile consumed challenges and sessions after restore (AC68 not verified here; sessions are not revived).
- T003 gates unchanged: before executing against anything but a disposable copy, the environment audit, backup/restore rehearsal and custodian are still required.

## 8. Money, privacy, security notes

- **Money (C08):** touches no obligation. Pre/post snapshots of `BalanceEntry`, `UsdcTransfer` (`walletAddress`, `recipient`), `UsdcAllocation`, `RaidEnrollment.walletAddress`, `RewardEnrollment.walletAddress`, `WalletIdentity` (including `previousAddress`/`rotatedAt`) must be byte-identical after a link. Withdrawal/funding keep using `WalletIdentity`.
- **Privacy (C09):** link list returns only the caller's own addresses, network label, status, verified time. No internal IDs, no other-account hints in conflict responses, no address in logs (log reason codes only). A wallet link grants no Guild role, private brief or repository access.
- **Security (C14):** existing `checkOrigin`, `publicRateLimit` and body validation reused for the new route/flag; per-account cap limits spam (07.5); no risk labels from shared network or young wallet. Sanitized errors carry the code only.
- Ownership observations are never accepted from HTTP; `inspectVerifiedLink` inputs are built by the trusted host inside the transaction.

Nothing here edits the canonical blueprint.

Risks and mitigations: (1) trigger on a legacy table (`WalletIdentity`) — small, `UPDATE OF address` only, covered by D4/D11/D15; (2) advisory-lock key collisions only add serialization; (3) READ COMMITTED reliance — port enforces it (D13); (4) deadlock against legacy `lockBalance`/merge — no cycle identified (link never takes the balance lock; triggers take subject locks after, not before, other legacy locks), PostgreSQL detects any, whole-transaction retry; (5) lost-response retry shows 409 until T019; (6) revision is derived and does not capture primary-wallet rotation; (7) a user may prefer promoting a link to payout — needs separate treasury review; (8) `proofRef` currently equals `WalletChallenge.digest`; T007 may change the proof format, so the column is an opaque reference with a format check only; (9) unique-on-address is stricter than the blueprint's `(network, address)` tuple (reviewer Q2).
