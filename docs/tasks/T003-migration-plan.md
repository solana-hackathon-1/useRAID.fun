## 2. Observed baseline and compatibility hazards

Baseline `13dd7ff6b0d097270c1d9a3b2ee8c3c8b99404eb` has 35 Prisma models and 18 migration SQL files. A verification manifest records every schema/migration-file SHA-256. The schema still has no persisted canonical Participant, Guild, TermsVersion, Engagement, ActiveCommitment, Asset, generic CommandReceipt or AccessGrant. T002 supplies additive validated DTOs/declarations, not those tables or commands. T001 and T002 acceptance records are dependency evidence, not deployed-data evidence.

Applied SQL is immutable, including its real data effects. `202609280001_x_connection` deletes in-flight OAuth attempts when callback/session binding changes; those authorizations must restart. `202610020006_auth_hardening` deletes administrator sessions; a restore must account for reauthentication instead of blindly reviving them. `202610020009_launch_finance_hardening` backfills failed-network-cost FeeClaim round references. `202610020002_job_dead_letter` adjusts historical submission/job states. Do not call every existing migration purely additive.

`202610020011_ledger_integrity` defines money vocabulary/FKs, deferred `balance_entry_conserved`, allocation/enrollment/moderation immutability, transfer identity guards and `raid_money_guard`. The earlier Studio migration owns `balance_entry_immutable`. Preserve functions, triggers and deferred behavior as well as Prisma models. The verified Raid guard freezes pool/rate/asset/network/recipient/amount/wallet/signature/target/cap/creator, but does not freeze every scope/timing/scoring field. Final `ALLOCATED`/`HELD_RESOLVED` phase/result guards do not establish full accepted-work consent.

`202610020012_state_checks` adds seven **NOT VALID** constraints: `Raid_status_check`, `Raid_trackingPhase_check`, `Raid_fundingStatus_check`, `Raid_fundingAsset_check`, `Post_qualification_check`, `Post_availability_check`, `Post_reviewStatus_check`. New writes are checked; deployed historical compatibility is unverified. Later validation must use the legacy vocabularies in `src/lib/states.ts`, not T002 engagement/listing enums. No validation, state normalization or constraint removal occurs here.

Policy hazard: `202610020004_raid_money_policies` defaults old `authorCapBps` to 10000 while runtime `authorCapBps()` defaults new funding to 2500. Tracking/rule/scoring versions, quoted rate, measure/review boundaries and dynamic minimum-payout/review settings require provenance audits. Preserve stored values and original evidence. A current runtime value cannot be presented as what a past participant accepted.

`isEmptyAccount()` checks only legacy activity tables. Before any new account-linked persistence exists, its guard/deletion paths must include new participant, link, consent, role, terms, command, case and financial references, with restrictive FKs and failing tests first. Otherwise a formerly empty account could be absorbed/deleted despite new rights. This is a hard entry dependency for the identity schema stage, not a later cleanup.

## 3. Audit gate before any migration execution

AG09 operations with AG03 identity/work and AG04 treasury supply a named authorized environment custodian and independent reviewer. Human names, approved environment, backup durability and actual deployed version are currently **unassigned/unverified**. Development access does not grant customer-data or treasury authority. Obtain an explicitly authorized, consistent read-only snapshot plus provider/chain observations with a common as-of/watermark; never inspect undisclosed live credentials or copy secrets into this repository.

Required sanitized evidence:

1. Environment identity, deployed build/schema revision, PostgreSQL version, migration IDs/checksums/applied failures, actual triggers/functions/indexes/FKs and `convalidated` flags. Compare deployed definitions with the repository; source hashes alone cannot prove deployed parity.
2. Counts/distributions of legacy status, tracking/rule/scoring/cap/funding policy versions; source timestamps and hashes of accepted terms/notices/consents where recoverable. Audit null/invalid/cross-campaign references, duplicate verified subjects, unsupported network labels, numeric range/precision and missing recipients. Store pseudonymous exception references with restricted case evidence, not raw profile/private content.
3. Per exact network/instrument: credited deposits, available/reserved balances, unpaid allocations, pending reward transfers/withdrawals/refunds, fee/rent obligations and finalized payouts. Follow existing bookkeeping to avoid counting reward credits and pending transfers twice. Reconcile to actual program/vault/custody and observation slot/finality. `reconcileUsdc()` is a legacy diagnostic, not a proof of full-asset accounting; its configured mint/recipient must be verified against the target network. Include SOL fee-derived and standalone funding paths independently.
4. Outstanding signed/submitted/unknown FinancialTx, launch/funding operations, payouts, USDC transfer intent expiries, jobs and provider effects. Preserve raw transaction evidence under its restricted storage boundary; summaries contain reference/hash/status only. Audit semantic retry bindings across multiple signatures before any import.
5. All disputed, restricted/suspended, withdrawn, held, blocked/frozen and partially paid records. A whole-pool admin release or suspended-login restriction is a known T001 gap; do not ratify forfeiture, hide accrued rights or erase claims by backfill. Escalate original contract/rights uncertainty to the owner/case authority while preserving funds/evidence.
6. Backup/artifact/config authority references, failure-domain/durability mechanism, recoverable acceptance/effect watermark and isolated restore results. Recover acknowledged terms, consents, operation IDs and capacity; a same-database outbox or a recent snapshot alone cannot establish zero loss of acknowledged authorizations.

Every mismatch gets a case owner, evidence reference, disposition and retest. Unknown consent/identity/asset facts go to a restricted unresolved mapping record; they do not receive fabricated current defaults. Repair proposals use reviewed commands/forward migrations with audit, retain original data and require affected-party consent when changing material accepted terms. **Stop** if authority, watermark, obligations, orphan disposition, backup recovery or migration parity cannot be established. Do not infer zero obligations from an empty test database or inaccessible provider.

The audit is NOT EXECUTED. Actual obligation quantities, consent/policy distributions, deployed checksum parity and restore assurance remain NOT VERIFIED. No gate is waived by accepting this planning document.

Acceptance: expected source/terms and individual consents → one transaction claims receipt, locks admission/source/terms, then sorted operators and participants using T002's order → rechecks funding/eligibility/restrictions/vacancy → creates pending engagement then FK-backed capacity/member snapshots/audit/outbox → ACCESS_PENDING. Conflict rolls everything back. Paid start requires current finalized binding and approved resources. Closure atomically records terminal outcome and releases only matching engagement commitments; settlement/access incidents remain. Importing legacy rows performs **none** of these acceptance transitions.

Competing operations include accept/accept, accept/refund, claim/appeal, Party replacement/closure, Challenge handoff/another offer, wallet merge/link, old cleanup/new acceptance, deadline/amendment and backfill/active legacy writes. Serialize using the owning domain's global lock order and version/digest/source rechecks; retry the whole transaction for serialization failure. Do not hold database locks during provider/RPC/finality/LLM waits. Operator reservations count distinct engagement IDs and survive multiple same-operator members; release only when none remains. Section 13.6's DEFAULT first managed individual-operator pilot permits one distinct active external engagement across its AI identities **and its own human engagement**. Broader organization operator capacity stays OPEN O15; no participant ever gains another personal slot.

For each backfill: persist stable source→target identity, source version/hash, batch checkpoint, target revision and exception disposition; enforce unique mapping and atomically record the result. Resume must verify existing mapping rather than generate a new identity. Capture concurrent changes through a reviewed transaction/revision or explicit write pause. Dual writes are permitted only after proving atomic ownership and old/new readers agree; no two independently authoritative writers. If a consistent snapshot/delta strategy cannot preserve acknowledged changes, pause the specific new mutation path and finish reconciliation before cutover. Do not pause required old claims/recovery without a supported safe continuity route.

Do not backfill audit actors, consent times, private grants, original policy defaults, semantic claim IDs or chain finality from today's assumptions. Source observations and unresolved mappings are not accepted customer contracts. A policy/authority/asset mismatch keeps the affected new operation disabled and the original obligation visible for authorized resolution.

## 6. Rollout, recovery and rollback boundaries

1. **Before expand:** approved section 3 audit, exact source/environment/release scope, named migration/rollback/case owners, old/new API/worker compatibility matrix, representative restored rehearsal data and feature-specific stop/continuity controls. No applied migration edits, force reset or production `migrate dev`.
2. **Expand:** additive nullable/backward-compatible structure first. Build indexes/constraints with reviewed lock behavior. Preserve restrictive history and finance triggers. Deploy compatible readers/commands before making new writes authoritative. Don't add default values that claim missing historical consent/verification.
3. **Backfill:** bounded resumable batches, provenance and immutable source mapping; dry-run counts/deltas first, then independently reconciled actual results. Each moved obligation has exactly one spending authority; bridge must prevent duplicate legacy/new settlement. Pause a dependent import if ambiguity or unexpected writes appear.
4. **Verify:** exact schema/trigger/checksum parity, no orphans/duplicates/precision loss, equal old/new entitlement/destination/policy totals per full asset, protected reservations, original receipts/jobs still reconcilable, expected denial and meaningful concurrency results. Validate legacy checks individually only after compatibility evidence. Required fixtures cover held/partial/restricted/unknown and old cap/policy variants, not just new happy paths.
5. **Cutover:** small named scope, server and UI gates, current recovery watermark and independent acceptance. Preserve routing to legacy claims/financial status/disputes/reconciliation. Monitor lock/retry rates, oldest commitments, outbox age, unknown effects, liability discrepancy, access incidents and failed mapping batches; thresholds/response owner selected for the actual deployment under O18/G10, not invented here.
6. **Restore rehearsal:** isolated database and approved object/config authority data, no live outbound effects. Simulate post-backup accepted work and successful external effect. Recover original terms/consents/operation IDs/capacity from approved durability; reconcile authoritative external receipts after the watermark before writes. Missing recoverable authorization keeps dependent commands unavailable and escalates to the named case owner. A provider transfer/grant alone is not evidence of missing consent.
7. **Rollback:** before any new writes, compatible application rollback can stop using unused additive structure; retain audit/mapping evidence. After acknowledged commitments/effects, retain new authoritative rows/constraints and a compatible claims/reconciliation worker. Use reviewed forward repair or read-only containment when old code cannot understand new data. Never drop obligation/capacity/receipt tables, disable money guards, edit settled history, reset claims, revive old grants, undo on-chain transactions or reinterpret assets. Database restore is disaster recovery with watermark reconciliation, not a shortcut to roll back accepted work.

Stop on checksum/schema drift, unexpected constraint rejection, unexplained liabilities, missing immutable evidence, duplicate semantic effects, orphaned capacity, inaccessible claims, excess lock/load or failed restore/reconciliation. Roll back only the reversible scope proven compatible; contain unsafe new actions and preserve old obligations/cleanup. Source inventory is not the deployed rollback assurance.
