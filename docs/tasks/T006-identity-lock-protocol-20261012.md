## Proposed acquisition protocol for challenge

1. **Plan from unlocked reads.** Gather the exact self/profile/primary/reservation account set and all required X/subject/balance keys. Record observations for comparison. No client role or owner field is accepted as an observation. New account IDs are server-generated; uniqueness failure rolls back.
2. **Advisory prefix.** Existing host global/financial keys precede subject and X keys. Within each class use one documented deterministic order. Acquire every key before roots; triggers must reacquire an already held subject key. The legacy 64-bit hash namespace can alias classes: independent review must either accept a qualified collision assumption for this bounded protocol or require a compatible namespace/migration design. No unconditional graph proof is asserted.
3. **Account roots.** Lock deduplicated IDs one at a time in an explicitly fixed order shared by every writer, initially FOR UPDATE for identity writer roots. Do not use a database collation order in one caller and JavaScript string order in another. Reject absent/changed roots or ownership after locks. Strong roots intentionally wait for pre-existing FK KEY SHARE holders and prevent new FK activity during a dropping merge. Cost/compatibility must be reviewed; weakening roots later needs evidence against every implicit upgrade.
4. **Owned children.** Prelock existing rows across all named roots in one table order: OAuthAttempt → XAccount → Session → WalletIdentity → Participant → WalletLink; within each table, fixed primary-key order. Use a separate lock statement for each sorted PK when cross-collation agreement is uncertain. Use the final needed row strength before mutation. Reads for link authority may use SHARE; rows to delete/update use UPDATE. Preserve post-lock database-clock expiry validation.
5. **Revalidate and mutate.** Re-read own live session, suspension, permanent X identity, profile ownership, reservation/primary owner, current proof/clock and merge activity. Any changed planned set aborts without adding a lock. Execute only the chosen plan; nested helpers take no previously unheld prefix/root/child locks. Inserted rows may require uniqueness/FK locks: list them explicitly and test competitors, including rootless legacy/fixture writers. Keep durable audit in the same transaction. Existing bounded whole-callback retry/sanitized errors stay; retry is not the proof of ordering.
6. **Leaf exceptions.** Wallet commands claim exactly one challenge once; rotation may take its balance lock first. No writer holding other identity resources subsequently requests a challenge held by a different identity command; prove this inventory obligation. Single-PK autocommit claim/finally/logout and separately committed skip-locked cleanup hold no lock into subsequent work. A failing obligation blocks protocol acceptance.

An acquired plan should be an internal typed host object, created by a shared helper, consumed by nested merge. It records account IDs, strongest modes and observations; it is not a client DTO or an authorization grant. Public reusable identity ports need a documented prelocked mode or compatible root upgrade that never occurs after child acquisition, contract tests and a consuming example. Choose that interface at design review before changing existing standalone contracts.

## Primitive observations and limits

The author experiments use the same actual User unique index and all repository migrations in a fresh PostgreSQL 16 target. `database-primitives.test.ts` observed: xId UPDATE blocked by KEY SHARE despite prior NO KEY UPDATE; non-key suspension update completed while KEY SHARE remained held; materialized cleanup skipped a locked expired attempt, removed only an unlocked expired row, retained a live row and removed the skipped row after release; analogous Session/challenge deletion progressed with the holder open; separate sorted root statements left the higher row lockable NOWAIT while the lower waited. These six checks prove their concrete statements only. They are not GREEN application fixes or a global protocol proof.

PostgreSQL's [row-lock documentation](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS) describes key-column UPDATE strength; its [SELECT locking documentation](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE) limits SKIP LOCKED to row locks. Cleanup tables currently have no delete-side child FK or trigger work, but a future migration must recheck that premise. DDL/maintenance and privileged manual writes are outside a live application row-lock proof; they require operational coordination.

The three original attempt deadlocks reproduce on current source with actual blocker PIDs and unchanged no-deadlock/rollback assertions. Additional links were false, folds true only in this dedicated process; production folds and linking remain off. The direct internal merge helper is callable regardless of the gate; these experiments do not claim that deployed routes bypass the fold gate. Current-source sanitized results and raw local evidence paths are in the continuation packet.
