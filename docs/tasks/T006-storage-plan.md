## Outcome and current repository facts

Outcome: a host can resolve/create one stable HUMAN participant for an existing `User`; retries and competing creates return that same identity. A canonical mapping makes its source account nonempty for legacy absorption, and database constraints protect it even when an older application does not know the new table. Participant creation competing with deletion/absorption has one serializable outcome, with no orphan mapping or partial identity move.

Inspected baseline: `prisma/schema.prisma` has 35 application models and 18 SQL migrations. `User.id` is the existing account authority. There is no Participant, Engagement, ActiveCommitment, immutable TermsVersion or generic CommandReceipt table. `WalletIdentity.userId` is unique and `address` is its primary key; its relation cascades on account deletion. `src/lib/account-merge.ts:isEmptyAccount()` checks seven legacy categories and rejects ADMIN/suspended accounts. `absorbAccount()` moves wallet/X identity, removes the dropped account's sessions/attempts, deletes that account and records a moderation event in its caller's transaction. Wallet and X authentication call these helpers; X uses an `x-auth:<subject>` advisory lock, while wallet rotation/legacy treasury use `balance:<userId>`. Neither namespace establishes canonical work capacity. There is no production account-deletion command in the inspected source; direct ORM/SQL deletion still needs database protection.

This first slice stores the immutable account-to-participant mapping and extends the existing guard. Multiple verified wallet links, auth/session/proof consumption, canonical work/capacity, account recovery/review commands, rights retention policy, Guilds and treasury follow their own contracts. It does not backfill every User or promote historical wallet/provider metadata into verified links. An account mapping creates no rank, role, permission, active work or payout entitlement. Its presence must not prevent permitted inspection/recovery of existing claims.

Storage is a privileged internal port. Public clients, visitors, token holders and a wrong-account session have no direct storage command. The composing identity service must establish current authenticated account authority before calling it for a user action; a separately authorized import would need its own provenance and scope. This slice supplies no authentication verifier and cannot attest a caller-supplied account ID. The host supplies one real transaction, no global database/session/config singleton. A restricted account's stable existing mapping can be read for permitted claim/recovery purposes; storage cannot lift restrictions or authorize new work. Low-level mapping creation grants no user-facing permission.

State transitions: existing User/no mapping → valid internal provision in one host transaction → one HUMAN mapping; existing mapping → repeated resolve → same immutable mapping; absent User → provision → typed missing-account failure/no row; mapped account → legacy absorption or direct deletion/reassignment → rejection/full rollback. No accepted-work state, beneficiary, credential, session or capacity transition is part of provision.

## Proposed physical mapping and database protection

Use a single new Prisma `Participant` model/table, with one HUMAN row per existing `User.id`. Do not create a second account/login authority. Proposed fields: `id` UUID primary key with PostgreSQL `gen_random_uuid()` default; `kind` text default HUMAN with a check allowing HUMAN only in this slice; `accountId` text NOT NULL UNIQUE with an immediate FK to `User.id` using ON DELETE RESTRICT and ON UPDATE RESTRICT; `createdAt` UTC `timestamptz(6)` default `CURRENT_TIMESTAMP`; immutable `provisionActorAccountId` and `provisionRequestId` opaque text fields. A CHECK requires the provisioning actor account to equal `accountId`; its existing User FK therefore also anchors that actor. The immutable row records the original `identity.human_provisioned.v1` provisioning event (account/participant, actor, request, timestamp); it is an owned creation audit record, not a generic command receipt/outbox. Retries retain the first actor/request provenance. `User.participant` is an optional reverse relation. Reuse the existing `ParticipantSchema` HUMAN DTO (`id`, `kind`, `accountId`); do not duplicate its identity vocabulary. Future AI kinds require their reviewed operator/FK/check migration and cannot be inserted through this contract.

The exact [SQL proposal](../../planning/migration-proposals/T006-participant.sql), outside `prisma/migrations/` and not applied, creates the table, its constraints and a trigger preventing deletion or changes to `id`, `kind`, `accountId`, `createdAt`, `provisionActorAccountId` or `provisionRequestId`. No-op UPDATE may succeed. Ordinary User display/profile updates remain possible. This protects canonical mapping continuity during this foundation stage; it does not adopt indefinite personal-data retention or implement anonymization/recovery. A later reviewed retention/recovery change must preserve outstanding rights and canonical history and cannot be implemented by dropping the guard casually. Privileged database owners can alter schema/triggers; these constraints are not a claim of protection from an authorized superuser.

No existing migration is edited; no legacy row is updated/deleted, old state check validated or financial trigger replaced. No automatic historical backfill is included. Creating a mapping for a fixture is explicit and does not certify any old provider proof. Review the actual new migration SQL and Prisma drift before execution, including constraint names, enabled trigger, validation flags and timestamp/default behavior.

Database-first compatibility: the new restrictive FK protects mapped accounts against the old binary's final DELETE; its encompassing transaction must roll back earlier credential/session moves. Next deploy the canonical reference count in `isEmptyAccount()`. Keep mapping creation uncomposed into live login until the bounded store/guard/consumer and independent review pass. New guard code on a database without the table fails closed; migration/version parity is an entry check, not a swallowed missing-table error.

## Public storage and host contract

Proposed separate public feature directory `src/identity-storage/` preserves `src/identity/` as the existing pure preflight module. Its public functions accept an injected PostgreSQL transaction port and runtime-validated opaque account IDs; return the existing HUMAN Participant DTO, a boolean reference check or a typed sanitized failure. Suggested v1 operations: `findHumanParticipant(accountId)`, `ensureHumanParticipant({ accountId, actorAccountId, requestId })`, `hasHumanParticipant(accountId)`. Provision validates all opaque IDs and denies actor/account mismatch before SQL. The composing host must supply a verified actor context; these input fields cannot verify an untrusted HTTP assertion. The first provision records actor/request provenance in the immutable mapping, and a retry never overwrites it. No merge/delete/write-link/session/work/payment command is exposed. Public module imports only its owned ports and `src/contracts`; it does not import Next, Prisma SDK types, `src/lib/db`, environment variables or credentials. A host adapter outside that public feature wraps an existing Prisma TransactionClient with parameterized queries.

The transaction port provides `query<Row>(sql, bindings): Promise<Row[]>`; queries are module-owned SQL and values use PostgreSQL parameters. The host must supply one READ COMMITTED transaction for provision. It must keep all enclosing business mutations inside that transaction and expose failure rather than return partial success. The minimal consumer declares its own dependencies, User table/fixture, the exact storage migration, a dedicated local database and adapter wiring. It must not use a hidden RAID client or app credentials. A deterministic alternate transaction adapter can test typed failure/substitution, but only real PostgreSQL proves FK/uniqueness/locking equivalence.

Provision algorithm: validate account/actor/request IDs and require the actor account to equal the target account; select the existing User row FOR KEY SHARE; deny if absent; insert the HUMAN mapping with ON CONFLICT (`accountId`) DO NOTHING RETURNING its DTO; if another transaction already created it, read and return that existing mapping. Never use an upsert that rewrites its ID/account, infer a mapping from a wallet/display name, delete an old identity or redirect a beneficiary. Verify returned DTO kind/account and reject invalid adapter output. A lost response can be retried by immutable account identity; it cannot create a second business mapping. This is natural mapping idempotency with immutable owned creation-audit provenance, not delivery of generic command receipts or an outbox.

Typed failures must distinguish malformed input, wrong-account actor, missing account, storage-contract violation and whole-transaction retry. The host adapter recognizes PostgreSQL `40001`/`40P01` (including the actual Prisma wrapper) and produces a sanitized retry classification. It must not automatically retry just one SQL statement or swallow a constraint violation. Enclosing commands own a bounded retry of the entire transaction with the same semantic identity. No provider/wallet/LLM/finality call occurs under these locks. A retry exhausted by a host is visible and creates no partial effects.

## Shared locking and legacy-writer coordination

The existing [capacity lock declaration](../../src/contracts/ownership.ts) remains authoritative for future receipt → admission → source → terms → sorted operators → sorted participants. This proposal does not insert a new unordered advisory lock before all those groups or alter them. No capacity transaction exists yet and no agreement with an implemented work/treasury writer is claimed.

For this foundation only, PostgreSQL FK/key locks serialize the new mapping with User deletion/key update. The User FOR KEY SHARE lock is the source-mapping gate while canonical identity is absent; it must precede its insert. A concurrent DELETE requires a conflicting row/key lock. The unique `accountId` constraint serializes competing provisions. Account merges retain the existing X subject lock order in their callers; this slice adds a canonical-reference read and restrictive database fence, rather than acquiring an incompatible participant/balance advisory lock. No new work or treasury write is introduced. Existing financial/history FKs and immutable triggers remain authoritative.

Before future work/treasury commands can mutate canonical rights, record their exact account/participant lock integration and test their competing mutations. Once identity is resolved, those commands must use the canonical participant in the established final participant group; they must not hold a newly introduced account lock and then acquire earlier work/operator groups. Recovery merging multiple canonical identities is unavailable until its proof/review, sorted participant/operator locks, rights inventory and capacity contract exist. A conservative mapped-account merge denial cannot be labeled a proof of full two-active-engagement enforcement.
