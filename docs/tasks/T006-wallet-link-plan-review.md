# T006 wallet-link plan review (independent, non-author)

**Verdict: ACCEPTED WITH CONDITIONS.** No blocking finding. The design (keep `WalletIdentity` as the single payout-bound primary wallet, add an additive participant-keyed `WalletLink` table) is sound and the proposed SQL applies cleanly and enforces the intended constraints on a real PostgreSQL 16 database. The plan may proceed to executable stubs and RED only after conditions WR01–WR14 are incorporated into the implementation task (amend the plan or record them in the first implementation checkpoint). This is plan acceptance, not implementation acceptance; it does not verify AC01, any T006 criterion, or any code.

## Findings

Severity: **blocking** (must change before RED), **condition** (binding, see WR list), **note**.

| ID | Sev | Finding and evidence |
| --- | --- | --- |
| F1 | condition | **Constraint-name classification cannot work through the repository's Prisma path, and in-transaction idempotent fallback is impossible.** Plan U6, D4, D7 and the section 5.2 row "same proof replayed" assume classifying SQLSTATE 23505 by constraint name and then returning idempotent `ALREADY_LINKED`. Probe (`prismaerr.cjs` against the migrated DB): trigger-raised conflict via `$queryRawUnsafe` surfaces as `P2010 meta {code:'23505', message:'Unique constraint failed: '}` (no constraint name); via model `create` as `P2002 meta.target null`; a real unique-index violation as `P2010 ... message 'Key (address)=(3333...) already exists.'` (still no constraint name, but it contains the address). After any such failure the next statement in the same transaction returns `25P02 current transaction is aborted`, so a read-after-conflict cannot happen inside the transaction. Today `classifyIdentityStorageFailure` maps everything except 40001/40P01/P2034 to `STORAGE_UNAVAILABLE`, and `failure()` in `src/lib/http.ts` logs `error.message` for non-`HttpError` errors, so the raw message with the address would reach logs (I06/C09). |
| F2 | condition | **Prisma drift on FK name** as shown above; the plan's "migrate diff must report no drift" holds only with `map: "WalletLink_participant_fkey"` (or renaming the SQL constraint to Prisma's default). |
| F3 | condition | **Reader inventory understated.** Plan says six readers. Actual: 24 `walletIdentity.*` call sites in 16 files outside `wallet-auth.ts` (pages: creator/raids/[id], creator/balance, creator/new, creator/account, raids/[id], launch, tokens/[mint]; enroll route; `usdc.ts` x2, `raid-funding.ts`, `studio-campaigns.ts` x2, `tracking.ts`, `pump-launch.ts` x5, `x-oauth.ts`, `account-merge.ts`) and a **writer the plan omits**: `studio-sandbox.ts:42` `walletIdentity.upsert`. The design conclusion strengthens (an unchanged primary row is the only way to keep all of them correct) and none of them reads or writes `WalletLink`, so no reader can be subverted by a link. Writers that touch `WalletIdentity`: `wallet-auth.ts` (3 creates, 1 delete), `studio-sandbox.ts`, `account-merge.ts` `updateMany({userId})`; the exclusivity trigger fires only on INSERT/`UPDATE OF address`, so the merge path is unaffected (probe Q7). |
| F4 | condition | **Account-takeover persistence without step-up or revoke.** Linking requires only a signed-in session plus a signature from the new wallet. `rotateWallet` requires X as a second factor precisely so a stolen wallet-only session cannot redirect funds. A stolen wallet-only session could add an attacker wallet that remains a permanent login credential for a 7-day-session product; the plan has no revoke/unlink command (non-goal) and no way for the victim to remove it (rows are undeletable by trigger). Payout cannot be redirected (verified: `usdc.ts` withdraws to `WalletIdentity`), but the attacker keeps access to creator, enrollment and balance operations. |
| F5 | condition | **`link-additional` for an account with no primary wallet** creates a login-only link while every legacy reader still says "connect your wallet"; a later legacy `link` of the same address then hits the trigger (probe Q5/Q11, legacy `P2002` "Already exists"). AC01 is literally a _second_ wallet. |
| F6 | condition | **Participant-at-first-link regression for legacy merge/fold.** Verified in `isEmptyAccount`: a mapped account is never "empty". Example: a wallet-only account with no activity links W2, later signs in to X where the X account has history; before, the empty wallet account folded into the X account, now `x-oauth` throws `identity` and `wallet-auth` throws the "has its own account with activity" 409 text even though there is no activity, and no recovery/merge approval (W03, O11) exists. Fail-closed is correct for D13, but the user-facing consequence and message are inaccurate. |
| F7 | condition | **Sign-in and legacy-path edges not covered.** (a) Sign-in with a REVOKED link address today falls to `user.create` + `WalletIdentity` insert; the trigger turns it into `P2002` (HTTP 409 "Already exists.") with the new user rolled back (probe Q11), fail-closed but untyped; the plan says only "REVOKED link cannot sign in". (b) Legacy `link` of a `WalletLink` address by an account without a primary reaches `walletIdentity.create` and gets the same untyped `P2002`. (c) `rotateWallet`'s explicit lookup runs before the lock, so a concurrent link of the target address still reaches the trigger (probe C3: 23505) and must map to the same 409, not 503. (d) Rolling deploy: if the flag is enabled while any instance still runs the old sign-in code, a user who links W2 cannot sign in with W2 on that instance (fails closed, but breaks the AC01 outcome). |
| F8 | condition | **Check ordering in the module.** Step 5 (no-op `ALREADY_LINKED`) precedes step 6 (preflight with restriction, session and proof-binding checks). A suspended account re-linking its own wallet could receive `ALREADY_LINKED` instead of `ACCOUNT_RESTRICTED`, and the no-op path would skip the session/restriction observations. |
| F9 | condition | **D1 does not by itself prove AC01's identity half.** If the first link creates the participant, "same participant ID after W2 and W3" only proves W2 and W3 share a mapping created by the link. AC01 requires the canonical participant that already existed to be unchanged. The capacity half is correctly declared a gap (G1: no `active_commitments`). |
| F10 | condition | **RED sequencing.** Behavioral DB tests D2-D12 need the `WalletLink` table; without it a failure is `42P01 relation does not exist`, i.e. a setup error, not a semantic RED. The plan's section 10 intro and section 13 order (tests first, migration at step 3) do not say so. The storage slice solved this with a catalog-only schema RED on the pre-migration database, then applying the reviewed SQL, then behavioral RED against executable stubs. Old-binary evidence by raw `INSERT` alone also does not exercise real legacy code (Prisma error shape, no orphan `User`). |
| F11 | condition | **Proof-observation derivation is under-specified.** `inspectVerifiedLink` requires `issuedAt`, `expiresAt`, `domain`, `uri`, `networkIdentity`. The challenge row stores only `expiresAt`; `issuedAt`, domain and URI exist only inside the signed message text, and the message hard-codes `Chain ID: mainnet`. The host adapter must derive these without silently defaulting (for example `issuedAt = now` would make the issued-at check vacuous) and the stored `networkIdentity` must be the same constant the challenge generator signs, not an independent config value. |
| F12 | note | **`proofRef` unique is defense in depth, not the effective replay barrier.** `consumeChallenge` looks the digest up and rejects consumed or expired rows; the worker prunes only expired rows (`worker-jobs.ts:283`), so a pruned digest is already unusable. Plan wording "durable replay barrier that survives pruning" and test D7 ("replay after challenge pruning") should say the effective barrier is challenge consumption in the same transaction; the unique index protects against a future nonce-store change (T007). |
| F13 | note | **Lock order claim verified, with limits.** advisory `wallet-subject:<address>` then `User ... FOR NO KEY UPDATE`, participant, link insert. Legacy writers: `lockBalance` is an advisory lock (not a row lock); `rotateWallet` takes `balance:` then reaches the subject advisory only through the trigger; wallet-auth legacy takes the subject advisory (trigger) before the FK `KEY SHARE`; `absorbAccount`/x-oauth take `x-auth:` and `User` row locks and never the subject advisory; the trigger re-acquires its own advisory lock re-entrantly. No cycle found by reading all writers and by C1-C4. Deadlocks that PostgreSQL can still detect (40P01) are handled by whole-callback retry. Not a proof over all interleavings; the DB tests must keep the named races. |
| F14 | note | **Reservation asymmetry.** A REVOKED link reserves its address forever, but a primary rotated away (legacy `previousAddress`) releases its address (rotation deletes the row) and `User` cascade deletion of an unmapped account releases it too. This is legacy behavior and acceptable, but docs must not claim "a wallet once verified is never reassigned". |
| F15 | note | **T019 seam.** Receipt claim precedes everything in `planCapacityLocks` and `COMMANDS.LinkWallet` is declared (`ownership.ts:14`). T019 (PR #182) already uses migration prefix `202610090001`; the plan's `202610090003` is plausible (T029 likely `...0002`) but must be renumbered at merge and the "fresh 20-migration bootstrap" count recomputed (could be 21 or 22). A receipt replay must return the stored result **without** re-running `consumeChallenge`/signature verification, otherwise a lost-response retry hits "Wallet challenge already used" and AC69 for this command cannot hold. |
| F16 | note | **Scope.** One PR containing module, SQL, wallet-auth sign-in change, route + flag, docs, standalone host, CI registration and (optionally) Playwright is large. All items are inside the AC01 outcome, but the sign-in resolution change and the link route are separable from migration + module. See WR13. |
| F17 | note | **Issue W03** ("require proof/review for recovery and merges") is only partially served: D5/D9 prove merge denial for mapped accounts, not proof or review. The plan correctly lists recovery/merge approval as a non-goal; its criteria mapping should not claim W03. |

Items confirmed true as claimed: one wallet per `User` (`WalletIdentity.userId @unique`, `User.wallet` optional single relation); the 409 `Account already has a wallet.` path (`wallet-auth.ts` line 130); sign-in creating a new wallet-only `User` for an unknown address (lines 132-137); rotation is the only payout change (7-day cooldown, X required, 24h withdrawal pause in `usdc.ts:364`); `WalletChallenge` is pruned by the worker and consumed by atomic `updateMany`; `isEmptyAccount` already refuses mapped accounts; `ensureHumanParticipant` is used by nothing outside the storage module (no login provisioning); no engagement or `active_commitments` table exists.

## Answers to the plan's open questions

1. **Primary stays in `WalletIdentity`, links in `WalletLink`: accepted.** No legacy reader can be subverted (F3). Do not generalize to a single link store now. Add WR05 so that a link-only, primary-less account is not created.
2. **Global uniqueness on `address` alone: accepted** as the conservative default (Solana addresses are not network-scoped; a looser rule is a later migration). Permanent reservation of a REVOKED link: accepted as DEFAULT; release is an O11 decision. Document F14.
3. **Derived revision is sufficient; no client `expectedRevision` in this slice.** Keep it internal (tautological preflight input) and do not expose it in the HTTP DTO. A stored revision belongs with the revoke/recovery slice. Document that it does not move on primary rotation or X linking.
4. **Lazy participant creation inside the first successful link is acceptable; the no-op path must not create it.** It is rolled back on any rejection. It permanently blocks legacy folding of that account, which must be documented, covered by a test and reflected in user-facing copy (WR06). Provisioning at first need (engagement) would not give AC01 a participant to compare.
5. **Lock order is deadlock-free against every legacy writer found (F13).** A per-account cap is wanted now: keep it as injected configuration (EXAMPLE 5, not a recorded decision), count ACTIVE links under the account lock, and also bound total rows (suggest an example ceiling of 20) so revoked rows cannot grow without limit.
6. **Triggers hold for old binaries and pooling; constraint-name classification does not.** Old binaries fail closed: model writes surface as `P2002` and `failure()` returns 409 "Already exists." with no orphan user (probe Q11 and Prisma probe). Transaction-scoped advisory locks are pooler-safe; READ COMMITTED is enforced by the adapter. The Prisma raw error carries no constraint name (F1), so classification must be by SQLSTATE plus pre-checked ownership (WR01).
7. **The T006/T007 seam is clean with WR11.** T006 adds the `link-additional` purpose and the post-proof storage only; T007 owns nonce, domain, URI, Chain ID and strict parsing. T007 depends on T006 (issue #49 blocked-by), so the link route must not be enabled outside tests until T007's AC02 evidence exists (WR04). Chain ID `mainnet` stays as is in T006; T006 must reuse one shared constant.
8. **The T019 hook is sufficient without a `WalletLink` schema change.** Key `(actor, 'LinkWallet', Idempotency-Key)`, digest over `(accountId, subjectKey, proofRef)`. Same key and digest returns the stored `ALREADY_LINKED`-shaped result without re-verifying the consumed challenge (F15); same key, different digest returns `409 IDEMPOTENCY_KEY_REUSED` in the section 26.4 envelope (`retryable:false`, no address or proof in details).
9. **Acceptable, if recorded honestly.** AC01 and T006-A01 remain NOT VERIFIED/PARTIAL (identity half only) and T006-A02 NOT VERIFIED until a capacity table exists; the first PASS wording waits for the capacity task, which must register the follow-up test (link while a real commitment exists, row unchanged).
10. **Test set is sufficient in count, not yet in coverage.** D3 and D6 are not redundant (cross-account versus same-account serialization). D13 duplicates storage-slice coverage and can fold into U8. Raw-`INSERT` old-binary simulation is not enough: add a frozen legacy `wallet-auth` helper (sign-in, link, rotate) in the style of `tests/helpers/legacy-account-merge.ts`. Add the tests listed in WR10.

## Binding conditions for implementation

- **WR01 (F1).** Classify by SQLSTATE and pre-checked ownership, never by constraint name or message. Extend `classifyIdentityStorageFailure` (additively; existing tests unchanged) so P2010 `meta.code` 23505 maps to a sanitized conflict code instead of `STORAGE_UNAVAILABLE`; no address, proof, owner or raw Prisma message in errors or logs. Replace error-driven idempotency with `INSERT ... ON CONFLICT DO NOTHING RETURNING` (or a savepoint) plus a read under the same locks; amend U6, D4, D7 and the section 5.2 row accordingly. Add a test through real Prisma wrappers that a trigger conflict and a unique-index conflict both classify, and a test that nothing from `meta.message` reaches `failure()` output.
- **WR02 (F2).** Add `map: "WalletLink_participant_fkey"` (or rename the SQL constraint) and prove `prisma migrate diff` empty plus repeat deploy plus fresh bootstrap in the migration test (D14).
- **WR03 (F3).** Correct the reader/writer inventory in the plan/module doc (24 sites, 16 files, plus the `studio-sandbox` upsert writer) and state that none reads `WalletLink`.
- **WR04 (F4, Q7).** Add a step-up for linking, decided before RED and recorded: either an X session/connected X as in `rotateWallet`, or a fresh signature from the existing primary wallet in the same command. Ship a revoke/unlink command or an audited operator revoke procedure before the flag is enabled anywhere except tests. `wallet_links_enabled` stays off in staging/production until revoke exists, T007 AC02 evidence exists and WR07(d) rollout order is satisfied. The flag must gate the server command, not only the UI.
- **WR05 (F5).** `link-additional` requires an existing `WalletIdentity` for the account (typed `PRIMARY_WALLET_REQUIRED`); first wallet remains the legacy `link` flow. Add a test.
- **WR06 (F6).** Record the accepted consequence (a mapped account can never be folded or deleted by the legacy helper) in the module doc and runbook; update the fold/identity error copy in `wallet-auth`/`x-oauth` for mapped accounts without changing their rejection behavior; add a test that a linked account is rejected by both fold paths with a truthful message. Register a follow-up task for reviewed merge/recovery (O11, W03) before the flag is enabled.
- **WR07 (F7).** Typed handling for: sign-in with a REVOKED link address (no new user, no session, stable code); legacy `link` and `rotate` onto a `WalletLink` address, including the race where the trigger fires after the pre-check (same 409 text, never 503); suspended owner signing in through a link. Rollout order: migration, then deploy sign-in resolution everywhere, then enable the flag only after all instances run the new code.
- **WR08 (F8).** Evaluate restriction, session and proof-binding checks before the `ALREADY_LINKED` short circuit; add the test "suspended account with its own existing address returns `ACCOUNT_RESTRICTED`, challenge not consumed".
- **WR09 (F9).** D1 must pre-provision the participant with its own request ID and assert the participant row (ID, `createdAt`, provision actor/request) is byte-identical after W2 and W3, in addition to the lazy-creation case. Do not record PASS for AC01 or T006-A01; record "identity half verified at real storage, capacity half NOT VERIFIED (G1)".
- **WR10 (F10).** Two-phase RED recorded with exact commands: (1) catalog-only schema RED on the pre-migration database (assertions, no 42P01 counted); (2) apply the reviewed SQL to a disposable copy; (3) behavioral RED against executable stubs. Add tests: frozen legacy `wallet-auth` helper for sign-in/link/rotate against linked and revoked addresses (D4, D11); link-versus-rotate race on one address; link versus legacy fold with the real `absorbAccount`; the Prisma-wrapper classification tests of WR01; cap boundary (ACTIVE count and total ceiling). State before-RED baselines (unchanged legacy `409 Account already has a wallet.`) with command and SHA.
- **WR11 (F11).** Specify the thin proof adapter: `issuedAt`/`domain`/`uri` are parsed strictly from the exact message the server generated for that digest (anything missing or non-matching is `PROOF_INVALID`, never defaulted to now), `expiresAt` from the column, and `networkIdentity` from the same constant the challenge generator signs. T007 later replaces the adapter without touching storage; do not add nonce or Chain ID semantics in T006.
- **WR12 (F13).** Keep the documented lock order as a module contract, covered by named `pg_blocking_pids` tests for: link versus link (same account, different addresses), link versus link (two accounts, same address), link versus legacy insert, link versus rotate, link versus merge as keep and as drop, and the user-row-lock case. A new 40P01 observed in these tests is a defect to fix or an explicitly retried case, not a pass.
- **WR13 (F16).** Prefer two PRs after the plan is accepted: (a) migration + `src/identity-link/` + docs + standalone host + DB tests; (b) wallet-auth sign-in resolution + route + flag + route tests. (a) may be merged while the flag does not exist; (b) cannot enable anything until WR04. One PR is acceptable if the reviewer of the implementation can inspect both; record the choice.
- **WR14 (F12, F14, F15, F17).** Correct plan wording: effective replay barrier is challenge consumption, `proofRef` is defense in depth; document reservation asymmetry; renumber the migration against T019/T029 and recompute counts; receipt replay returns the stored result before challenge consumption; do not claim T006-W03.
