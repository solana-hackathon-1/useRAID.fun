# Private existing-project proposal form

T010C2 lets a current draft owner prepare, save, edit and reload a private pending token relationship. It implements R01–R04/R10/R15/R16 and I06/I07/I10/I13, with partial AC71/AC73 and privacy boundaries AC74/AC75. Pending preparation does not verify Founder control, recognize a Guild, activate a token, approve a public profile, grant access or create financial/capacity effects. Full T010 and independent acceptance remain NOT VERIFIED.

## Public boundary and host dependencies

`ProjectProposalForm` in `src/components/project-proposal-form.tsx` consumes strict v1 `GuildProjectProposalHttpState`, a positive current `draftRevision`, and an optional injected `ProjectProposalTransport`. The port exposes `save(draftId, input, idempotencyKey)`, `readProposal(draftId)` and `readDraft(draftId)`, each returning a standard `Response`. React19/ReactDOM19, zod4 and bs58/owned asset and draft/proposal schemas are declared dependencies. The module imports no Next, database, Node or authentication singleton. A host supplies its theme, route, authenticated transport, Web Crypto UUID support and verified server props. Client props and callbacks never establish authority.

The default transport uses same-origin POST/GET `/api/v1/guild-drafts/[id]/project-proposal` and existing draft GET, with private no-store reads. [Portable HTTP](raid-project-proposal-http.md) supplies strict resource/body/acknowledgment binding and current cookie, origin, rate and SQL permission enforcement. [Storage](raid-project-proposals.md) owns immutable versions, receipts and guarded transactions. The dynamic root page `/creator/guild-drafts/[id]/project` loads the current own draft and proposal in one guarded transaction; no actor/cookie is passed to the client. Anonymous pages show sign-in; foreign, unknown and restricted resources use a generic private error without saved content or fields. Metadata is generic. Saved draft pages link to this preparation route.

## Interaction and recovery

Inputs collect the complete claimed network identity, mint, token program and one to five different HTTPS reference URLs without credentials. Schema validation normalizes references and validates real address bytes. Saved references remain plain text and are never fetched as evidence. Loading/busy states prevent duplicate clicks; errors receive focus, inputs retain corrections, and saved values wrap on mobile.

A new save binds both current draft and proposal revisions. Successful acknowledgments must match the resource, expected next proposal revision, submitted draft revision, exact asset and normalized reference order. Lost responses, server failures, malformed acknowledgments and reused-key conflicts keep the original key/body in memory and lock mutable fields. Later401/403/429 responses retain an already uncertain intent; retry submits the same command. Keep the page open: refresh, closing the tab or process loss is not covered by durable client recovery.

A known revision conflict requires reloading current saved draft and proposal. Reload validates both resources, retains local fields, shows the current saved proposal and permits a reviewed retry with a new key. Concurrent changes between the two reads can produce another safe revision conflict; the server rechecks both revisions. Failed reload preserves the local proposal. New writes require non-demo mode and both `GUILD_DRAFTS_ENABLED=true` and `GUILD_PROJECT_PROPOSALS_ENABLED=true`. Default-off states disable saving while retaining current-owner saved reads and original receipt replay. No migration or backfill is added; removing this UI leaves immutable records and receipt recovery available through the existing API.
