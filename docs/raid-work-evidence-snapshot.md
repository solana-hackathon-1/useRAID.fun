# Applicant evidence snapshot for the reviewing Founder

Implements [DEC-2026-11-13-13](../RAID_AGENT_BLUEPRINT.md#0222-owner-delegated-decisions--13-november-2026) as confirmed by DEC-2026-11-14-12 (#331, T022, section 23.6, invariant I07). The Founder reviewing an application sees only what that applicant chose to share **for that application**, as an immutable snapshot, and only while the application is pending and the share is not withdrawn. Simulation and devnet only; nothing here grants a rank, Raid access or Guild authority.

## Contract

`src/work-loop/evidence-snapshot-contracts.ts` (strict version-one schemas, `EvidenceSnapshotHost`) and `evidence-snapshot-storage.ts`:

- `recordEvidenceSnapshot(tx, command, host)`: input `{applicationId, sharedSkillIds, consent: true}`. `consent: true` is the explicit per-application consent; applying shares nothing by itself. Only the application's own participant (real Session, canonical HUMAN Participant) may call it, only while the application is `SUBMITTED`, only for skills named in the exact stored terms' `requiredSkills`, once per application. The host's `readSkillRecords(tx, subject, skillIds)` is asked for exactly the chosen skills inside the transaction; the values read are frozen. Idempotent (`RecordApplicantEvidenceSnapshot` receipt; a replay returns the original snapshot).
- `withdrawEvidenceSnapshot(tx, command)`: input `{applicationId}`. Takes **no host**: a withdrawal only reduces what is shown, so no switch can trap consent (as application and consent withdrawal). Applicant only, while pending. **Final for that application**: a withdrawn snapshot is not replaced (a second share is `EVIDENCE_SNAPSHOT_EXISTS`).
- `readEvidenceSnapshot(tx, actor, applicationId, host)`: returns `{version, role, applicationId, availability, snapshot|null}`. `role` is `APPLICANT` for the application's own account, `REVIEWER` for the listing's creator who also holds current scoped authority (`host.authorize(..., 'MANAGE_LISTING')`, the same contract as terms publication, held transaction-locally); anyone else is `FORBIDDEN`, including another Founder and another applicant on the same Raid. **A missing application is also `FORBIDDEN`** (view, share and withdraw alike), so the commands are no existence oracle. `availability` is `SHARED` (the only case carrying `snapshot`) or `NOT_SHARED`; the **reviewer is only ever told `NOT_SHARED`** when nothing is visible (never shared, withdrawn, or application ended), so a withdrawal or the application's end is not disclosed to them. The applicant alone is additionally told `WITHDRAWN` or `CLOSED`. The view never selects `evidenceRefs`, other skills or any profile data.

Errors: the existing `WorkError` set plus `EVIDENCE_SNAPSHOT_EXISTS` (HTTP `REVISION_CHANGED`) and `EVIDENCE_SNAPSHOT_UNAVAILABLE` (nothing to withdraw, already withdrawn, or application no longer pending; HTTP `NO_LONGER_OPEN`). Events `work.applicant_evidence_shared.v1` and `work.applicant_evidence_withdrawn.v1` are identifier-only (`{termsVersionId}`); no skill, rank or evidence enters them.

## Storage and locking

Additive migration `202611140005_applicant_evidence_snapshot`: `ApplicantEvidenceSnapshot` (one per application via unique `applicationId`; composite FK to the exact application/slot/terms version/participant; per-element shape enforced by `raid_applicant_evidence_skills_ok` (exactly skillId/rank/status/assessedAt, known status, rank and date only when assessed); immutable by trigger `raid_engagement_immutable`) and append-only `ApplicantEvidenceSnapshotWithdrawal` (composite FK to the snapshot and its own participant; at most one; a BEFORE INSERT guard refuses it once the application is no longer pending). A BEFORE INSERT guard takes the application `FOR SHARE` and refuses a snapshot unless it is `SUBMITTED`, so a concurrent withdrawal/close and a share serialize at the database. Lock order for commands is listing, slot, identity roots, then the application row `FOR UPDATE`, as every admission writer. Participant FKs are RESTRICT and supply no identity mutation authority. Down migration is unsupported once used; backups keep snapshots with their applications and receipts.

## Reuse (R15/R16)

Explicit host dependencies: transaction (PostgreSQL READ COMMITTED), `EvidenceSnapshotHost.{allowNewWrites, authorize, readSkillRecords}`, existing work-loop/command-receipts/identity-locks modules and the `RaidApplication`/`RaidSlot`/`WorkListing`/`TermsVersion` tables. The module imports no skills code: the skill source is the injected port, so a host with different assessment storage supplies its own reader. The independent [raid-terms host](../examples/raid-terms/README.md) consumes it with its own `HostSkillRecord` table: the applicant shares one required skill, the Founder sees exactly it, a stranger is refused, a later change does not alter the snapshot, and withdrawal drops it.

Shared Root: `WORK_EVIDENCE_SNAPSHOT_ENABLED` (exact string `true`, default off) plus `WORK_WORKSPACE_READS_ENABLED` gate taking and viewing; **withdrawing needs no switch** (still a real session and the applicant's own application). Config validation **refuses** `WORK_EVIDENCE_SNAPSHOT_ENABLED=true` under `RAID_ENVIRONMENT=production` (`TEST_MODE_IN_PRODUCTION`), because reviewer authority is only the synthetic allowlist. An assessment state this contract does not know is left out of the Root reader, so that skill reads `NOT_ASSESSED` instead of failing the share. Reviewer authority is the synthetic `RAID_WORK_OPERATOR_ACCOUNT_IDS` allowlist (not Guild or production authority) and the caller must be the listing's creator. The Root reader selects the **current** `SkillAssessmentVersion` of the applicant's own assessments for exactly the chosen skills (no evidence, claim references or files). Routes (private, no-store, origin/session/rate-limited, strict bodies, idempotency key on commands): `GET|POST /api/v1/work/applications/{applicationId}/evidence-snapshot` (view / share) and `POST .../evidence-snapshot/withdrawal`.

## Verification

`tests/work-evidence-snapshot-db.test.ts` (real PostgreSQL): reviewer sees only the chosen skills and no private reference; consent literal, relevance, duplicate and empty rejections; `NOT_ASSESSED` instead of a guessed rank; immutability (UPDATE/DELETE rejected, later records unchanged, second snapshot refused); replay; **refusal of a stranger, another applicant on the same Raid, another Founder, a creator without current authority and a missing application (all `FORBIDDEN`), for view, share and withdraw**; withdrawal drops the view for good; closing the application ends access; database refusal for a closed application, another participant, a malformed skills element and a withdrawal after close; a two-connection test where a share waits on a concurrent uncommitted close and then fails `APPLICATION_CLOSED`; write switch off still allows withdrawal. `tests/work-evidence-snapshot-root-db.test.ts`: the Root reader over a real assessment, frozen across a later revocation. `tests/work-evidence-snapshot-http.test.ts`: strict contracts, privacy headers, status mapping, flag defaults. Independent review of this risky boundary (access, migration) and any human or UAT sign-off are NOT VERIFIED here.
