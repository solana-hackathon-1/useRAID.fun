# Private holder eligibility observations

T011A computes a private informational holder result from current-self trusted host facts and complete supported token-account observations. It implements06.3–4, R01–R04/R10/R15/R16 and I06/I07/I10/I13. [T010 recognition](raid-project-proposals.md) remains a prerequisite for real root/provider enablement. A legacy baremint Token, market display metadata, public ticker, candidate proposal or global role does not establish a recognized exact token relationship. No root route, UI, DDL, persisted membership, RPC integration, public enrollment, permission or payment effect is added.

## Typed reusable boundary

`evaluateGuildHolderEligibility(context, observation)` and exported contracts live in `src/guild-profiles/holder-observation.ts` and `holder-observation-contracts.ts`. The strict v1 context reuses `GuildSchema` and exact `TokenAssetIdSchema`; it supplies current actor/session/restriction, target account, current verified linked wallet addresses, current relationship reference/status, current time and a versioned approved ownership/dust/finality/freshness policy. These are server facts, never client-selected authority. Anonymous, restricted and foreign-account contexts throw sanitized AUTHENTICATION_REQUIRED/ACCOUNT_RESTRICTED/FORBIDDEN. Malformed or extra host/provider fields throw INVALID_HOST_CONTRACT.

The replaceable `GuildHolderObservationAdapter` versionv1 exposes `observe(GuildHolderObservationRequest): Promise<GuildHolderObservation>`. Request pins Guild, relationship/policy references, exact asset and full current supported wallet set. A VERIFIED response includes exact asset/reference binding, queried wallet set, completeness, observed time/slot/finality, provider ID/version and every supported token account with address/owner/exact asset/raw integer balance. UNAVAILABLE or CONFLICT carries only a safe provider reference. Null represents no available observation. Adapter/host must validate raw payloads with the exported schema; no error body or SDK type belongs in the contract.

The host owns actual verified wallet credential provenance, recognized relationship/policy approval, declared network/provider/extension support and complete account discovery. Do not query only an associated token account, trust ticker text or claim unsupported exchange custody as a verified linked wallet. A real provider must verify network genesis/program/mint and account ownership, raw-unit bounds, supported extensions, slot/finality and consistent complete observations. These live capabilities are NOT VERIFIED here. Technical input bounds are1000wallets,10000account rows and78raw digits; timestamps have at most millisecond precision. They do not adopt a production account/dust/provider policy.

## State and failure semantics

Complete fresh verified balance at or above the approved positive raw-unit threshold returns ELIGIBLE/true; a complete actual fresh zero or below-threshold amount returns NOT_ELIGIBLE/false. The blueprint DEFAULT positive threshold is demonstrated with synthetic approved threshold1; other dust/finality/age choices require actual host approval, not fixture promotion. Integer sums and slots remain strings/BigInt without numeric coercion.

Identical token-account rows count once; inconsistent duplicates return UNKNOWN/SOURCE_CONFLICT. Wrong network/program/mint, foreign account owner, duplicate/partial/mismatched wallet scope, incomplete observation, unavailable/conflicting provider, pending/revoked/conflicting relationship, unapproved/revoked policy and changed reference versions return UNKNOWN with null eligibility/balance. No current verified wallets also means UNKNOWN. Future observations are UNKNOWN; age at or above the approved maximum is STALE. Insufficient approved finality is UNKNOWN/FINALITY_PENDING. A provider failure or stale result never fabricates a zero balance.

The frozen private `GuildHolderEligibility` DTO includes Guild ID, exact target asset, relationship/policy references, computation time, state/reason, nullable holder eligibility/balance and actual matching observation time/slot/finality/provider metadata. Target asset/reference fields describe the supplied context; UNKNOWN never certifies recognition. Rejected asset/scope/reference observations do not attach unrelated time/slot/finality metadata to the target Guild. Matching stale/future/finality-pending observations retain actual metadata with null eligibility/balance. The DTO omits wallet addresses, account identity, private grant details and provider error text. Its informational/isAuthorizationToken/persisted/effect flags explicitly deny automatic Founder verification, permissions, public association, notification subscription, capacity consumption and work/claim changes. These describe this calculation's effects; they do not reset existing preferences or rights. Do not put private balances/metadata into a public projection or derive code/Guild admin permissions from the result. Existing [profile permissions](raid-guild-profiles.md) remain separately enforced.

The example is not real chain evidence or current project recognition.
