# Proposal-bound informational project control

T010D extends [v1 control proof](raid-project-control.md) with a coexisting v2 purpose that binds a [saved private pending proposal](raid-project-proposals.md). It implements R01–R04/R10/R15/R16, I06/I07/I10/I13 and partial AC71/AC73. A signature over an old draft-level v1 message gains no proposal binding. Nothing here approves actual authority/evidence, consumes a nonce, recognizes a Guild/token, grants Founder/access, publishes a profile or affects capacity/money.

## Stable public contract

`createProjectProposalControlMessage(context)` and `evaluateProjectProposalControlProof(context, facts, signatureInput, verifier)` live in `src/guild-profiles/proposal-control.ts`; strict typed schemas/results live in `proposal-control-contracts.ts`. Versionv2/purposeEXISTING_PROJECT_PROPOSAL_CONTROL context contains the original strict v1 control context and a strict immutable `SavedGuildProjectProposal`. Parent draft/revision and exact asset must agree before a signable message exists. No approved flags or request-chosen identity/resource/policy fields are accepted from callers; the signature input remains the v1 strict signature-only schema.

Signed bytes start with `RAID existing-project proposal control attestation v2` and contain fixed-order JSON with the entire saved pending snapshot plus the original canonical control message as a string. Proposal ID, draft ID, proposal/draft revisions, recorded time, exact network/kind/mint/program, ordered normalized references and pending/no-authority fields are bound. UUID case and UTC timestamps are normalized; object insertion order cannot change the message. The separate v2 envelope prevents using a v1 proof as v2, or a v2 proof as v1. Existing v1 bytes and result behavior remain unchanged.

Trusted facts contain the original v1 current account/session/draft/origin/clock/challenge/policy/authority/public-evidence facts plus the currently saved proposal or null. Existing authentication, restriction, ownership, revision, origin, expiry, challenge and approved/current/fresh record checks run before cryptography. A missing or different complete current proposal snapshot returns REJECTED/PROPOSAL_CHANGED and never invokes the crypto adapter. Claimed proposal references remain unverified private inputs; the separate approved evidence record must still come from an actual trusted provenance process.

The shared `ProjectControlSignatureVerifierSchema` validates the existing synchronous v1/ED25519 signature port. Supported adapters receive the canonical v2 message, signature and signer. The built-in tweetnacl adapter and independent Node crypto implementation use the same bytes. Unsupported adapters, malformed/extra inputs and nonboolean/async verifier returns fail with existing sanitized `ProjectControlContractError`; adapter exceptions become VERIFIER_UNAVAILABLE. No network/provider lookup, environment/database/auth singleton, secret key or log is imported by the module.

Result is a frozen versionv2 informational `ProjectProposalControlProofResult`, carrying challenge/proposal identity and revision, SIGNATURE_BOUND or REJECTED, the original denial reasons plus PROPOSAL_CHANGED, and explicit false persistence/nonce/Founder/Guild/token/grant flags. It is never an authorization token. AVAILABLE facts can produce repeated informational success; callers must not claim one-use replay protection.

## Host ownership and replacement

Declare Node22.12+/standard TextEncoder, zod4, bs58 and an explicit local signature adapter; React/Next/PostgreSQL are unnecessary here. Import canonical asset/identity/entity/state/draft/proposal contracts, not copies with divergent policy. [The independent example](../examples/project-control/README.md) dereferences canonical links into an available fresh directory and installs its own exact zod/bs58/tsx/tweetnacl dependencies. Its synthetic current records and deterministic disposable signing fixture prove both protocols, alternate crypto, current snapshot rejection and cross-version denial. They never establish live approval.

For production composition, the host must load actual current own proposal and approved policy/authority/evidence, issue an expiring purpose-bound challenge and preserve its exact snapshot and nonce. It must reauthorize and atomically consume nonce plus immutable receipt under current proposal/draft/authority checks before any separately approved recognition command, with exact recognized-asset uniqueness and history-preserving conflict/authority/token-migration review. Do not hold transaction locks during wallet, RPC or evidence waits. This command and real records remain NOT VERIFIED; no root route, signing UI, persistence, flag or DDL is introduced.

Replacing crypto preserves the original message/version/nonce/account/asset/proposal identity. Do not reinterpret or reroute an in-flight v1 or v2 proof; reconcile its original bytes, then issue a separately approved challenge if needed. The unused informational module can be removed without deleting pending history/receipts. Observability is limited to sanitized correlation IDs and typed failure categories; never log full messages/signatures/nonces/private records. No owned server/container is started by the CLI; retain test evidence and exit cleanly.

Genuine executable-stub RED26fail/2pass preceded implementation; first shared v1/v2 GREEN101pass, then additional signature-only/adapter/error and module boundaries passed108cases. [Task and source evidence](tasks/2026-10-13-T010-proposal-control.md) records actual later checks and SELF-EVALUATED timing. Matching UI/DB/backend evidence is reused only for unchanged boundaries; mandatory new-main CI is separate. Independent review, UAT, actual approval/evidence/nonce/recognized asset/history/provider/funded flow and O11/G01–G10 remain unverified.
