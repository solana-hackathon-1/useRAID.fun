# Versioned Raid terms and publication (T016)

Implements T016-W01–W03, R05/R15/R16, I03/I05/I08/I10/I13 and AC69/AC72–AC74 for an explicit synthetic M2 host. `WorkListing`, immutable `TermsVersion` and version-bound `RaidSlot` are additive tables; the legacy social-campaign `Raid` is unchanged. Status: implementation under self-check; independent migration/authority review, formal task closure, actual RAID Guild authority composition, UAT and release remain NOT VERIFIED.

## Public interface and dependencies

- `RaidTermsSchema` validates prospective terms without inventing an accepted roster. It covers outcome/deliverables/criteria, E–S difficulty, structured skill/policy requirements, admission/privacy, tools, finite ordered deadlines, reviewer/revisions, rights/dispute/finality, exact asset-policy/reward amounts and separate fee disclosure. `TermsSnapshotSchema` remains the accepted roster/beneficiary contract for subsequent engagement work.
- `saveRaidTerms(tx, command, host)` creates a DRAFT or adds a revision with compare-and-set. `readRaidTerms(tx, actor, versionId, host)` returns authorized immutable history. `publishRaid` checks the current version, future commitment window and supported mode, then creates/reuses its one exact reserved slot and opens the listing. Publication never starts work or acquires capacity.
- Host supplies a real READ COMMITTED PostgreSQL transaction, current cookie-derived `WorkActor`, mandatory `authorize` callback, explicit `allowNewWrites` (default off at a consuming application), and transactional `reserveSimulatedFunding` callback. Authorization is actor × Guild × MANAGE_LISTING, rechecked after waiting and before return; this version also requires the actual listing creator. The callback must hold current session/restriction/Guild-authority locks to commit, reject revoked/expired/suspended/cross-Guild/token-holder-only actors and never accept caller role flags. No built-in callback grants authority to a draft/proposal.
- Public commands import only shared contracts, asset-registry exact-amount helpers and command-receipts; no Next, Prisma, auth singleton, network request or ambient configuration. [Independent PostgreSQL consuming host](../examples/raid-terms/README.md) declares all source/migration/runtime dependencies and its own trusted authority policy.

The host owns the entire transaction including commit/rollback and retries; use `runCommandTransaction` in the RAID Prisma composition or equivalent `retryWholeTransaction` with classified 40001/40P01 failures. Retry the same actor/command/key/request; never only the final insert. Receipt → listing → version/slot is the module's mutation order; a host must coordinate any identity lock acquisition with the global identity protocol before composing capacity commands. No external network effects are allowed in the funding callback: it creates a transaction-local synthetic reservation tied to this exact slot/version/reward. Returned reference must be unique across slots; the database rejects reusing it. It proves only the host's synthetic reservation, never live funding.

## State, history and errors

New versions leave the listing DRAFT and close older AVAILABLE slot targets. Publication validates all fields and requires a fresh commitment deadline, explicit all-leg reservation, public SOLO HUMAN mode and APPLICATION admission for B/A/S. Other visibility/execution/participant kinds and live settlement fail closed. Only zero-fee founder-paid simulation is currently supported; no production fee/custody policy is selected. Full private briefs, Parties and AI/operator reservations belong to their own later tasks.

Database constraints reject an OPEN commit without the current reserved slot and malformed raw reward base units (positive u64), and triggers reject terms UPDATE/DELETE, noncontiguous versions, source/Guild/creator changes, slot rebinding and edits after a slot has been FILLED. Old accepted source/history remains frozen even after closure; replacement work needs a new source. A pre-acceptance amendment gets a new slot/reservation and cannot reuse the old obligation. New-write disablement preserves authorized history and original receipt replay. Same key with changed payload returns IDEMPOTENCY_KEY_REUSED. Replays reauthorize the current actor rather than trusting an old receipt.

Typed module failures: INVALID_INPUT, FORBIDDEN, WRITES_DISABLED, NOT_FOUND, REVISION_CONFLICT, TERMS_FROZEN, PUBLICATION_BLOCKED, FUNDING_REQUIRED, STORAGE_CONTRACT; receipt/driver errors retain the shared sanitized command-receipt contract. Applications must not expose raw SQL detail. Reads return private terms only to the authorized creator; safe public discovery requires a separate explicit DTO. Audit/outbox payloads contain identifiers only (`termsVersionId`, additive optional `raidSlotId`), never scope/private bytes.

## Verification and rollout

Meaningful tests are `raid-terms.test.ts` (publication contract) and `raid-terms-db.test.ts` (actual PostgreSQL immutable history, denied authority, stale revisions, replay, exact reservation, pre-acceptance replacement and assignment freeze). Initial unit RED covered complete contract/approval/deadline behavior. The first database attempt had a missing fixture handle; after correction, missing persistence failed before the additive migration, then the same behavior checks passed. Publication also caught an undeclared event field; the identifier-only envelope now declares `raidSlotId`. Test names/results and CI links belong in the PR, not committed logs.

Migration is additive with no backfill or production enablement. Apply with existing migration deploy; do not roll back acknowledged versions, receipts, audit or reservation history by dropping tables. A code rollback must preserve these rows. Independent review identified missing controlled transaction interleavings. Its single fix pass adds real-PG barrier/lock-graph tests for save/save, publish/amendment in both orders, duplicate publication, revocation while authorization waits and whole-transaction retry with one committed receipt/slot/outbox. Review disposition is recorded in the PR; no new per-slice evidence reports are committed.

The root application has no T016 route/feature enablement in this change: actual scoped Guild/session composition remains a required integration dependency. This module does not claim those tasks are implemented.
