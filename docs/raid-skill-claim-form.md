# Private skill claims in the browser

[Canonical skills](../RAID_AGENT_BLUEPRINT.md#08-skills-and-ranks) · [Protected API](raid-skill-http.md) · [Own-install React consumer](../examples/skill-claim-form/README.md)

Authenticated owners use `/raider/skills` to browse the actual published catalog and `/raider/skills/[skillId]` to record self-reported experience and up to five private HTTPS proof URLs. Orientation links to this flow. A claim is explicitly unassessed and supplies no verified rank, work admission, access, reputation, payment or extra capacity. T012 assessment/history, T013 trials/evaluator authority and T014 actual admission remain separate obligations.

R05/R06/R12/R15/R16/I06/I07/I10/I13/AC04–06 bounded/AC73–75 govern this M1 slice. Descriptive rank and numerical promotion O09 are unchanged. All 27 applied migrations, money/provider/link gates and actual stored assessments remain unchanged; no assessment model is asserted to exist.

`SkillClaimForm` is a React19 client component with parsed own `SkillClaimHttpState`, actual `PublishedSkillTaxonomy`, canonical `participantId` and an optional injected `SkillClaimTransport`. The versioned API DTOs are shared with the existing durable SQL commands. The ID binds acknowledgments, never grants authority; no actor/session credential is passed to the browser. The transport supplies save(skillId,input,key), read(skillId) and readCatalog(taxonomyId), each returning a native Response. The default uses protected Root APIs with relative URLs and no-store reads. Alternate hosts own authorization/origin/rate/private cache/receipt policy and theme/layout; no Next/Prisma singleton or global secret is imported by the component. Its direct dependencies and SSR consumer are declared independently.

Root pages are force-dynamic, await Next16 params/cookies, authenticate current sessions and authorize real catalog/claim reads before hydration. Each human uses the immutable canonical Participant mapping; an account without one follows existing Raider orientation, and the page never provisions a participant. Anonymous, revoked, restricted, unknown category and failed reads show fixed sign-in/unavailable messages without claim/proof/driver bytes. Metadata is generic. Root selects only `SKILL_TAXONOMY_ID` from a valid opaque ID; unset, malformed or unpublished selection is honestly unavailable. No example catalog is created or guessed. `SKILL_CLAIMS_ENABLED=true` controls new writes through the existing command, default false; own reads and original replay remain available. An actual deployment needs its real published catalog ID and the normal account/DB/session dependencies. Do not switch the catalog identity away from existing claim history without a reviewed migration/selection contract; this UI supports one host-selected catalog. Publication/admin policy and enabling actual deployment flags are separate work.

The catalog lists active categories. A known retired category URL retains the owner's saved claim as read-only and never revokes an assessment. The form validates canonical skill/domain/participant/catalog identity, displays current saved claim revision, and preserves local draft through failures. Initial missing rank/assessment is described accurately, not rendered as earned E-rank. Free text such as “S” remains a claim. Proof URLs are rendered as private plain text; no import, fetch, preview or provider verification occurs. Long references wrap. React escapes user content, labeled semantic controls and focused alerts support keyboard use, controls stay disabled until hydration is ready so early typing cannot be lost, a no-script explanation preserves readable saved data, busy guards prevent duplicate dispatch, and desktop/mobile reflow is tested.

A save normalizes bounded claimed text and 0–5 distinct HTTPS references without credentials. It snapshots the exact catalog/claim revisions and creates one UUID command key. Unknown outcome (lost response, invalid/mismatched acknowledgment or server failure) retains that exact key/body and disables field changes. Retry uses the original intent through later temporary401/403/429; a disabled-new-write command can still replay its original receipt. A success acknowledgment must match skill/domain/participant, stable existing claim ID, expected next claim revision, exact catalog ID/revision, normalized level and ordered references, with the strict CLAIMED/no-verification DTO. Only then are saved state and fields updated.

Known REVISION_CHANGED409 requires reloading the current catalog and own claim, preserving draft and reviewing the new saved revision before a new intent. Resource bindings are checked again. Failed reload retains the draft and blocked stale state. Reload cannot replace an unresolved unknown save. No localStorage/sessionStorage or durable page-reload recovery is claimed; keep the page open for unknown results. Definitive denied/validation failures preserve draft and display a clear action. Network/provider/session authority always remains on the server.

No new table, assessment/rank/reputation, audit/outbox/public projection, monetary transfer, access grant or capacity effect is introduced; existing SQL claim receipt/audit owns persistence. UI private payloads include the authorized catalog, own claim/proof URLs and canonical participant ID. They never enter public cards, generic metadata, logs or analytics. Independent assessment/storage authority and current eligibility checks cannot be replaced by any client prop or visible label.
