# Product metrics (operator)

`GET /api/v1/admin/metrics/product` gives an authorized operator an honest, read-only view of who activates and returns in the useful work loop, how work moves from draft to work accepted, what is due and disputed per asset, and how long reviews take, on simulated funding. Every ratio states its numerator, denominator, denominator definition and exclusions. It is private and default off, and it complements the per-state and per-asset [work-loop metrics](raid-work-metrics.md) rather than replacing them.

## Host contract

`PRODUCT_METRICS_READS_ENABLED` is an exact-string `true` flag, default off, independent of `WORK_METRICS_READS_ENABLED`. `authorize` must resolve only for an authorized operator and return their account id (it rejects with `MetricsHttpError` 401/403); `rateLimit(operatorAccountId)` rejects with 429. A response outside the strict `ProductMetricsSchema` is `503` and never forwarded. The storage module reads existing tables (`Guild`, `Participant`, `WorkListing`, `RaidSlot`, `RaidApplication`, `Engagement`, `EngagementMember`, `EngagementClosure`, `WorkSubmission`, `WorkReview`) and the SQL function `raid_effective_terms(engagementId)` (an engagement's current reward legs, with accepted amendments applied; a host without amendments may return its stored terms) through an injected READ COMMITTED PostgreSQL transaction and performs no write.

## Exclusion markers (T043, DEC-2026-11-13-10)

`POST /api/v1/admin/metrics/exclusions` lets an operator exclude one record from product metrics. It is behind the same exact-string `PRODUCT_METRICS_READS_ENABLED` flag (404 when off), requires the shared administrator rule (environment allowlist, X sign-in, `requireUser(true)`), a same-origin request and a per-operator throttle, and reads no body for a caller who is not an operator. Body (strict, `application/json`): `subjectType` (`GUILD`, `WORK_LISTING`, `ENGAGEMENT`, `PARTICIPANT`), `subjectId`, `reason` (`FIXTURE`, `INTERNAL_DEMO`, `SELF_DEALING`, `DUPLICATE`, `KNOWN_ABUSE`), `evidenceRef` (an id or ticket reference matching `^[A-Za-z0-9][A-Za-z0-9._:/#-]{0,199}$`, in both the schema and a database CHECK: markers are append-only, so free text such as an email, a name or a secret is refused rather than stored for ever), `effect` (`EXCLUDE` or `RELEASE`) and `supersedesMarkerId`. The request needs an `Idempotency-Key` header (a retry returns the same marker with `200`; another payload under that key is `409 IDEMPOTENCY_KEY_REUSED`), and each marker also writes one private `work.metrics_exclusion_recorded.v1` audit event (operator as actor, no outbox). The actor is the signed-in operator and the time is the database clock; neither can be supplied. `201` returns a new marker and `200` the same marker for an idempotent replay; `403` a caller who is not an operator (including a stored actor who is not an active administrator with an X id); `404` an unknown subject; `409` a chain conflict; `422` an invalid body.

Markers are append-only (`raid_append_only_guard_v1` rejects UPDATE, DELETE and TRUNCATE). A subject has one chain: the first marker has no predecessor and each later marker supersedes the current head, to change the reason (`EXCLUDE`) or to lift the exclusion (`RELEASE`, which must name its predecessor). Unique indexes admit exactly one marker per predecessor and one root per subject, so two operators cannot fork a chain; the loser gets `409`. A database trigger also refuses an actor that is not an active `ADMIN` account with a non-empty X id (as `isAdmin`) (defence in depth; the allowlist itself lives in the environment). A marker is effective while it is an `EXCLUDE` that no later marker supersedes.

Effect on the report: an excluded Guild leaves every figure; an excluded listing leaves the funnel, funding and its engagements (the Guild still counts); an excluded engagement leaves outcomes, settlement, disputes and review delay; an excluded participant leaves participant measures only, never a Guild figure. A marker changes metrics only: no work, reward, reputation or account record is touched, and `User.suspended` and `SkillEvidenceFingerprint` are never automatic markers. `excluded` still counts only work without a verified Guild; `fixtureExclusion`, `knownAbuseExclusion` and `duplicateExclusion` are no longer in `notMeasured`. The work-loop [metrics](raid-work-metrics.md) report does not read markers yet (NOT VERIFIED, follow-up), and demo or simulated-fund data is still not a public success claim (§31.2). Portable modules: `src/metrics/{exclusion,exclusion-http}`; the host supplies the flag, `checkOrigin`, `authorize`, `rateLimit` and the transaction, and the `examples/metrics` host carries a minimal `MetricsExclusion` table and a check that a marker removes a Guild and a release restores it.
