# Versioned submissions and criterion review

T023 lets the canonical HUMAN member of an `IN_PROGRESS` engagement record immutable, bounded submission versions, and lets the accepted terms' exact reviewer decide each one against the original acceptance criteria. All funding is simulated. It supplies a reusable PostgreSQL transaction boundary and consuming host; Root routes, screens, start/binding/access, disputes, settlement and deadline closure remain separate work.

## Public module interface

`submission-storage.ts` exports `submitWork` and `decideReview`, each `(tx, WorkCommand, SubmissionHost)` with `SubmissionHost = { allowNewWrites }`. Inputs are strict version-one schemas in `submission-contracts.ts`: `{engagementId, expectedSubmissionNumber, explanation, artifacts[1..20], dependencies, aiUsage}` and `{submissionId, decision: ACCEPT | REQUEST_REVISION | DISPUTE, reason, criteria[{index, result, evidence}], revisionDeadline}`. Results carry `EXECUTED | REPLAYED`, the stored record and the engagement's current state. Idempotent receipts are per actor and command kind; the same key with a changed payload conflicts. Original replay returns the first stored record without writing again, even with writes off.

Errors extend `WorkError` with `ENGAGEMENT_STATE`, `REVISION_LIMIT` and `REVIEW_EXISTS`. A stale `expectedSubmissionNumber`, or a decision on a submission that is no longer the latest, reports `REVISION_CONFLICT`. A missing, foreign or non-reviewer submission is one indistinguishable `FORBIDDEN`; a non-member submitting is `NOT_FOUND`.

## State, locking and privacy

Transitions allowed by the new database guard: `ACCESS_PENDING → IN_PROGRESS` (performed by `startEngagement`, see [starting accepted work](raid-work-start.md); the database still allows direct writers to make the transition, so the command is the only supported path), `IN_PROGRESS | REVISION_REQUESTED → SUBMITTED` (submit), `SUBMITTED → REVISION_REQUESTED | ACCEPTED` (review). A dispute records the decision and leaves the engagement `SUBMITTED` with capacity held until the dispute/closure tasks act; it blocks further decisions and resubmission. Each transition advances `revision` by exactly one and nothing else in the engagement row may change.

Lock order is command receipt → canonical identity (SHARE actor roots) → the Engagement row `FOR UPDATE` → submission/review inserts and capacity delete. Session and exact capacity are rechecked after the engagement lock wait. Competing decisions and submissions serialize on that row; the losers get typed state or conflict errors. Events `work.submission_recorded.v1` and `work.review_decided.v1` carry identifiers only (engagement and submission IDs, version 1 and 2 of the submission aggregate); no explanation, evidence or reference enters them.

## Migration and operation

`202610260004_work_submissions` replaces the T020 blanket-immutable engagement trigger with a lifecycle guard (exact transitions above, immutable other columns, no delete), widens the state check to the §12.2 vocabulary, extends the deferred capacity guard (active states hold exactly the roster, closed states hold nothing and keep their source), and adds `WorkSubmission` and `WorkReview`. Both are immutable, compose-keyed to the engagement member or submission, unique per number and per submission, and guarded at insert for state, bounded round, deadline, latest submission, exact independent reviewer and finite revision deadline. Deferred triggers require the engagement state to move with the record, and conversely require `SUBMITTED` to have a latest unreviewed submission, `REVISION_REQUESTED` a latest revision-request review and `ACCEPTED` a latest ACCEPT review, so a direct writer cannot change state or release capacity without evidence. New engagements must start `ACCESS_PENDING` at revision 1. FKs are RESTRICT; `WorkReview.reviewerAccountId` is classified as immutable attribution in the identity fence. Backup and restore must keep submissions, reviews, engagements and capacity together; destructive down migration is unsupported once used.

`202610270003_work_json_shape` (#240) mirrors the command schemas in the database: `WorkSubmission.artifacts` (1–20 strict `{kind, ref, immutableVersion}` objects, unique by ref and version), `dependencies` (≤50 non-empty strings) and `WorkReview.criteria` (1–50 strict `{index 0–49, result MET|UNMET, evidence null|string}` objects, one per index) are `CHECK`-validated, so a direct writer cannot store a malformed shape that `submitWork`/`decideReview` refuse. `202610270007_work_json_shape_js_rules` makes the mirror exact on the two string rules: the validators trim with the JavaScript `trim()` set (tabs, newlines, NBSP, Unicode spaces, BOM; `raid_js_trim`) and count UTF-16 units (`raid_utf16_length`), branch on `jsonb_typeof` with `CASE` for deterministic evaluation and pin `search_path`. It replaces the functions in place, so existing CHECK constraints stay bound and stored rows are not re-scanned (rows already stored with whitespace-only strings are not rewritten). It also refuses a JSON `null` for `kind` and `result`. Caveats: the rules are stricter than the earlier validators, so a row written directly (never through the commands, whose zod rules are at least as strict) could fail a later restore that re-adds the constraints; and U+0000 or lone surrogates pass zod but fail `jsonb` itself with a raw error rather than a CHECK violation, so the mirror is exact for what `jsonb` can store. Remaining boundaries, unchanged on purpose: the `ACCESS_PENDING → IN_PROGRESS` start has no precondition until the resource-readiness task lands, so only the synthetic host may perform it; a review decision is not refused after `deadlines.review` (blueprint §12: a review timeout notifies and routes to operations, and silence closes only at the operational deadline, never by a fault rule), and a `DISPUTE` leaves the engagement `SUBMITTED` with capacity held until the operational closure or a dispute task acts, so neither is to be exposed through Root as a finished flow.
