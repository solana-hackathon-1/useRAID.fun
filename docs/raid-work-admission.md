# Applications and exact-version offers

T021 extends [canonical acceptance/capacity](raid-engagement-capacity.md) with nonbinding HUMAN/SOLO applications and Founder offers for published PUBLIC/APPLICATION work. All funding is simulated. It supplies a reusable transaction boundary and consuming host; Root routes, screens, private admission, Parties, operators, binding/access/start and production gates remain separate.

## Public module interface

`admission-storage.ts` exports `submitApplication`, `withdrawApplication`, `issueOffer`, `revokeOffer`; each takes the existing `(tx, WorkCommand, AdmissionHost)`. Strict inputs respectively are `{slotId,termsVersionId,evidenceRefs}`, `{applicationId}`, `{applicationId,expiresAt}`, `{offerId}`. Evidence references are bounded internal references, not public artifact access. `admission-contracts.ts` owns strict version-one result schemas: status EXECUTED/REPLAYED plus application or offer. Results recover the original entity ID and its current state; history is retained. Acceptance's additive optional offerId preserves existing instant inputs/receipt digests.

`AdmissionHost` requires trusted `allowNewWrites`, positive integer `applicationLimit` (1–100) and current scoped `authorize` callback; no default success or global policy exists. New commands fail closed when disabled; current authorized original receipt recovery remains available. Submit/withdraw require the real canonical HUMAN/session; issue/revoke require actual current actor/session, exact creator and scoped callback held through commit. Host `authorize` has the same MANAGE_LISTING contract as terms publication, and must use only transaction-local data/locks. The host supplies request quotas/rate limits at its transport boundary. Root HTTP/origin/CSRF/rate policy is not implied by an internal command.

Dependencies remain owned work-loop, contracts, command-receipts, asset-registry and identity-locks. The host owns PostgreSQL READ COMMITTED, exact migrations, parameterized queries, bounded whole-domain retry and commit-before-delivery. `engagement-authority.ts` shares current actor/canonical participant, source/version and database-clock checks; provider/framework/Prisma globals stay outside this module. No network, wallet or model wait occurs under these locks. API changes that alter accepted intent require a versioned contract; additive optional fields preserve callers.

## State, locking and privacy

RaidApplication retains exact source/version/participant/evidence; SUBMITTED → WITHDRAWN or CLOSED. A new application may replace its own expired offer path after closing retained old records and rechecking quota. RaidOffer retains exact application/source/version/participant/issuer/expiry; PENDING → REVOKED or ACCEPTED, with ACCEPTED bound to the actual exact engagement. Expiry is evaluated against database time even if persisted state is still PENDING. Issuing another offer cannot revive an old expired/revoked path; reapplication and quota checking are required. Withdrawal revokes pending offers, revocation closes the application, and assignment closes all source applications and revokes competing offers. Changed/closed sources are immediately excluded from quota by current joins; no cleanup worker delay is authoritative.

Lock order is command receipt → WorkListing → RaidSlot → offer/application as needed → canonical identity advisories/roots/children. Submission takes an UPDATE root through the shared identity protocol to serialize this canonical participant's quota, then rechecks time/session before persistence. Other commands use SHARE roots; final session/authority checks survive waits. All commands lock source before any mutable admission row. Caller-supplied source/recipient identity cannot replace stored bindings. Only own canonical participants receive application results; only current scoped creator receives offer-management results. Unauthorized attempts roll back the receipt and events. No public reader/DTO, private artifact grant or token-holder permission is introduced.

### Acceptance with an offer

- **Outcomes.** An elapsed pending offer is `OFFER_EXPIRED` (HTTP `OFFER_EXPIRED`); a revoked or accepted offer, or one whose issuer no longer holds authority, is `OFFER_UNAVAILABLE`. An offer named on OPEN-admission terms is `INVALID_INPUT`; APPLICATION terms without an offer are `ADMISSION_REQUIRED`.
- **Issuer authority.** `AcceptanceHost.authorizeOfferIssuer(tx, {accountId}, {offerId, slotId, guildId})` is required whenever an `offerId` is named; a host without it fails `STORAGE_CONTRACT` before the offer lock, identity locks or any other callback. The issuer is judged as an account, never with a session. The command reads the issuer from the offer row it has already locked and asks last, after `assess`, `fundingAvailable` and the session/window recheck, immediately before inserting the engagement; the applicant's session and the commitment window are proven again after the insert.
- **Host obligation.** The command does not ask the issuer question twice, so the host's `true` must stay true until commit: read the authority it relies on inside the given transaction with a lock that a revocation must wait for (for example `FOR SHARE` on the grant row), or judge from state that cannot change mid-transaction. Taking those locks after the command's offer, slot and identity locks can invert another command's order; the host's whole-transaction deadlock retry is what serializes them. The Root host judges the synthetic operator allowlist, which has no rows to lock.
- **Identity locking.** A host that passes `identityLocks` to `commitEngagement` locks canonical identity before the source row, the reverse of submit's source-then-identity order; the same retry serializes them. A host that accepts application offers should not pre-lock identity; the command acquires it itself, in order.
- **Superseded terms.** When `saveRaidTerms` replaces a listing's terms version, it closes the listing's AVAILABLE slots, revokes its PENDING offers and closes its SUBMITTED applications (§14: unusable offers are revoked; history is kept). If anything was revoked or closed, the command records one `work.offers_revoked.v1` event in addition to `work.terms_saved.v1`: same aggregate (the listing) and aggregate version (the new revision), payload `{termsVersionId}` naming the **superseded** version. Consumers find the affected offers and applications by that version and the new version through the paired `work.terms_saved.v1`. A first save, or an edit that leaves nothing outstanding, records no revocation event; closing AVAILABLE slots alone records none either.
- **Lookup.** `RaidOffer(applicationId)` is indexed.

Open boundaries: withdrawal while writes are disabled or the account is suspended (deliberately deferred pending an owner policy, #239 item 7); the Founder-self-application guard (the host `assess` must reject it); the UUID lock-before-recipient-check existence oracle; and the unimplemented SHORTLISTED, REJECTED and DECLINED states.

The additive `202610260003_work_admission` migration enforces exact FK bindings, one submitted application per participant/source, one pending offer per application, immutable intent/history and accepted-offer engagement correspondence. Participant/User FKs are RESTRICT and supply no identity mutation/rehome/fold authority. `RaidOffer.offeredByAccountId` is classified as immutable attribution in the identity fence. `work.application_submitted.v1`, `work.application_withdrawn.v1`, `work.offer_issued.v1`, `work.offer_revoked.v1` reuse identifier-only terms-version event payloads and scoped receipt/audit/outbox; no evidence/consent/session body enters them.

Errors extend WorkError with APPLICATION_LIMIT, APPLICATION_EXISTS, APPLICATION_CLOSED, OFFER_EXISTS, OFFER_UNAVAILABLE (revoked or accepted) and OFFER_EXPIRED (an elapsed pending offer); existing current-session/authority/source/version/funding/capacity/receipt errors remain. A source filled first can report SLOT_FILLED. Same command key with a changed valid payload reports IDEMPOTENCY_KEY_REUSED, and original replay never reopens a path or reacquires capacity. Host transport maps safe statuses and protects internal errors.

## Operation and verification

Monitor current pending/expired path counts, typed conflict/retry exhaustion, constraint failures and receipt/outbox health without private reference dumps. Backup/restore must retain applications, offers, source histories, accepted work, capacity and receipts together. Preserve accepted and pending intent on application rollback; destructive down migration is unsupported once used. No external effect is reported complete, no live settlement/provider is selected and no worker is enabled by these events. Existing accepted work survives disabling new admission or losing a session.

`tests/work-admission-db.test.ts` verifies nonbinding application/offer, current founder/recipient denial, exact acceptance, busy-after-offer, cap/withdraw/revoke/expiry cleanup, new application after actual expiry, disabled-write replay, changed-intent conflict, true concurrent quota acquisition and accept/revoke races in both orders. Existing capacity/terms/identity/receipt/shared tests remain regression checks. The independent consuming host declares four exact migrations, its own session/Guild/reservation/consent stores and pg transaction adapter, and exercises stale busy offer then a fresh candidate's exact acceptance/competing-path closure. PR records contain actual checks, genuine RED/GREEN and independent review separately from SELF-EVALUATED author checks. No browser preview is required for this internal boundary.
