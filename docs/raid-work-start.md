# Starting accepted work

`startEngagement` moves an accepted engagement from `ACCESS_PENDING` to `IN_PROGRESS` once the exact funding binding is verified and the resources its terms need are ready. Until now nothing in the application could do that, so accepted work waited forever; the member now presses **Start work** in My Raid. Simulated funding only, behind a default-off flag.

## Contract and requirements

| Requirement                     | Behavior / verification                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Blueprint §10.2 step 6–7, §12.2 | Work starts only when the host confirms (a) the exact reservation for this slot, terms version and reward vector is still held (`StartHost.verifyBinding`, else `FUNDING_REQUIRED`) and (b) every resource the terms need is ready (`resourcesReady`, else `RESOURCES_NOT_READY`, wire code `SETUP_NOT_READY`, `409`, not retryable, so clients do not auto-retry a condition the request cannot change). Public work needs none. The simulated reference host checks the canonical `WorkSimulatedReservation` digest. |
| I10, R04, R13                   | Only the engagement's own HUMAN member with a current session can start it. Missing, foreign and Founder-only attempts are one `NOT_FOUND`; a non-participant is `FORBIDDEN`. Capacity stays held and the accepted terms are untouched; the single transition advances `revision` by one and nothing else.                                                                                                         |
| I05, I11                        | Idempotent per actor and key: replay returns the recorded start without a second transition even with new writes off, reporting the engagement's current state (it may already be submitted or closed). Two simultaneous starts serialize on the engagement row: one wins, the other is `ENGAGEMENT_STATE`. A `work.engagement_started.v1` audit event carries identifiers only.                                   |
| §12.5 (finite work)             | Refused as `DEADLINE_PASSED` when the effective (amended) submission deadline has passed, so no work starts that can only time out. Session and deadline are rechecked after host callbacks.                                                                                                                                                                                                                       |
| R15/R16                         | `start-contracts`, `start-storage` and the reference `start-simulated` are portable; the host injects `StartHost`. The independent [raid-terms host](../examples/raid-terms/README.md) starts its accepted candidate through the command.                                                                                                                                                                          |

Requirement mapping: T032 (start part; closes the "no start precondition" note of #240), AG03/M2, blueprint §§10.2, 12.2, 13, 16 (no money moves), 24.6–24.7, 28. Binding to a **live** escrow, private resource provisioning, repository access grants, a start deadline policy (`preparation`) and automatic starts remain separate work. The database transition `ACCESS_PENDING → IN_PROGRESS` is still allowed to any direct writer (test helpers use it); only the command enforces the preconditions, so the command is the only supported path. Full numbered task criteria, UAT and business/release approval remain NOT VERIFIED.

## Host contract

`WORK_START_ENABLED` is an exact-string `true` flag, default off, and also needs `WORK_WORKSPACE_READS_ENABLED`. `POST /api/v1/work/engagements/{engagementId}/start` uses the existing protected workspace boundary (origin check, authentication, rate limit, `Idempotency-Key`, empty strict body); the result is re-parsed and must be for the same engagement or the call fails closed. My Raid shows **Start work** only for a pending engagement while the flag is on, keeps one request key across a retryable failure and explains that starting checks the reservation and keeps the person's one active Raid slot.
