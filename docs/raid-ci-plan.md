# RAID CI and feature test coverage

[Project](https://github.com/orgs/solana-hackathon-1/projects/1) · [Live issue/epic status](raid-project-status.md) · [Workflow](../.github/workflows/checks.yml) · [Machine-readable feature matrix](../planning/raid-ci-matrix.json)

Every feature and integration requires meaningful automated checks for its own behavior. C22 is present in all 165 task packets. Existing test discovery covers the repository's current suites; it does not prove future blueprint systems implemented. No task becomes complete because a broad workflow passes while its own required tests are absent.

## Required jobs

| Check               | Evidence and failure rule                                                                                                                                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| planning-contracts  | Source hash, every task/core criterion, TDD/completion packet validation and status-generator regressions. Missing or removed contracts fail.                                                                                          |
| static              | Whole-repository formatting, generated Prisma client, TypeScript and lint. Generated local cache errors and existing typing gaps must be repaired in T005, not hidden.                                                                 |
| dependency-security | Independent dependency audit; failure stays visible even when static fails. No blanket suppression or unjustified allowlist.                                                                                                           |
| test                | All discovered Vitest suites with real PostgreSQL, migrations and schema-drift check. `RUN_DB_TESTS=true`; preserve JUnit artifacts on success/failure. Skipped material domain tests are not proof.                                   |
| docker              | Build and runtime smoke check for actual server/worker dependencies and migration availability.                                                                                                                                        |
| browser             | Desktop/mobile demo, Studio and database-backed live suites, production build and supported live-flow fixture. Reports/traces remain downloadable. Test fixtures do not prove a real external provider or production gate.             |
| ci-gate             | Runs even when an upstream job fails; requires all six named jobs successful. Failure, cancellation or skipped required job fails the gate. Repository branch protection must actually require this check to technically block merges. |

Browser and database jobs run independently to reduce wall-clock time. Concurrent runs on the same ref cancel outdated candidates; all checks refer to the candidate commit. Hosted workflows currently run only on manual dispatch because the owner reported exhausted Actions minutes (9 October 2026). Run the required checks locally as described below. No real external funds, publishing, customer secrets or production deployment are authorized by CI.

## Per-feature test layers

1. Unit tests for actual domain decisions, exact amounts, DTO validation and state transitions.
2. Shared adapter contract tests for supported and refused capabilities, typed errors and substitution.
3. Real database concurrency and constraints for capacity, acceptance, idempotency, Party atomicity and handoff.
4. Program/provider boundaries for funding, refund/binding/claim/finality and effective grants where applicable.
5. Security tests for actor/resource/Guild scope, private bytes, nonce replay, malicious input and sandbox/tool limits.
6. Crash, retry, partial result, cancellation, stale-generation, backup/restore and reconciliation evidence.
7. Desktop/mobile/keyboard, loading/empty/stale/denied/pending/failed user journeys.
8. Documented independent consuming-host and version/migration tests for delivered reusable modules.
9. Representative UAT, operational ownership and affected G01–G10 evidence before live enablement; these are separate from automated CI.

Define each applicable scenario before coding, record RED → GREEN → REFACTOR and wire the test into CI discovery. Do not add empty passing jobs for missing systems. The matrix distinguishes existing suite assignments from unimplemented domain coverage. A reviewer must verify that the actual test assertions cover that epic rather than infer coverage from a filename.

## Automatic status file

[raid-project-status.md](raid-project-status.md) refreshes from actual GitHub issue states on manual dispatch. Automatic issue events and the daily schedule are paused to conserve Actions minutes. It shows all epics, closed/total children, remaining work and candidates whose predecessor issues are closed. Closed with open children is explicitly flagged; deleted/missing issues remain Unknown. The bot writes only this status document to main. If repository permissions or protected-branch policy reject that write, the workflow fails visibly; it does not bypass protection.

CI status/evidence on the Project belongs to the feature's actual candidate; the status file tracks issue lifecycle and does not invent QA/UAT or release approval.

## Completion report CI records

Implementation reports require a `ci` object keyed by every required check from the task packet. Each record contains `result: SUCCESS`, full candidate `sha` and actual `evidence_url`. Missing/failed checks are rejected by the completion validator. A independently reviewed non-code task boundary may record why implementation checks are not applicable; it does not authorize feature or release approval. Reviewers verify the actual run and artifacts, not merely a string claiming success.

## Studio database isolation

The Studio preview helper requires Docker Compose and creates its own `useraid_studio_test` database. CI starts the existing test Compose override on port 55432 under project `raid-ci-studio`, supplies those Compose settings to the preview helper and always cleans up that isolated database. Demo/live jobs keep the GitHub service database on 5432. This corrects a real hosted-CI setup failure without weakening the preview safeguards or changing application logic.

## Local verification while Actions minutes are exhausted

Run `bash scripts/local-ci.sh` from a dedicated checkout of the exact candidate. The runner installs locked dependencies and runs every existing hosted layer: planning, static, security, migrated real-database tests and drift, container build/runtime, demo/Studio/live browsers, production build and live-flow fixtures. Host requirements are Node 22.12+, Python 3.12, Docker Compose, browser system dependencies, and free ports 3000, 3001, 3006, 3007, 3008 and 55432. The runner installs the locked Playwright Chromium revision. Install browser prerequisites with `npx playwright install --with-deps chromium` when needed. No GitHub token, provider credentials or production database is needed.

For a slow local disk, supply a test-only Compose overlay through `RAID_CI_COMPOSE_FILE` (the usual base and test override plus an overlay replacing only the database volume with tmpfs). PostgreSQL durability settings, constraints and test assertions stay unchanged; tmpfs is not crash/restore evidence. The isolated Compose project is `raid-local-ci`; databases are `useraid_test`, `useraid_shadow` and `useraid_studio_test`. Never run against a shared database. The runner stops its database on exit and retains its volume for inspection. Logs, candidate SHA plus working diff, result codes, JUnit and browser reports are retained under `/tmp/raid-local-ci-*` (override with `RAID_CI_LOG_DIR`). Any failed required step returns nonzero; prerequisite failure blocks later checks and must be reported as not run. A local success is not a hosted Actions check, branch-protection bypass, independent review or release approval. Attach sanitized results for each exact PR candidate; do not reuse main results for a different SHA.

Both hosted workflows retain all jobs and can be manually dispatched when minutes are available. Restore push/PR triggers and the status issue/schedule triggers through a reviewed change when the allowance returns. PR branches carrying older workflows still retain their old triggers until this change is incorporated.
