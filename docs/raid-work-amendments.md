# Consented amendments and replacement contracts

T025 lets accepted work change only by agreement and lets a terminated worker be replaced without rewriting history. The Founder proposes a change; nothing is effective until the affected member consents to that exact version, and any added reward is separately reserved first. A terminated attempt is replaced by a new slot with its own terms and reservation, linked to the attempt it follows. All funding is simulated. The Root composition (routes and workspace screens) is below; notifications, disputes, settlement, multi-member rosters and reopening terminal work remain separate work.

## Contract and requirements

| Requirement                                | Implemented behavior / verification                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC72, blueprint §11.5/§12.1                | `Engagement.acceptedTerms` stays immutable. `proposeAmendment` stores a complete new `TermsSnapshot` (`EngagementAmendment`, digest-bound) that changes only scope, acceptance criteria, reward amounts and the four deadlines. `respondToAmendment` by the engagement's own HUMAN member makes it effective; a Founder, admin or listing edit (`TERMS_FROZEN`) cannot, and the database rejects any change to accepted terms or to a decided amendment. The exact-digest consent and funding checks are enforced by the TypeScript command and the host; a database-level writer can only name a member's account, so database guards are a backstop, not a substitute for the command path. A missing reference fails `FUNDING_REQUIRED` and writes nothing.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| I10, I05                                   | Proposer must be the listing creator, host-authorized for the Guild and not a member; consent needs a current Session, membership and `AmendmentHost.assessConsent` for the exact digest. Authority is rechecked after engagement lock waits and host callbacks.                                                                                                                                                                                                                                                                                                                                                                             |
| R13, AC25, blueprint §12.5 DEFAULT reissue | `reissueRaid` replaces only a `TERMINATED` engagement with a closure. It creates a new listing, terms version, slot and distinct reservation, and a `RaidReplacement` link; the original slot, engagement, closure, reservation and unsettled claim are untouched and the original participant's capacity was already released by closure. Any eligible worker (including the earlier one, if still eligible) commits the new slot through the ordinary acceptance command, so eligibility, consent, funding and capacity are unchanged.                                                                                                                                                                                                                                                     |
| R15/R16                                    | Explicit `AmendmentHost` and the existing `WorkHost`, strict version-one schemas, own-installed PostgreSQL consumer that proposes, is refused consent without the member's agreement and the Founder's consent, then sees the agreed reward in its effective terms and claim.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

Known limits from the review (#244): one member's consent suffices because only solo rosters are implemented; database guards cannot bind consent to the digest or check funding; the consent-versus-submission race test asserts an either/or outcome rather than a barrier-controlled interleaving. At consent the proposer's Founder authority is asked of the host again as an account through `AmendmentHost.authorizeProposer` (never a session; required only to accept, so a host without it can still propose, decline and withdraw and fails closed on consent) and a lapsed proposer, expired proposal or lapsed amended deadline is `AMENDMENT_UNAVAILABLE`; a slot or earlier-amendment funding reference is `FUNDING_REQUIRED`; migration `202610270002_funding_reference_serialization` serializes slot-versus-amendment reuse of one reference with a per-reference advisory lock. `proposeAmendment` takes that same per-reference lock before its reuse check, so the loser of a concurrent slot-versus-amendment race is answered `FUNDING_REQUIRED` rather than surfacing the trigger's raw constraint error as `STORAGE_UNAVAILABLE` (#269).

Consent ordering (#269): on `ACCEPT`, `respondToAmendment` first refuses a decided or expired proposal and a proposal whose amended submission or operational-closure deadline has lapsed, then judges the proposer's current authority (a host without `authorizeProposer` fails `STORAGE_CONTRACT` here), all before `assessConsent` or `fundingAvailable` run. After those callbacks it re-reads the database clock and re-checks proposal expiry, deadline lapse and proposer authority, because callbacks and lock waits take time. The contract is the post-callback check, on the clock read immediately before the decision is written; the earlier check only avoids calling the host for a proposal that cannot be accepted. The database guard is a backstop for writers outside the command. Still open from #269: a proposal whose proposer lost Founder authority stays `PROPOSED` until the member declines or it expires (who else may withdraw or close it is an owner decision), and folding the funding-serialization checks into the existing BEFORE guards needs a migration.

Requirement mapping: T025 uses AG03/AG02, M2, R04/R13, I05/I08/I10, AC25/AC72 and blueprint §§11.5, 12.1–12.5, 13, 16 (no money moves), 17, 24.6–24.7, 25–28. Full numbered task criteria, Root integration, UAT, business/operating/release approval and withdrawal (no withdrawal command exists) remain NOT VERIFIED; roster/member replacement inside one multi-member engagement, extensions after submission and consent for non-HUMAN participants are not implemented. This bounded implementation does not close the issue.

## Public module interface

`amendment-storage.ts` exports `proposeAmendment`, `respondToAmendment` (`ACCEPT`/`DECLINE`), `withdrawAmendment`, `readEffectiveTerms` (member) and `readEngagementAmendments` (member or authorized Founder). `replacement-storage.ts` exports `reissueRaid(tx, WorkCommand, WorkHost)` with `{engagementId, terms}`. Errors add `AMENDMENT_EXISTS` (one open proposal), `AMENDMENT_UNAVAILABLE` (decided, withdrawn or expired), `CONSENT_REQUIRED`, `REPLACEMENT_EXISTS`; wrong state is `ENGAGEMENT_STATE`; unauthorized and missing are one `FORBIDDEN`/`NOT_FOUND`. Amendments are only accepted while the engagement is `ACCESS_PENDING` or `IN_PROGRESS`: submitted, closed or terminated work is never re-scoped. Events (`work.amendment_{proposed,accepted,declined,withdrawn}.v1`, `work.raid_reissued.v1`) carry identifiers only; `amendmentId` is an additive optional envelope key.

## State, locking and database enforcement

Lock order is receipt → actor identity (SHARE) → Engagement `FOR UPDATE` → amendment `FOR UPDATE`, matching submission, review and closure, so consent racing a submission yields exactly one winner. Migration `202610260006_work_amendments` adds `EngagementAmendment` (one open proposal per engagement, RESTRICT FKs, `proposedByAccountId`/`decidedByAccountId` classified in the identity fence), insert and update guards (only amendable fields change; reward legs, policy and beneficiary fixed; increase needs a funding reference; deadlines ordered and in the future; only a member may accept or decline, only the proposer withdraws; an accepted row needs consent), `RaidReplacement` (one per terminated engagement; the replacement must be a distinct, funded, open slot of the same Founder and Guild) and replaces the submission, review and closure guards so they read effective deadlines. TypeScript readers (submission, review criteria, closure claims, workspace) use `raid_effective_terms`. Backup and restore keep amendments with engagements; destructive down migration is unsupported once used.

## Root composition (HTTP)

Default-off `WORK_AMENDMENTS_ENABLED` (exact `true`) is the only write switch. Routes are private/no-store, same-origin for commands, cookie actor, `Idempotency-Key` required, strict bounded JSON (16 KB) and no query string:

| Route                                          | Command              | Notes                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/work/amendments`                  | own desk             | Also needs `WORK_WORKSPACE_READS_ENABLED`. Reads stay available when writes are off; `proposalsAvailable` reports the write switch. Lists up to 20 amendable (`ACCESS_PENDING`/`IN_PROGRESS`) engagements as member or Founder with every recorded version; each carries the current effective terms (the member's from the storage read, the Founder's from the same listing-creator query). |
| `POST /api/v1/work/amendments`                 | `proposeAmendment`   | Body is the storage input (`engagementId`, `changes`, `expiresAt`).                                                                                                                                                                                                                                                                                                                           |
| `POST /api/v1/work/amendments/{id}/response`   | `respondToAmendment` | Body `{decision:"ACCEPT",digest}` or `{decision:"DECLINE"}`.                                                                                                                                                                                                                                                                                                                                  |
| `POST /api/v1/work/amendments/{id}/withdrawal` | `withdrawAmendment`  | Empty body; the proposer only.                                                                                                                                                                                                                                                                                                                                                                |

Authority is the same-transaction `AmendmentHost` port. The Root host (`src/lib/work-amendment-host.ts`) answers `authorize`/`authorizeProposer` from the synthetic `RAID_WORK_OPERATOR_ACCOUNT_IDS` allowlist and ignores the Guild id: this is NOT Guild or production authority (as for `ClosureHost`), and storage still requires the proposer to be the listing's creator and not a member. **Consent** is the member's own request naming the exact proposal digest they read (`digest` in the body, bound inside the transaction to the stored digest; a different digest or none is `CONSENT_REQUIRED`). A decline needs no digest. **Funding** is simulated coverage, not a balance: a reward increase reserves `sim-amendment-reservation:{amendmentId}` only when every increased leg matches a funded policy in `WORK_REWARD_ASSETS_JSON` (one leg per asset), and the same coverage and reference are rechecked at consent; otherwise the Founder gets `FUNDING_NOT_VERIFIED` and nothing is written. Nothing is reserved against a real balance and no money moves; settlement, release and top-ups of an unaccepted reservation belong to the funding task.

Replies are strict-parsed and bound to the request: an amendment's digest must be the digest of its own terms, a proposal result must carry exactly the requested changes for the requested engagement, and a response or withdrawal must report the decision asked for on the amendment asked about. Replays return the recorded result even after the proposal has moved on or the switch is off. Error mapping: `AMENDMENT_UNAVAILABLE` (decided, withdrawn, expired) is `NO_LONGER_OPEN`; `AMENDMENT_EXISTS` and `ENGAGEMENT_STATE` (stale: the work moved on) are `REVISION_CHANGED`; `CONSENT_REQUIRED`, `FUNDING_REQUIRED` (as `FUNDING_NOT_VERIFIED`) and `WRITES_DISABLED` (as `NOT_AVAILABLE`) map as for the other work routes. Internal codes are never returned. Reads and commands have separate per-account throttles.

`tests/work-amendment-http.test.ts` (route contract), `tests/work-amendment-host.test.ts` (flag default off, allowlist authority, simulated coverage, exact-digest consent) and `tests/work-amendment-root-db.test.ts` (real PostgreSQL through the same handlers: the full propose→consent flow, an unfunded increase, non-participant / non-creator / wrong-actor / cross-engagement IDOR, flag off with replays, repeat decisions, a stale engagement, and engagement-lock-barrier races of consent against withdrawal, of two proposals, and of a double-sent consent) cover it. The standalone `examples/raid-terms` host consumes the same schema files through its symlinks. ## Workspace screens

`AmendmentPanel` (`src/components/work-amendments.tsx`, one import and one section in each of `MyRaidsWorkspace` and `WorkDesk`) loads the own desk after hydration through the portable `amendment-client` and sends only the person's explicit answer; the server stays the authority. A member sees, for a waiting proposal, exactly what changes (scope, criteria, reward before → after with the asset's own decimals, deadlines), "Your current terms stay in force until you agree", the answer-by time, and **Agree to this change** (sends the proposal's digest) or **Decline**. A Founder who is on the synthetic allowlist and created the listing sees a form prefilled with the current terms that sends only deliberate changes in exact base units, plus a proposal-valid-until time; while a proposal is waiting they see it and **Withdraw proposal** instead of a second form.

Honest states: a reward increase says the added reward is covered by simulated funding only and no money has moved, and an uncovered increase is told nothing was proposed (`FUNDING_NOT_VERIFIED`); with the write switch off the controls are disabled with a plain "currently unavailable" notice while reads still work; a stale or already-answered proposal (`NO_LONGER_OPEN`, `REVISION_CHANGED`) says nothing changed and offers Refresh; not permitted, not found and a lapsed Session use the shared wording. Unconfirmed network failures keep the same idempotency key for a retry. `tests/work-amendments-ui.test.ts` covers the markup states, change description and form building; `tests/work-workspace-consumer.test.ts` renders the consent card in the independent `examples/work-workspace` host with an injected transport and no dispatch during server rendering. A browser preview of the real screens remains the reviewer's check.
