# Persisted Guilds, Founder authority and scoped grants

## Purpose and status

T009 storage core under R01–R04/R10/R15/R16, I06/I07/I10/I13, AC07/AC73–75 and blueprint 06.1–06.4, 25.2, 28.1. It persists a Guild from an owner's private [draft](raid-guild-drafts.md), keeps immutable profile history, defines scoped role grants and exposes the Guild's current authority. It builds on the pure [profile policy](raid-guild-profiles.md) (`evaluateGuildProfilePermission`), which it calls with facts rebuilt inside the command transaction. It adds no HTTP route, UI, feature flag, token recognition, money, capacity or work effect. Project-control verification (T010 evidence review, O11/G10), ownership transfer, public updates, the directory (T015) and the wiring of the work boundary's `authorize` to these records are separate slices and remain NOT VERIFIED. Independent review, UAT and business sign-off remain NOT VERIFIED.

## Authority model

- **Founder** is the account that owned the draft at activation. It changes only through the consented ownership-transfer process below (a database guard rejects every other write) and implies **profile** and **work** management only.
- **Activation** (`activateGuild`) is performed by an approver account the host authorizes (`GuildActivationHost.authorizeActivation`). The module stores the approver and an opaque `activationRef` naming the host's evidence record. The module does not decide project control: the module itself refuses an approver who is the draft owner (whatever the host policy answers), so Founder control is always approved by someone other than the Founder, and a token balance, market metadata or X/admin allowlist never creates a Guild or Founder.
- **Grants** (`GuildRoleGrant`) have a `kind`: `PROFILE` (names the editable fields, `name` and/or `description`), `WORK`, `TREASURY` or `DISPUTE`. Only `PROFILE` grants carry fields; the others are whole-scope and cannot delegate. A grant is live only inside its `[validFrom, expiresAt)` window, evaluated on the database clock, and until revoked. Kinds never imply one another, and the Founder holds no treasury or dispute authority by role (blueprint 06.2). Grants are issued and revoked only through `grantGuildRole` / `revokeGuildRole` (below); the table guard allows only a one-time revocation and never an edit or delete. Rows inserted directly by a privileged writer (as tests do to place a window in the past) carry no receipt.
- **Holder eligibility** is never an input. Token holding grants no administration, treasury, dispute or code permission (AC07).
- **Cross-Guild writes** are denied: authority is looked up per Guild id, so a Founder or grantee of one Guild has nothing in another.

Grant rules (DEFAULT, not an owner decision): nobody grants themselves a role and the Founder is never a grantee (they already hold profile and work by role, and treasury/dispute authority is issued to other accounts only); only `PROFILE` grants carry fields and may delegate; a delegate passes on only fields they hold with delegation rights, without delegation of their own, with an explicit expiry no later than theirs, at most 10 live grants each; at most 200 live grants per Guild (`GRANT_LIMIT`); a past expiry is `INVALID_INPUT`; a suspended grantee is `ACCOUNT_RESTRICTED`. Grant and revoke lock the Guild row, so they serialize with profile edits: an edit sees a committed revocation or runs before it. Revoking a delegating grant also revokes each still-live grant that grantee passed on unless, for every field of it, they still hold another live delegating grant covering that field and lasting at least as long (expired rows grant nothing and are left as history). Whether treasury or dispute roles should need a separate issuing process is an OPEN policy question; this slice records only the structural separation.

Ownership change (DEFAULT process, not an owner decision): the Founder proposes, the recipient accepts with their own session, and the host's `authorizeOwnershipTransfer(tx, {guildId, fromAccountId, toAccountId})` must approve (the hook for a recorded re-verification of project control, O11/G10). The Founder changes only through that accepted transfer: the `Guild` guard rejects any other Founder write, an accepted transfer must be applied before the transaction ends, and a decided transfer is final. A direct writer cannot decide on a party's behalf: CHECKs bind the decider (the recipient for accept/decline, the proposer for withdraw) and the decision time to the proposal window, and a deferred trigger requires, at commit, the proposing Founder's `ProposeOwnershipTransfer` receipt and the deciding account's `RespondOwnershipTransfer` receipt (or, for a lapse recorded by a later proposal, that Founder's `ProposeOwnershipTransfer` receipt). A privileged writer who can also fabricate command receipts is outside this guard, as for the other Guild tables. A response to a lapsed proposal records it as `EXPIRED` instead of applying it. The former Founder keeps no role by default; grants issued earlier stay in force until revoked; the profile revision and history do not change. Responses and replays are for the two parties, judged by identity.

Public updates (DEFAULT, not an owner decision): an update is plain text (title ≤200, body ≤4000 characters, trimmed) stored and returned verbatim; consuming UIs must escape it. Its public projection is title, body, publication time and an opaque id: no author, Guild id, state or private configuration (the table has no column for a private roadmap). Drafting is delegated to profile authority, but publishing is the Founder's alone, so approval cannot be delegated; a withdrawn update leaves the public list. An author can withdraw their own draft only while they still hold live profile authority. Withdrawal is allowed while `allowNewWrites` is false (a takedown must not wait for the kill switch); drafting and publishing are not. Rows are never deleted, so drafts withdrawn before publication keep counting against their author (open drafts ≤50 per Guild; open plus withdrawn-unpublished ≤100 per author, then `UPDATE_LIMIT`). The managed view lists drafts and published updates, not withdrawn ones; a Founder can always find a published update by id in the public list. Content and authorship are immutable once written (database guard), publication needs the current Founder and the matching command receipts at commit, and nothing is deleted.

Errors (`GuildStorageError`): `INVALID_INPUT`, `UNAUTHENTICATED`, `ACCOUNT_RESTRICTED`, `FORBIDDEN`, `NOT_FOUND`, `WRITES_DISABLED`, `REVISION_CONFLICT`, `GUILD_EXISTS`, `SLUG_UNAVAILABLE`, `GRANT_LIMIT`, `TRANSFER_PENDING`, `UPDATE_LIMIT`, `STORAGE_CONTRACT`, `STORAGE_UNAVAILABLE`. Permission is judged before the caller's revision, so a stranger learns nothing about it.

## Public HTTP reads

`createGuildPublicHandlers(host)` (`src/guild-profiles/guild-public-http.ts`) is a framework-free Request/Response factory for two unauthenticated reads: `GET /api/v1/guilds/{slug}` (the approved public projection: `id`, `slug`, `name`, `description`, `primaryToken`) and `GET /api/v1/guilds/{slug}/updates?limit&before` (published updates as `{id, title, body, publishedAt}`, page ≤20, `nextCursor`). The host supplies `version:'v1'`, `requestId`, `available` (the feature flag), `rateLimit`, `guild` and `updates`; it owns SQL, the transaction and the throttle. Order of checks: method (405), flag (a closed flag answers `NOT_FOUND`, touching nothing), slug and strict query (unknown or repeated parameters, malformed `limit`/`before` → `INVALID_COMMAND`), throttle (429), read. Every host result is re-parsed with a strict schema and the profile's slug must equal the requested slug; a malformed, over-shared or wrong-Guild result becomes `SERVICE_UNAVAILABLE`, never a forwarded body. Responses are `Cache-Control: no-store` so a withdrawn update disappears at once; failures use fixed, sanitized envelopes. The Root host (`src/lib/guild-public-host.ts`, `guild-public-http.ts`, routes under `src/app/api/v1/guilds/[slug]`) reads in one command transaction, throttles at 120 requests per 60 seconds per client and is gated by `GUILD_PUBLIC_READS_ENABLED` (exact `true`, default off). No write, session, private field or directory listing is added; the public page below renders the same reads. A closed Guild's profile is still exposed once active; there is no unlisting yet (OPEN).

## Public Guild page

`/guilds/{slug}` (`src/app/guilds/[slug]/page.tsx`, with `loading.tsx` and `not-found.tsx`) is the server-rendered visitor view of the same projection (T015 slice, R08/R10, I06/I07, AC42). Its data layer `src/lib/guild-public-page.ts` calls the same host reads as the public API (`readGuildFromHost` → `readPublicGuild`, `readGuildUpdatesFromHost` → `listPublicGuildUpdates`), behind the same `GUILD_PUBLIC_READS_ENABLED` flag, and re-parses both results with the same strict schemas (slug must match). It renders only the name, slug, description, primary-token mint (when set) and published updates (title, body as escaped plain text, `publishedAt`), ten per page; the internal Guild id, Founder, authors, drafts and withdrawn updates never reach HTML, metadata or the hydration payload (the page is a server component and passes no data to client code). "Load more updates" is an ordinary link to `?before=<cursor>` (the public cursor) and "Back to latest updates" returns to the first page; other query parameters are ignored. Flag off, a malformed slug or cursor, or an unknown Guild all render the same not-found page (because the root `loading.tsx` streams, it is a soft not-found: HTTP 200 with `noindex`, as on other dynamic pages); other read failures reach the error boundary. `generateMetadata` uses only the name and description (generic "Guild not found" otherwise) and sets `noindex` while unlisting is OPEN. The route is `force-dynamic` with no data cache, so a withdrawn update is gone on the next request. Unlike the API, the page has no per-client throttle yet (follow-up). Not included: the Guild directory, homepage changes, management UI, holder or skill information. Tests: `tests/guild-public-page.test.ts` (flag/input refusals without a database; real-PG projection, empty/not-found, pagination and withdrawal), fixture `tests/helpers/guild-public-page-fixture.ts`.

## Management HTTP for public updates

`createGuildUpdatesHandlers(host)` (`src/guild-profiles/guild-updates-http.ts`) is the authenticated Request/Response transport for the update commands: `GET /api/v1/guild-updates?guildId=` (the caller's managed view plus `writesAvailable`), `POST /api/v1/guild-updates` (`{guildId,title,body}` → draft) and `POST /api/v1/guild-updates/{updateId}` (`{guildId,action:'PUBLISH'|'WITHDRAW'}`). The host supplies `actor` (its own cookie-derived session; an actor, account or role in the body is a strict-schema failure), `checkOrigin`, `rateLimit`, `list`, `draft`, `publish` and `withdraw`. POSTs check origin, then the actor, then the throttle, then the `Idempotency-Key` header and a bounded strict JSON body; GET authenticates and throttles but needs no origin. Authorization stays in storage (Founder or live `PROFILE` grantee drafts, Founder alone publishes, author-or-Founder withdraws); the transport only maps results: every host result is re-parsed strictly and bound to the request (update id, Guild id, resulting state, and the drafted title/text), a mismatch becomes `SERVICE_UNAVAILABLE`. Responses are `private, no-store` with `Vary: Cookie`; failures use fixed envelopes (`FORBIDDEN`, `NOT_FOUND`, `REVISION_CHANGED` for an update already moved, the new `GUILD_UPDATE_LIMIT_REACHED`, `NOT_AVAILABLE` for disabled writes, `IDEMPOTENCY_KEY_REUSED`, `RATE_LIMITED`). The Root host (`src/lib/guild-updates-host.ts`, `guild-updates-http.ts`, routes under `src/app/api/v1/guild-updates`) throttles commands at 30 per 60 seconds and reads at 120 per 60 seconds per account, in separate buckets so polling cannot block a publication or takedown. An idempotent replay may find the update already moved on and still succeeds (a replayed publish may show `WITHDRAWN`); only a fresh result must land in exactly the requested state. `GUILD_UPDATES_ENABLED` (exact `true`, default off) gates only new drafts and publications; own reads and withdrawal stay available so a takedown never waits for the flag. There is still no HTTP to activate a Guild, so no account can reach these routes as a Founder in production until that slice exists; no UI is added.

Publish and withdraw judge the caller's standing before taking any lock (publish needs Founder status; withdraw needs the Founder or a live `PROFILE` authority), so an account with no authority in a Guild cannot queue behind its row and gets the same `FORBIDDEN` for a missing Guild, a missing update and an existing update; standing is rechecked under the lock. Requests are throttled before the body is validated, as at the draft and work boundaries, so malformed requests spend budget. `runCommandTransaction` retries whole transactions on deadlock and serialization failures; only exhaustion (`RETRY_TRANSACTION`) or an unmapped storage failure reaches the client, as a generic retryable `SERVICE_UNAVAILABLE`. `writesAvailable` in a read and the `allowNewWrites` of the next command are read from the environment at different instants, so a flag flipped in between can show writes enabled and then answer `NOT_AVAILABLE`.

## Profile edit HTTP

`createGuildProfileHandlers(host)` (`src/guild-profiles/guild-profile-http.ts`) is the authenticated Request/Response transport for `editGuildProfile`: `GET /api/v1/guild-profile?guildId=` returns the caller's managed view (`guild`, the `authority` they hold, `writesAvailable`) and `POST /api/v1/guild-profile` takes the storage input `{guildId,expectedRevision,profile:{name?,description?}}` (strict; a slug, actor or role is a schema failure). The host supplies `actor` (its own cookie-derived session), `checkOrigin`, `rateLimit` (separate `READ`/`WRITE` scopes so polling cannot block an edit), `read` and `edit`. POSTs check origin, then the actor, then the throttle, then `Idempotency-Key` and a bounded strict JSON body; GET authenticates and throttles but needs no origin. Who may edit which field stays in storage (Founder, or a live `PROFILE` grantee for exactly the granted fields; permission is judged before the revision, so a stranger learns nothing). Every host result is re-parsed with a strict schema and must describe the request: same Guild, revision `expectedRevision + 1` and the requested fields; a replay returns the version its own command wrote, so fresh and replayed results match exactly. Responses are `private, no-store` with `Vary: Cookie`. The Next host (`src/lib/guild-profile-host.ts`, `src/lib/guild-profile-http.ts`, route `src/app/api/v1/guild-profile/route.ts`) is gated by `GUILD_PROFILE_EDITS_ENABLED` (exact `true`, default off, never in demo mode): it gates new edits only; replays and the caller's own reads stay available. Tests: `tests/guild-profile-http.test.ts` (boundary), `tests/guild-profile-http-db.test.ts` (real storage: Founder edit and replay, field-scoped grantee, stranger, switch off), `tests/guild-profile-host.test.ts` (flag).

Not yet available: HTTP to **activate** a Guild (who may approve activation is an owner decision, #305), so no account can become a Founder in production; the Guild management UI and the directory (T015).

## Host dependencies and transaction rules

Inject the existing `CommandReceiptTransaction` (PostgreSQL, READ COMMITTED) and an explicit `allowNewWrites` boolean; for activation also `authorizeActivation`. The host owns cookie authentication (the `GuildActor` is the account and the SHA-256 of the current session cookie), origin/rate/body limits for any future transport, whole-transaction retry and commit-before-response. Receipt-first ordering: the command receipt, then the actor's `User` (`FOR NO KEY UPDATE`), `Session` (`FOR SHARE`); activation then takes the draft owner's `User` row (`FOR SHARE`) before the draft row (`FOR UPDATE`), the same User-before-draft order as the draft writer, so a draft save and an activation by another approver cannot deadlock (two approvers who each own a draft the other activates still can; Postgres aborts one and the host's whole-transaction retry covers it); an edit takes the Guild row (`FOR UPDATE`). Authority is re-proven on the database clock after each row wait and on replay; an expired or revoked session, a suspended account or a revoked grant rolls the whole command back. A replayed edit re-proves that the actor's current authority covers the same fields and returns the Guild as that stored profile version recorded it, never later revisions; a replayed activation re-proves the approver.

## Storage, audit and recovery

Migrations `202610270008_guilds`, `202610270009_guild_ownership_transfer` and `202610270010_guild_updates` add `Guild` (stable unique slug, fixed Founder, activation record, one Guild per source draft), `GuildProfileVersion` (immutable, each tied to its command receipt) and `GuildRoleGrant`. Guards reject a changed id, slug, Founder, activation record or source draft; a revision without its own new version; deleting a Guild, version or grant; and any grant edit except one-time revocation. Every activation and edit records a private audit event (identifier-only payload `guildProfileVersionId`, no outbox). The shared event envelope gains the additive keys `guildProfileVersionId`, `guildRoleGrantId`, `guildOwnershipTransferId` and `guildUpdateId`. Backup/restore must keep Guilds, versions, grants, receipts and audit together; the migration is additive and has no destructive down step once used. Limitation: unlike the draft tables, the version table has no deferred "receipt and audit must exist" trigger, so a privileged direct writer could add a version without its audit row.
