# Persisted Guilds, Founder authority and scoped grants

## Purpose and status

T009 storage core under R01–R04/R10/R15/R16, I06/I07/I10/I13, AC07/AC73–75 and blueprint 06.1–06.4, 25.2, 28.1. It persists a Guild from an owner's private [draft](raid-guild-drafts.md), keeps immutable profile history, defines scoped role grants and exposes the Guild's current authority. It builds on the pure [profile policy](raid-guild-profiles.md) (`evaluateGuildProfilePermission`), which it calls with facts rebuilt inside the command transaction. It adds no HTTP route, UI, feature flag, token recognition, money, capacity or work effect. Project-control verification (T010 evidence review, O11/G10), ownership transfer, public updates, the directory (T015) and the wiring of the work boundary's `authorize` to these records are separate slices and remain NOT VERIFIED. Independent review, UAT and business sign-off remain NOT VERIFIED.

## Authority model

- **Founder** is the account that owned the draft at activation. It changes only through the consented ownership-transfer process below (a database guard rejects every other write) and implies **profile** and **work** management only.
- **Activation** (`activateGuild`) is performed by an approver account the host authorizes (`GuildActivationHost.authorizeActivation`). The module stores the approver and an opaque `activationRef` naming the host's evidence record. The module does not decide project control: the module itself refuses an approver who is the draft owner (whatever the host policy answers), so Founder control is always approved by someone other than the Founder, and a token balance, market metadata or X/admin allowlist never creates a Guild or Founder.
- **Grants** (`GuildRoleGrant`) have a `kind`: `PROFILE` (names the editable fields, `name` and/or `description`), `WORK`, `TREASURY` or `DISPUTE`. Only `PROFILE` grants carry fields; the others are whole-scope and cannot delegate. A grant is live only inside its `[validFrom, expiresAt)` window, evaluated on the database clock, and until revoked. Kinds never imply one another, and the Founder holds no treasury or dispute authority by role (blueprint 06.2). Grants are issued and revoked only through `grantGuildRole` / `revokeGuildRole` (below); the table guard allows only a one-time revocation and never an edit or delete. Rows inserted directly by a privileged writer (as tests do to place a window in the past) carry no receipt.
- **Holder eligibility** is never an input. Token holding grants no administration, treasury, dispute or code permission (AC07).
- **Cross-Guild writes** are denied: authority is looked up per Guild id, so a Founder or grantee of one Guild has nothing in another.

Grant rules (DEFAULT, not an owner decision): nobody grants themselves a role and the Founder is never a grantee (they already hold profile and work by role, and treasury/dispute authority is issued to other accounts only); only `PROFILE` grants carry fields and may delegate; a delegate passes on only fields they hold with delegation rights, without delegation of their own, with an expiry no later than their own (an explicit one when their cover is bounded; none is allowed only when their cover is unbounded), at most 10 live grants each; at most 200 live grants per Guild (`GRANT_LIMIT`); a past expiry is `INVALID_INPUT`; a suspended grantee is `ACCOUNT_RESTRICTED`. Grant and revoke judge standing first without a lock (a stranger gets `FORBIDDEN` for a missing Guild, a missing grant and an existing one alike, and cannot stall the Guild), recheck it under the lock, and so serialize with profile edits: an edit sees a committed revocation or runs before it. Revoking a delegating grant also revokes each still-live grant that grantee passed on unless, for every field of it, they still hold another live delegating grant covering that field and lasting at least as long (expired rows grant nothing and are left as history). Whether treasury or dispute roles should need a separate issuing process is an OPEN policy question; this slice records only the structural separation.

Ownership change (DEFAULT process, not an owner decision): the Founder proposes, the recipient accepts with their own session, and the host's `authorizeOwnershipTransfer(tx, {guildId, fromAccountId, toAccountId})` must approve (the hook for a recorded re-verification of project control, O11/G10). The Founder changes only through that accepted transfer: the `Guild` guard rejects any other Founder write, an accepted transfer must be applied before the transaction ends, and a decided transfer is final. A direct writer cannot decide on a party's behalf: CHECKs bind the decider (the recipient for accept/decline, the proposer for withdraw) and the decision time to the proposal window, and a deferred trigger requires, at commit, the proposing Founder's `ProposeOwnershipTransfer` receipt and the deciding account's `RespondOwnershipTransfer` receipt (or, for a lapse recorded by a later proposal, that Founder's `ProposeOwnershipTransfer` receipt). A privileged writer who can also fabricate command receipts is outside this guard, as for the other Guild tables. A response to a lapsed proposal (ACCEPT, DECLINE or WITHDRAW alike) records it as `EXPIRED` instead of applying it and returns `status: 'EXECUTED'` with `transfer.state: 'EXPIRED'`, `applied: false` and audit `guild.ownership_expired.v1`; this is not an error, so clients must check `transfer.state` (or `applied`), never only `status`, before treating ownership as moved. The decision is stamped once, so an acceptance whose host hook runs past `expiresAt` is recorded the same way. `authorizeOwnershipTransfer` runs while the Guild and transfer rows are locked: it must be fast and use only the given transaction (no network calls), or it blocks every write to that Guild and holds a connection. Treasury and dispute authority stay separate from the Founder role (blueprint 06.2): as `grantGuildRole` never makes the Founder a grantee, a proposal to an account holding an unrevoked, unexpired (including not yet started) `TREASURY` or `DISPUTE` grant in the Guild is `FORBIDDEN`, and acceptance re-checks it (a grant issued after the proposal also refuses with `FORBIDDEN`, leaving the proposal open; the recipient may surrender that grant and accept again). `PROFILE` and `WORK` grants held by the recipient are not revoked by a transfer. The former Founder keeps no Founder role, but keeps the issuer's revoke power over grants they issued (`revokeGuildRole` admits the issuing account), including the cascade over grants their delegates passed on; grants issued earlier stay in force until revoked; the profile revision and history do not change. Because the cascade keys on the issuing account, a new Founder who earlier held a delegating profile grant still loses, when that grant is revoked, the `PROFILE` grants they issued (also those issued later as Founder) that no other delegating grant of theirs covers. Ids in commands are canonicalized to lowercase, so an uppercase UUID is the same request as its lowercase form. Responses and replays are for the two parties, judged by identity.

Public updates (DEFAULT, not an owner decision): an update is plain text (title ≤200, body ≤4000 characters, trimmed) stored and returned verbatim; consuming UIs must escape it. Its public projection is title, body, publication time and an opaque id: no author, Guild id, state or private configuration (the table has no column for a private roadmap). Drafting is delegated to profile authority, but publishing is the Founder's alone, so approval cannot be delegated; a withdrawn update leaves the public list. An author can withdraw their own draft only while they still hold live profile authority. Withdrawal is allowed while `allowNewWrites` is false (a takedown must not wait for the kill switch); drafting and publishing are not. Rows are never deleted, so drafts withdrawn before publication keep counting against their author (open drafts ≤50 per Guild; open plus withdrawn-unpublished ≤100 per author, then `UPDATE_LIMIT`). The managed view lists drafts and published updates, not withdrawn ones, newest 100 in one query (no cursor yet); a Founder can always find a published update by id in the public list. A public `before` cursor must name an update of this Guild that was published (it may have been withdrawn since the page was served); an unknown, other-Guild or never-published id is `INVALID_INPUT` (HTTP `INVALID_COMMAND`), not an empty last page. Content and authorship are immutable once written (database guard), publication needs the current Founder and the matching command receipts at commit, and nothing is deleted.

Managed view redaction (#290): `readManagedGuild` returns the Founder's account id only to the Founder and to `PROFILE` managers. A caller whose authority is only `WORK`, `TREASURY` and/or `DISPUTE` gets the same strict `ManagedGuild` shape with `founderAccountId: null` (redacted, not unknown); the other fields are the public profile plus the edit `revision`, which identifies nobody. `activateGuild` and `editGuildProfile` results always carry the id, since only an approver, the Founder or a `PROFILE` manager receives them.

Grant view redaction (#318): `revokeGuildRole` (and its replay) returns `grantedByAccountId: null` (redacted, not unknown; the schema field is nullable) to a caller without `PROFILE` authority at that moment, e.g. a `TREASURY`/`DISPUTE`/`WORK` grantee surrendering their grant, because for those kinds the issuer is the Founder. The Founder and profile managers still receive the issuer. Pre-check ordering (#321): an involved caller (Founder, issuer or grantee) revoking an already revoked grant gets `GRANT_REVOKED` before the Guild row lock is taken; strangers still get `FORBIDDEN`. The check is on current authority, not on who issued the grant, so a user who surrenders their own `PROFILE` grant (they hold no `PROFILE` authority afterwards) and a former Founder who issued the grant (ownership has moved) are redacted too; this is deliberate over-redaction, safe because nothing is revealed that the caller no longer manages.

Profile edit ordering (#310): `editGuildProfile` first judges the caller's standing without a lock (the Founder or any live `PROFILE` grant), so an account with no profile authority gets `FORBIDDEN` for a missing and an existing Guild alike and never queues behind the Guild row; it then takes the Guild row lock and re-judges the exact field scope under it. One database clock reading taken with that row is used both for the policy's `now` and, as a bound parameter, for selecting live grants, so the two can never disagree about a grant created or expiring in between. Redelegation in `grantGuildRole` does the same (#314): the policy check, the per-field delegating-cover bounds that cap the new grant's expiry, and the per-issuer and per-Guild live-grant counts all bind the one instant read with the locked Guild row, and the command fails closed (`FORBIDDEN`) if any requested field shows no covering delegating grant at that instant, so cover that lapses between reads can never yield an unbounded grant. The HTTP edit result is re-parsed with a non-null `founderAccountId`; only a managed read may carry the redacted `null`.

Errors (`GuildStorageError`): `INVALID_INPUT`, `UNAUTHENTICATED`, `ACCOUNT_RESTRICTED`, `FORBIDDEN`, `NOT_FOUND`, `WRITES_DISABLED`, `REVISION_CONFLICT`, `GRANT_REVOKED` (a repeat revocation: the grant is already revoked, so treat it as done; revocation is never blocked by the new-writes switch), `GUILD_EXISTS`, `SLUG_UNAVAILABLE`, `GRANT_LIMIT`, `TRANSFER_PENDING`, `UPDATE_LIMIT`, `STORAGE_CONTRACT`, `STORAGE_UNAVAILABLE`. Permission is judged before the caller's revision, so a stranger learns nothing about it.

## Public HTTP reads

`createGuildPublicHandlers(host)` (`src/guild-profiles/guild-public-http.ts`) is a framework-free Request/Response factory for unauthenticated reads (the two below, plus the directory described after them): `GET /api/v1/guilds/{slug}` (the approved public projection: `id`, `slug`, `name`, `description`, `primaryToken`) and `GET /api/v1/guilds/{slug}/updates?limit&before` (published updates as `{id, title, body, publishedAt}`, page ≤20, `nextCursor`). The host supplies `version:'v1'`, `requestId`, `available` (the feature flag), `rateLimit`, `guild` and `updates`; it owns SQL, the transaction and the throttle. Order of checks: method (405), flag (a closed flag answers `NOT_FOUND`, touching nothing), slug and strict query (unknown or repeated parameters, malformed `limit`/`before` → `INVALID_COMMAND`), throttle (429), read. Every host result is re-parsed with a strict schema and the profile's slug must equal the requested slug; a malformed, over-shared or wrong-Guild result becomes `SERVICE_UNAVAILABLE`, never a forwarded body. Responses are `Cache-Control: no-store` so a withdrawn update disappears at once; failures use fixed, sanitized envelopes. The Root host (`src/lib/guild-public-host.ts`, `guild-public-http.ts`, routes under `src/app/api/v1/guilds/[slug]`) reads in one command transaction, throttles at 120 requests per 60 seconds per client and is gated by `GUILD_PUBLIC_READS_ENABLED` (exact `true`, default off). No write, session or private field is added by these two reads; the public page below renders the same reads. A closed Guild's profile is still exposed once active; there is no unlisting yet (OPEN). **Directory (T015):** `listPublicGuilds(tx, {limit?, after?})` returns active Guilds in slug order as `{guilds:[{slug,name,description}], nextCursor}` (page ≤20, default 20); `after` is the last slug already seen (keyset on the unique `Guild_slug_key` index, so no migration), `nextCursor` is the last slug of a full page and null at the end, and a slug that names no Guild just continues after it. Entries carry no Guild id, Founder, token or state; each row passes the same `projectPublicGuildProfile` approval as `readPublicGuild`, then a strict directory schema, so a malformed row is `STORAGE_CONTRACT`, never forwarded. `GET /api/v1/guilds?limit&after` is `handlers.GUILDS(request)` with the same method/flag/throttle/error mapping and `no-store` headers as the other reads; unknown or repeated parameters, a bad `limit` or a malformed slug cursor are `INVALID_COMMAND`. The host member `guilds(query)` is optional (adding it is backward compatible): a host that omits it answers that route as not found; when present it must be a function. The Root host wires `readGuildDirectoryFromHost` (`src/lib/guild-public-host.ts`) behind the same `GUILD_PUBLIC_READS_ENABLED` flag and `guild-public` budget.

## Public Guild page

`/guilds/{slug}` (`src/app/guilds/[slug]/page.tsx`, with `loading.tsx` and `not-found.tsx`) is the server-rendered visitor view of the same projection (T015 slice, R08/R10, I06/I07, AC42). Its data layer `src/lib/guild-public-page.ts` calls the same host reads as the public API (`readGuildFromHost` → `readPublicGuild`, `readGuildUpdatesFromHost` → `listPublicGuildUpdates`), behind the same `GUILD_PUBLIC_READS_ENABLED` flag, and re-parses both results with the same strict schemas (slug must match). It renders only the name, slug, description, primary-token mint (when set) and published updates (title, body as escaped plain text, `publishedAt`), ten per page; the internal Guild id, Founder, authors, drafts and withdrawn updates never reach HTML, metadata or the hydration payload (the page is a server component and passes no data to client code). "Load more updates" is an ordinary link to `?before=<cursor>` (the public cursor) and "Back to latest updates" returns to the first page; other query parameters are ignored. Flag off, a malformed slug or cursor, or an unknown Guild all render the same not-found page (because the root `loading.tsx` streams, it is a soft not-found: HTTP 200 with `noindex`, as on other dynamic pages); other read failures reach the error boundary. `generateMetadata` uses only the name and description (generic "Guild not found" otherwise) and sets `noindex` while unlisting is OPEN. The route is `force-dynamic` with no data cache, so a withdrawn update is gone on the next request. Like the API, the page is throttled at 120 requests per 60 seconds per client (same `publicRateLimit` scope `guild-public`, same `TRUSTED_IP_HEADER` client key and shared-bucket fallback, so page and API views share one budget). The throttle runs after the flag and slug checks and before any storage read, once per request (metadata and page share it); over the limit the page renders a "Too many requests" notice and generic `noindex` metadata, reads nothing and cannot set a 429 status because the response is already streaming (see the soft-404 note: Next.js fixes the status when `loading.tsx` first streams). A non-429 limiter failure reaches the error boundary. A true 404/429 status for this route is not feasible without broader change: the root `loading.tsx` wraps every route in Suspense, so any status decided after rendering starts is already 200; only moving that loading boundary out of this route (route-group restructure) or a Proxy slug check that reads storage would change it, both outside this slice. Not included: management UI, holder or skill information. Tests: `tests/guild-public-page-throttle.test.ts` (budget, key, no storage read when throttled), `tests/guild-public-page.test.ts` (flag/input refusals without a database; real-PG projection, empty/not-found, pagination and withdrawal), fixture `tests/helpers/guild-public-page-fixture.ts`. **Directory page and homepage entry (T015):** `/guilds` (`src/app/guilds/page.tsx`, `loading.tsx`) is the server-rendered Guild list from `loadGuildDirectory` (`src/lib/guild-public-page.ts`): twelve Guilds per page, each a link to `/guilds/{slug}` with the name, slug and a 200-character description excerpt (escaped plain text). "Load more Guilds" is an ordinary link to `?after=<slug>` (keyboard-reachable, no client code) and "Back to first Guilds" returns to the first page; a malformed or repeated `after` is the not-found page and other parameters are ignored. States: flag off renders a "not open yet" notice and reads nothing; over the shared 120/60 s `guild-public` budget renders "Too many requests" without a storage read; zero Guilds renders "No Guilds are listed yet"; `loading.tsx` is the accessible loading state; other read failures reach the error boundary. The page is `force-dynamic` and `noindex` like the Guild page (soft-status limits as documented above). The homepage (`src/app/page.tsx`) shows a "Browse Guilds" panel above the discovery hero, and `publicNavLinks()` adds "Guilds" to the desktop and mobile main navigation, both only while `GUILD_PUBLIC_READS_ENABLED` is exactly `true`. Only the Guild name, slug and description reach HTML; no new flag. Tests: `tests/guild-directory-db.test.ts` (real-PG projection, order, cursor, validation), `tests/guild-directory-http.test.ts`, `tests/guild-directory-page.test.ts` (states, links, throttle, strict re-parse), `tests/guild-directory-page-db.test.ts` (real-PG pages and API), `tests/home-guild-entry.test.ts`; consuming host: `examples/guild-storage` exercises `listPublicGuilds` and `GUILDS` with its own flag and storage.

## Management HTTP for public updates

`createGuildUpdatesHandlers(host)` (`src/guild-profiles/guild-updates-http.ts`) is the authenticated Request/Response transport for the update commands: `GET /api/v1/guild-updates?guildId=` (the caller's managed view plus `writesAvailable`), `POST /api/v1/guild-updates` (`{guildId,title,body}` → draft) and `POST /api/v1/guild-updates/{updateId}` (`{guildId,action:'PUBLISH'|'WITHDRAW'}`). The host supplies `actor` (its own cookie-derived session; an actor, account or role in the body is a strict-schema failure), `checkOrigin`, `rateLimit`, `list`, `draft`, `publish` and `withdraw`. POSTs check origin, then the actor, then the throttle, then the `Idempotency-Key` header and a bounded strict JSON body; GET authenticates and throttles but needs no origin. Authorization stays in storage (Founder or live `PROFILE` grantee drafts, Founder alone publishes, author-or-Founder withdraws); the transport only maps results: every host result is re-parsed strictly and bound to the request (update id, Guild id, resulting state, and the drafted title/text), a mismatch becomes `SERVICE_UNAVAILABLE`. Responses are `private, no-store` with `Vary: Cookie`; failures use fixed envelopes (`FORBIDDEN`, `NOT_FOUND`, `REVISION_CHANGED` for an update already moved, the new `GUILD_UPDATE_LIMIT_REACHED`, `NOT_AVAILABLE` for disabled writes, `IDEMPOTENCY_KEY_REUSED`, `RATE_LIMITED`). The Root host (`src/lib/guild-updates-host.ts`, `guild-updates-http.ts`, routes under `src/app/api/v1/guild-updates`) throttles commands at 30 per 60 seconds and reads at 120 per 60 seconds per account, in separate buckets so polling cannot block a publication or takedown. An idempotent replay may find the update already moved on and still succeeds (a replayed publish may show `WITHDRAWN`); only a fresh result must land in exactly the requested state. `GUILD_UPDATES_ENABLED` (exact `true`, default off) gates only new drafts and publications; own reads and withdrawal stay available so a takedown never waits for the flag. There is still no HTTP to activate a Guild, so no account can reach these routes as a Founder in production until that slice exists; no UI is added.

Publish and withdraw judge the caller's standing before taking any lock (publish needs Founder status; withdraw needs the Founder or a live `PROFILE` authority), so an account with no authority in a Guild cannot queue behind its row and gets the same `FORBIDDEN` for a missing Guild, a missing update and an existing update; standing is rechecked under the lock. Requests are throttled before the body is validated, as at the draft and work boundaries, so malformed requests spend budget. `runCommandTransaction` retries whole transactions on deadlock and serialization failures; only exhaustion (`RETRY_TRANSACTION`) or an unmapped storage failure reaches the client, as a generic retryable `SERVICE_UNAVAILABLE`. `writesAvailable` in a read and the `allowNewWrites` of the next command are read from the environment at different instants, so a flag flipped in between can show writes enabled and then answer `NOT_AVAILABLE`.

## Role grant and ownership transfer HTTP

`createGuildRolesHandlers(host)` (`src/guild-profiles/guild-roles-http.ts`) is the authenticated Request/Response transport for `grantGuildRole`, `revokeGuildRole`, `proposeOwnershipTransfer` and `respondOwnershipTransfer` (T009, #51). Routes: `POST /api/v1/guild-grants` (the grant input of the storage command), `POST /api/v1/guild-grants/{grantId}/revoke` (`{guildId}`), `POST /api/v1/guild-ownership-transfers` (`{guildId,toAccountId,expiresAt}`) and `POST /api/v1/guild-ownership-transfers/{transferId}` (`{guildId,decision:'ACCEPT'|'DECLINE'|'WITHDRAW'}`). Routes are flat and take the Guild id in the body like the other management routes (the `/guilds/{slug}` namespace stays public read-only). Every call checks origin, then the cookie-derived actor, then the per-account command throttle (30 per 60 seconds, bucket `guild-roles`; there are no reads on this transport), then the `Idempotency-Key` header and a bounded strict JSON body. An actor, issuer, session or role in the body is a strict-schema failure. Authorization is storage's alone: the Founder or a delegating `PROFILE` grantee grants within its own fields and expiry, the Founder, issuer or grantee revokes, the Founder proposes, the recipient accepts or declines and the proposing Founder withdraws; a stranger and a caller from another Guild get `FORBIDDEN`, and a grant or transfer id that is not in the named Guild is not found (nothing about other Guilds is revealed).

Every host result is re-parsed strictly and bound to the request: the grant must be for the requested Guild, grantee, kind, fields, delegation right and expiry, issued by the caller, and live when fresh; a revocation must show the requested grant revoked, fresh or replayed; a proposal must come from the caller to the requested recipient and expiry and be open when fresh; a response must be the requested decision, or the lapse that overtook it (`EXPIRED`, `applied: false`, still `status: 'EXECUTED'`: clients must read `transfer.state`), with `applied` true only for `ACCEPTED`. A mismatch is `SERVICE_UNAVAILABLE`. A replay never fails because the world moved on (a replayed grant may show `revokedAt`, a replayed proposal may show a decided state). The validated grant body is forwarded as sent because storage parses and normalizes it itself. `grantedByAccountId` is exactly what storage returns: the issuer for the Founder and profile managers, `null` for a surrendering `WORK`/`TREASURY`/`DISPUTE` grantee. Responses are `private, no-store` with `Vary: Cookie`; failures use fixed envelopes: `FORBIDDEN`, `NOT_FOUND`, `REVISION_CHANGED` (an already revoked grant or an already decided transfer; a repeated revocation with a fresh key is therefore a safe "done"), the new `GUILD_GRANT_LIMIT_REACHED` and `GUILD_TRANSFER_PENDING`, `NOT_AVAILABLE`, `IDEMPOTENCY_KEY_REUSED`, `RATE_LIMITED`, `INVALID_COMMAND`.

The Root host (`src/lib/guild-roles-host.ts`, `guild-roles-http.ts`, `guild-http-session.ts`, routes under `src/app/api/v1/guild-grants` and `guild-ownership-transfers`) gates new grants, proposals and responses on `GUILD_ROLE_MANAGEMENT_ENABLED` (exact `true`, default off, never in demo mode); revocation is never gated, so taking authority away stays possible in an incident. The Root ownership policy hook (`authorizeOwnershipTransfer`) answers **closed**: the recorded project-control re-verification it stands for (O11/G10, T010) does not exist, so no acceptance moves a Founder over HTTP in production; declining and withdrawing do not need it. There is no HTTP to activate a Guild (#305), so no account can reach these routes as a Founder in production, and no UI or read endpoint is added (the recipient of a proposal has no list yet). Open policy for the owner: a former Founder stays `grantedBy` on what it issued while Founder and can still revoke it after a transfer (also under the switch), including `TREASURY`/`DISPUTE` grants (#321 NOTE); this transport keeps that behavior.

## Profile edit HTTP

`createGuildProfileHandlers(host)` (`src/guild-profiles/guild-profile-http.ts`) is the authenticated Request/Response transport for `editGuildProfile`: `GET /api/v1/guild-profile?guildId=` returns the caller's managed view (`guild`, the `authority` they hold, `writesAvailable`) and `POST /api/v1/guild-profile` takes the storage input `{guildId,expectedRevision,profile:{name?,description?}}` (strict; a slug, actor or role is a schema failure). The host supplies `actor` (its own cookie-derived session), `checkOrigin`, `rateLimit` (separate `READ`/`WRITE` scopes so polling cannot block an edit), `read` and `edit`. POSTs check origin, then the actor, then the throttle, then `Idempotency-Key` and a bounded strict JSON body; GET authenticates and throttles but needs no origin. Who may edit which field stays in storage (Founder, or a live `PROFILE` grantee for exactly the granted fields; permission is judged before the revision, so a stranger learns nothing). Every host result is re-parsed with a strict schema and must describe the request: same Guild, revision `expectedRevision + 1` and the requested fields; a replay returns the version its own command wrote, so fresh and replayed results match exactly. Responses are `private, no-store` with `Vary: Cookie`. The Next host (`src/lib/guild-profile-host.ts`, `src/lib/guild-profile-http.ts`, route `src/app/api/v1/guild-profile/route.ts`) is gated by `GUILD_PROFILE_EDITS_ENABLED` (exact `true`, default off, never in demo mode): it gates new edits only; replays and the caller's own reads stay available. Tests: `tests/guild-profile-http.test.ts` (boundary), `tests/guild-profile-http-db.test.ts` (real storage: Founder edit and replay, field-scoped grantee, stranger, switch off), `tests/guild-profile-host.test.ts` (flag).

Not yet available: HTTP to **activate** a Guild (who may approve activation is an owner decision, #305), so no account can become a Founder in production; a UI for role grants, revocation and ownership transfer.

## Guild management UI

`/creator/guilds` lists the signed-in caller's own Guilds and `/creator/guilds/{slug}` manages one (T009, #51; R03, R04, I06, I07; AC07). Both are server-rendered, dynamic and `noindex`. The Root host reads with the session actor only (`src/lib/guild-manage-page.ts` → `listManagedGuildsState` → `listManagedGuilds`) and re-parses the result with the strict `ManagedGuildListSchema`; no new public API exists. The detail page finds the Guild by slug in that list, so a missing Guild, a malformed slug and a Guild the caller holds nothing in all render one identical "not found or you do not manage it" page (no existence oracle). Holders of only `WORK`, `TREASURY` or `DISPUTE` authority see a read-only summary of the authority they hold (Founder id redacted) and no editor; treasury and dispute stay separate from profile administration.

Profile managers get two portable client components (`src/components/guild-manage.tsx`, over the injected `GuildManageApi` transport and the pure `src/guild-profiles/guild-manage-client.ts`): `GuildProfileEditor` posts only the changed fields to `POST /api/v1/guild-profile` with the page's revision as `expectedRevision`, and `GuildUpdatesManager` drafts, publishes (Founder only) and withdraws through `/api/v1/guild-updates[/{updateId}]`. The runner keeps one idempotency key per unchanged intent: an unconfirmed outcome (network failure, 5xx, key reuse, a success that fails the strict re-parse) keeps the same key and says the change could not be confirmed, a temporary 401, 403 or 429 after such an attempt keeps it too, and a definite answer drops it; a result is accepted only if it is the command that was sent (same Guild and update, next revision, same text, expected state). Honest states: writes off (`GUILD_PROFILE_EDITS_ENABLED` / `GUILD_UPDATES_ENABLED`, both existing, default off) disable the fields and say so while saved content stays readable and withdrawal stays available; a stale revision (`REVISION_CHANGED`) offers "Reload saved details" that keeps the typed text; no authority, not signed in, empty list and update-limit are explicit messages that never show server text. The UI hides actions the server would refuse, but the server is the authority and re-judges every command. Update and Guild text is plain text, escaped by React.

Host dependencies: the page needs the Root session (`currentUser`, cookie hash) and the two host reads; an alternate host supplies its own `GuildManageApi` (any fetch-compatible transport to the same routes) and renders the components, as [the independent host](../examples/guild-storage/README.md) does with `manage-example.tsx`. Verified: real-PostgreSQL `tests/guild-managed-list-db.test.ts` (authority-filtered list, redaction, revoked/expired/future grants, no leak across Guilds), `tests/guild-manage-client.test.ts` (runner and response contracts), `tests/guild-manage-ui.test.ts` and `tests/guild-manage-page.test.ts` (render states, no oracle, escaping). NOT VERIFIED: live browser interaction, assistive-technology behaviour, independent review and UAT.

## Host dependencies and transaction rules

Inject the existing `CommandReceiptTransaction` (PostgreSQL, READ COMMITTED) and an explicit `allowNewWrites` boolean; for activation also `authorizeActivation`. The host owns cookie authentication (the `GuildActor` is the account and the SHA-256 of the current session cookie), origin/rate/body limits for any future transport, whole-transaction retry and commit-before-response. Receipt-first ordering: the command receipt, then the actor's `User` (`FOR NO KEY UPDATE`), `Session` (`FOR SHARE`); activation then takes the draft owner's `User` row (`FOR SHARE`) before the draft row (`FOR UPDATE`), the same User-before-draft order as the draft writer, so a draft save and an activation by another approver cannot deadlock (two approvers who each own a draft the other activates still can; Postgres aborts one and the host's whole-transaction retry covers it); an edit takes the Guild row (`FOR UPDATE`). Authority is re-proven on the database clock after each row wait and on replay; an expired or revoked session, a suspended account or a revoked grant rolls the whole command back. A replayed edit re-proves that the actor's current authority covers the same fields and returns the Guild as that stored profile version recorded it, never later revisions; a replayed activation re-proves the approver.

## Storage, audit and recovery

Migrations `202610270008_guilds`, `202610270009_guild_ownership_transfer`, `202610270010_guild_updates` and `202610290001_guild_fk_indexes` (additive indexes on `Guild.activatedByAccountId`, `GuildProfileVersion.actorAccountId` and `GuildRoleGrant.grantedByAccountId`) add `Guild` (stable unique slug, fixed Founder, activation record, one Guild per source draft), `GuildProfileVersion` (immutable, each tied to its command receipt) and `GuildRoleGrant`. Guards reject a changed id, slug, Founder, activation record or source draft; a revision without its own new version; deleting a Guild, version or grant; and any grant edit except one-time revocation. Every activation and edit records a private audit event (identifier-only payload `guildProfileVersionId`, no outbox). The shared event envelope gains the additive keys `guildProfileVersionId`, `guildRoleGrantId`, `guildOwnershipTransferId` and `guildUpdateId`. `202610290001_guild_fk_indexes` uses plain `CREATE INDEX` inside the migration transaction, which takes a `SHARE` lock (blocking writes) on `Guild`, `GuildProfileVersion` and `GuildRoleGrant` while it builds: harmless on new small tables, but a large existing environment should schedule it in a quiet window or build the indexes `CONCURRENTLY` outside a transaction first. Backup/restore must keep Guilds, versions, grants, receipts and audit together; the migration is additive and has no destructive down step once used. Limitation: unlike the draft tables, the version table has no deferred "receipt and audit must exist" trigger, so a privileged direct writer could add a version without its audit row.
