# Standalone Raids: funding and content CPA

Current product accepts existing Solana token Raids and independent project Raids. Creator chooses project type first. Token Raids rank before non-token Raids in public discovery. Token creation, trading, creator-fee rewards, and launchpad payouts show **Coming soon**.

## Non-token campaign contract

- Creator chooses impression target (at least 1,000), duration, campaign brief, and optional X campaign post links. A campaign post link is context; it does not count as a raider contribution.
- Operator sets `RAID_LAMPORTS_PER_1000_IMPRESSIONS`, `RAID_FUNDING_ADDRESS`, and mainnet `SOLANA_RPC_URL`. The rate is an explicit operator business decision. Before configuring it, drafts can be saved but cannot accept funding or launch.
- Quote is frozen in each draft: `ceil(target impressions × lamports per 1,000 / 1,000)`. Creator verifies a Solana wallet and sends exactly that amount to the platform funding wallet with memo `useRAID:<raidId>`. Server accepts a finalized mainnet transaction only when signer, source, destination, amount, memo, and Raid creation time match. Funding transaction signature is globally unique.
- Held SOL funds only validated participant results; no platform campaign fee is deducted in this pilot. No impression or income guarantee. Creator accepts these terms when drafting. Funding and payout wallet transfers need manual wallet signing; app never holds creator or platform private keys.
- Raider verifies X and wallet, joins before posting, and submits original or quote posts that contain the frozen official mention. Wrong author, duplicate content, reply/repost wrappers, out-of-window posts, and posts made before enrollment do not qualify. X `public_metrics.impression_count`, when available, supplies observed views. Missing view data stays unknown; it never becomes zero or an invented estimate.
- During active Raid, observed views of qualifying, unflagged participant posts count toward target. Reaching target ends Raid. Duration expiry ends Raid even when target is missed. Ending starts final X collection, refresh, versioned result publication, and two-hour dispute review. Ending a funded Raid early closes posting immediately, but posts already made keep being measured until the originally scheduled end and settlement uses those views. A creator cannot enroll in or be paid from their own Raid. SOL rewards below `SOL_MIN_PAYOUT_LAMPORTS` (default 890,880, the rent-exempt minimum) are refunded to the creator instead of paid. No single raider earns more than the author cap of the funded pool (`RAID_AUTHOR_CAP_BPS`, default 25%, frozen when funding is verified). Launchpad fee rewards are not capped. `X_TRACKING_V2_SETTLEMENT_ENABLED=true` is required for any allocation.
- Final allocation waits for complete X data, all qualified post views, no open disputes or flagged contributions, and approved frozen result. Earned pool is `deposit × min(observed eligible views, target) / target`. Each participant earns `earned pool × their eligible views / all eligible views`. Any unearned balance and rounding dust return to creator's verified funding wallet. Zero eligible views returns whole deposit. Allocations sum exactly to deposit.
- Admin panel lists exact wallet, amount, and memo `useRAID:pay:<allocationId>` for every reward/refund. Admin sends each transfer from platform funding wallet, then records finalized mainnet signature. Server verifies source, destination, amount, memo, signer, and unique signature before marking paid. Raider sees own allocation and receipt. No automated signing or settlement is enabled for this release.

## CPA measurement

Impression target is CPM-like: rate per 1,000 observed post views. “Cost per action” requires defined action. For content planning, action means **one reviewed qualifying original or quote post from an enrolled, verified author**. Calculator divides quoted budget by creator's expected post count to show _estimated content CPA_. CSV report divides funding earned by reviewed qualifying post count for _actual content CPA_. This does **not** measure customer acquisition, purchases, unique viewers, or X Ads conversions. Later conversion CPA would need consented conversion tracking and attribution, separate from current public-post tracking.

X Ads defines target CPA around conversions and charges engagement campaigns on engagement rather than impression alone: [Google Ads CPA definition](https://support.google.com/google-ads/answer/6396841), [X engagements campaign](https://business.x.com/en/help/campaign-setup/create-an-engagements-campaign). These are conceptual comparisons only; useRAID Raids are not X Ads purchases. Verify X API field availability, usage cost, storage/display permission, and rules for incentivized posts with X before accepting deposits. Provider missing `impression_count` prevents target completion and payout allocation rather than substituting likes or estimates.

## Deployment gates

Deploy web and worker against same PostgreSQL database; apply migrations first. Set `DEMO_MODE=false`, HTTPS `NEXT_PUBLIC_APP_URL`, X OAuth credentials, `X_BEARER_TOKEN`, official handle, Solana mainnet RPC, funding address, and operator-approved rate. Register exact HTTPS OAuth callback in X Developer Console. Configure initial admin X user ID; admin enables collection only after provider feasibility checks. Run `npm run tracking:audit`. Verify a real OAuth session, post lookup including `public_metrics.impression_count`, and one small mainnet deposit/payment before public funding. Keep `LIVE_COLLECTION_APPROVED=false` until those checks pass; pricing and non-token payment then remain unavailable. Monitor collection errors, X spend, pending allocation ledger, and refund queue.
