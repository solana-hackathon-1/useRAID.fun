# RAID development agent assignments

Every issue has a recommendation in the organization Project and its issue body. These are delivery recommendations, not proof that a model can complete the work. AI-led means the agent can implement a bounded slice subject to independent review. AI-assisted means shared preparation/automation with a human responsible for acceptance. Human-led means an owner must make the decision or authorize the gate.

## Authority and verification

This maps blueprint sections 00, 02, 07, 13, 16, 19, 28, 32–35, 39–40 and invariants I01–I13, R15/R16 and AC73–75 through each issue's existing detailed packet. The entities affected here are delivery issues, Project items and planning records; no runtime identity, account, wallet, escrow, permissions or product state changes. Repository ownership remains with the existing module and test files mapped in each packet. A development assistant gains no Raider registration, credentials, spending authority or release authority from a recommendation.

## Model and effort policy

Verified on 6 October 2026 against the [OpenAI model guidance](https://learn.chatgpt.com/docs/models), [Claude model catalogue](https://platform.claude.com/docs/en/models/overview) and [Claude effort documentation](https://platform.claude.com/docs/en/build-with-claude/effort). Codex names and supported settings were also checked against the local client catalogue. Availability depends on the account and client; Claude account access has not been tested. Per-issue choices are engineering judgments, not vendor benchmark claims or equivalent scores across vendors.

Use GPT-6 Luna at high for small repeatable work, GPT-6.1 Sol at high for normal implementation, and GPT-6 Astra at extra high (`xhigh`) for money, identity, authorization, concurrency or sensitive provider workflows. Claude alternatives are Sonnet 5.5 at medium/high and Opus 5.5 at extra high (`xhigh`) respectively. CLI Low corresponds to Light, and xhigh to Extra High, in Codex interfaces. Claude and Codex effort scales are independent. No automatic Max/Ultra recommendation: first increase scope clarity and evaluate failures. Haiku 4.5 has no effort selector and is not used in this issue matrix.

If the recommended model is unavailable, record the replacement and validate it against the same tests. Use an available Sol/Sonnet for normal tasks and an available Astra/Opus for sensitive tasks; reduced model capability never lowers acceptance criteria. Escalate repeated failures, unclear invariants, conflicting contracts or unexplained race outcomes to a stronger available model and human reviewer.

## Capacity and execution

Each task starts with one implementer and one independent reviewer. Decisions add a human owner; UAT adds a representative tester. Story points retain the existing relative estimates; they are not hours, token budgets, guaranteed throughput or product Raider capacity. Epics are coordination envelopes, so their points do not constitute an additional implementation estimate. Eight-point and larger slices must be decomposed for review. Parallel work is appropriate only when dependencies are satisfied and file/module ownership is isolated; these recommendations do not launch agents or reserve capacity. Re-estimate sprint capacity after observing the first week's completed, reviewed work.

Preserve all C01–C22 criteria, dependencies, TDD evidence, replaceable integration interfaces and reusable feature documentation. Human acceptance, security review and release authorization remain mandatory where the packet requires them. Never mark QA/UAT passed from a model recommendation, successful issue sync or issue closure.
