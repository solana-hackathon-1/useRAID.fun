# Shared contracts v1 — T002

[Canonical authority](../RAID_AGENT_BLUEPRINT.md) · [Acceptance-first plan](tasks/T002-plan.md) · [Reuse requirements](raid-module-reuse.md)

Purpose: one source of runtime-validated, framework-independent identity, Guild, accepted terms, engagement, instrument, amount, state and protocol contracts for M0 consumers. Public entry point is [`src/contracts/index.ts`](../src/contracts/index.ts). This additive module does not authenticate an account, authorize work, store agreements, reserve capacity, settle funds or issue provider calls. An accepted snapshot's references are identifiers, not proof of consent, destination ownership, asset verification or funding.

Direct requirements: R15/R16, I03/I06/I08/I13, AC74/75. The module preserves the shape of R01–R14 and documents I01/02/04/05/07/09/10/11/12 obligations; the owning feature tasks must prove their actual database/program/provider enforcement. No new feature is live-enabled.

## Dependencies and installation

```text
Web / worker / independent host
             ↓ explicit public import
       src/contracts/index.ts
             ↓
        Zod 4 + bs58 6
```

No Next.js, Prisma, application config, database singleton, provider SDK objects, cookies or environment variables are imported. TypeScript targets ES2022; Node 22.12+ is the declared host runtime. `bs58` validates the shape of a Solana address, not its deployment or authority. A configured cluster/genesis identity is supplied by the host. The host also supplies the actual program/storage amount maximum. No secrets or configuration environment names are needed by this module.

In this repository use `import { EngagementSchema, parseDisplayAmount } from '@/contracts'` (or a relative import in tools). The public barrel is the only consumer entry point. No package has been published. To reuse in an authorized project, copy `src/contracts` and declare Zod/bs58; retain the version and contract tests. Do not copy application data or credentials.

Asset policy revision changes preserve `assetKey`. Policy snapshots cannot establish spendable funds; financial funding/claim records stay distinct.

Parsed immutable terms include all roster/reward/policy elements. Duplicate participants, beneficiaries outside the roster, invalid UTC dates, absent finite deadlines and reversed deadline order fail; the final operational-closure and review deadlines may coincide. Policies and consent/destination references are opaque. A host must look them up and reject stale/unauthorized references before any mutation.

## State and transition ownership

The exported vocabularies adopt canonical sections 25.7, 16.9, 10.3 and 19's run lifecycle as v1 contract declarations. This freezes DTO spelling; it does not resolve OPEN custody, dispute authority, timing, access provider or budget policy. The table assigns mutations to the owner; the full command registry includes guard requirements. A future command must validate its precise before-state and the accepted feature policy, rather than treating every pair of states as allowed.

## API, retries and lock protocol

Default public JSON API version is `/api/v1`. UTC ISO timestamps end in Z; exact amounts are strings. Work edits use `expectedRevision` rather than a competing If-Match representation, and acceptance/amendment also uses `expectedTermsVersion`. Cursor pagination belongs to feature-specific list schemas. Existing legacy API paths/error strings remain unchanged; T089 owns v1 endpoint rollout and compatibility.

`createErrorEnvelope` returns `{ status, body: { error: { code, message, retryable, requestId } } }`. Missing authentication is 401; permission 403; hidden resource 404; stale terms/state/capacity/idempotency 409; invalid command/asset 422; rate limiting 429; service unavailable 503. `PAYMENT_STATUS_UNKNOWN` is deliberately not automatically retryable: reconciliation must precede another effect.

`planCapacityLocks` validates and produces: receipt → admission/offer → source → terms → operators → canonical participants. Within every group, deduplicate and sort IDs by JavaScript code-unit order; the host must use that same ordering on every acceptance/replacement/closure/recovery/handoff path, not locale or database collation. This is a deterministic plan, not a transactional lock implementation. Receipt keys must come from collision-safe encoding of actor + command kind + retry key. Admission/source IDs must include their table/type namespace when commands use more than one source kind. The caller must assemble ALL source/target IDs before acquiring the first lock.

Database transaction claims immutable request digest, rechecks current authorization/terms/eligibility/funding/vacancy, creates engagement before FK-backed reservations, snapshots consent and writes state/audit/receipt/outbox together. Same key + different payload conflicts. Serialization retries rerun the entire transaction with the same identity. Release matches both participant and engagement; same-engagement AI members share one operator reservation. No wallet/provider/model/finality waits under these locks. Those rules are contracts for T019/T020, not proven by the planner.

## Independent consuming host

[`examples/shared-contracts/host.ts`](../examples/shared-contracts/host.ts) declares all fixture inputs and imports only the barrel. Its `contracts` symlink points at the canonical source for repository use. The host's separate [`package.json`](../examples/shared-contracts/package.json) declares its three dependencies. It prints `simulation: true`, an exact reward string, active versus terminal capacity classification, and rejected private/source inputs. The genesis, token addresses, precision, consent, deadlines, policies and storage maximum are synthetic observations, never live approval.

From the repository: `cd examples/shared-contracts && npm start` uses the explicitly declared host and installed root runtime. For a completely separate host:

```sh
mkdir /tmp/raid-contracts-host
cp -R src/contracts /tmp/raid-contracts-host/contracts
cp examples/shared-contracts/host.ts examples/shared-contracts/package.json /tmp/raid-contracts-host/
cd /tmp/raid-contracts-host
npm install --ignore-scripts --no-audit --no-fund
npm start
```

The CI consuming-host test copies the module and host outside the application, supplies the declared installed dependency runtime and runs with no DATABASE_URL, provider credentials or RAID configuration. A separately installed host must also be executed locally for delivery evidence. In-memory DTO checks do not replace storage/provider verification.

## Compatibility, operations and gaps

Legacy `src/lib/states.ts` remains authority for existing campaign CHECK constraints; `src/lib/http.ts`, monetary arithmetic, auth, worker, migrations and accepted campaign snapshots remain unchanged. The new work listing is not the old social campaign `Raid.status`; no automatic enum/model mapping is valid. T003 must review the authorized deployed-obligation snapshot and compatibility plan before any backfill. No new database tables, foreign keys, production flags or routes are delivered here.

IDs and JSON field/state spelling are v1. Adding/changing a required field or permission/state meaning needs a reviewed next version and consumer tests; retain old accepted snapshots. Policy-version changes never change an underlying instrument key. No generic set-state, set-paid, grant-by-rank or arbitrary withdrawal API exists in this module. Validation rejection must be mapped to a fixed safe error by a host; do not log Zod input, policy bodies or private brief bytes.

The pure module creates no external effects, durable jobs or provider operations; timeout/cancellation, drain/switch, reconciliation, monitoring and backup/restore belong to each consuming feature. R15 adapter substitution is not claimed for any legacy provider. Keep original in-flight bindings/receipts during those future migrations; never route old claims to a new provider by updating defaults.

Implementation maintainer: Codex AG03/AG10; independent reviewer recorded in the task packet. OPEN O01–O19 and G01–G10 remain relevant gates for their actual dependent features, not barriers to DTO work. Permissions, real capacity races, ledger conservation, effective private access, live provider switches and UAT remain unverified for the new domain. Next bounded task is T003 migration/backfill/rollback planning; T004 supplies realistic fixtures, while T006/T019/T020/T029/T089 implement the named domain boundaries.
