# Finite closure preserving claims and newer capacity

T024 closes the work duty of an engagement exactly once, finitely and without deciding money. Acceptance closes immediately; an unresponsive worker, reviewer or setup closes after the accepted operational deadline. Closing releases that engagement's own participant capacity and nothing else, and the reward claim stays visible and unsettled. All funding is simulated. Root routes, notifications, dispute resolution, settlement, reopening, replacement and the start/binding task remain separate work.

## Contract and requirements

| Requirement                 | Implemented behavior / verification                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC20, blueprint §12.2/§13.5 | Review acceptance writes one immutable `EngagementClosure` (reason `ACCEPTED`), moves the engagement to `ACCEPTED` and deletes only its own `(engagementId, participantId)` commitments in the same transaction. `readOwnEngagementClosure` returns the member's closure and the accepted terms' reward claims with status `UNSETTLED`, even after a newer engagement starts.                              |
| AC21, blueprint §12.5/§17.5 | `closeOverdueEngagement` closes `ACCESS_PENDING`, `IN_PROGRESS`, `SUBMITTED` (including an unresolved dispute) and `REVISION_REQUESTED` work as `TERMINATED` once the database clock passes the accepted `operationalClosure`. The reason names the missing duty (`ACCESS_`, `SUBMISSION_`, `REVIEW_`, `REVISION_TIMEOUT`). No fault, refund or payout is decided; `financialResolution` is always `OPEN`. |
| AC23, I13                   | Release matches participant and engagement, the command carries the revision its scheduler observed, and an already-closed engagement is `ENGAGEMENT_STATE`. A participant-only cleanup that would take a newer engagement's reservation is refused by the deferred capacity guard.                                                                                                                        |
| R15/R16                     | Explicit `ClosureHost` (`allowNewWrites`, current operations `authorize`), strict version-one schemas, own-installed PostgreSQL consumer that reads its claim after acceptance and is refused a premature closure.                                                                                                                                                                                         |

Requirement mapping: T024 uses AG03/M2 and blueprint §§12.2, 12.5, 13.5, 16 (no money moves), 17.5, 24.6–24.7, 25–28. Full numbered task criteria, Root integration, UAT/business/operating/release approval remain NOT VERIFIED; the DEFAULT seven-day escalation window and incident routing are not implemented — the accepted, snapshotted `operationalClosure` is the single finite bound here. This bounded implementation does not close the issue.

## Public module interface

`closure-storage.ts` exports `closeOverdueEngagement(tx, WorkCommand, ClosureHost)` with strict input `{engagementId, expectedRevision}`, `readOwnEngagementClosure(tx, actor, engagementId)` and the shared in-transaction `closeEngagement` used by review acceptance. `ClosureHost.authorize(tx, actor, {engagementId, guildId})` must prove current operations authority in the same transaction; a missing or unauthorized engagement is one indistinguishable `FORBIDDEN`. The actor still needs a current canonical Session. Errors add `DEADLINE_NOT_REACHED`; stale revisions report `REVISION_CONFLICT`. Replays of the original receipt return the first closure even with writes off. Event `work.engagement_closed.v1` carries only the engagement ID.

## State, locking and database enforcement

Lock order is receipt → actor identity (SHARE) → Engagement row `FOR UPDATE` → closure insert, state update, commitment delete. Reviewer decisions and operations closures serialize on the same row, so a late acceptance and a timeout cannot both close. Migration `202610260005_work_closure` adds the immutable `EngagementClosure` (one per engagement, RESTRICT FKs, `closedByAccountId` classified in the identity fence), extends the lifecycle guard with `* → TERMINATED` from the four active states only, and adds a closure insert guard (reason must match the prior state; timeout needs the accepted deadline passed in database time; acceptance needs an ACCEPT review of the latest submission) plus deferred guards requiring a terminal state and its matching closure to commit together. The existing capacity guard already requires closed engagements to hold no commitments. Closed work cannot be reactivated: no transition leaves `ACCEPTED` or `TERMINATED`. Reopening or replacing needs new consent, funding and capacity under later tasks.

## Operation and verification

Monitor `DEADLINE_NOT_REACHED`, stale-revision and retry volumes and overdue engagements still holding commitments after `operationalClosure`; a scheduler must call the command with the revision it read. Backup and restore keep closures with engagements and capacity; destructive down migration is unsupported once used. `tests/work-closure-db.test.ts` verifies acceptance release with visible unsettled claims (including after a newer engagement and for a stranger), refusal before the deadline and for wrong actor/stale revision/writes off, finite closure of all four active states with unchanged accepted-terms digest and filled source, replay, a reviewer-versus-operations race with one outcome, delayed closure against a newer commitment, and direct-SQL bypass attempts. Test names and genuine RED/GREEN results belong in the PR; independent review disposition is recorded there separately from SELF-EVALUATED author checks.
