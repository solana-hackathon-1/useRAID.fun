# Finite closure preserving claims and newer capacity

T024 closes the work duty of an engagement exactly once, finitely and without deciding money. Acceptance closes immediately; an unresponsive worker, reviewer or setup closes after the accepted operational deadline. Closing releases that engagement's own participant capacity and nothing else, and the reward claim stays visible and unsettled. All funding is simulated. The Root composition (operator route, worker pass, My Raid wording) is below; notifications, dispute resolution, settlement, reopening, replacement and the start/binding task remain separate work.

## Contract and requirements

| Requirement                 | Implemented behavior / verification                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC20, blueprint §12.2/§13.5 | Review acceptance writes one immutable `EngagementClosure` (reason `ACCEPTED`), moves the engagement to `ACCEPTED` and deletes only its own `(engagementId, participantId)` commitments in the same transaction. `readOwnEngagementClosure` returns the member's closure and the accepted terms' reward claims with status `UNSETTLED`, even after a newer engagement starts.                              |
| AC21, blueprint §12.5/§17.5 | `closeOverdueEngagement` closes `ACCESS_PENDING`, `IN_PROGRESS`, `SUBMITTED` (including an unresolved dispute) and `REVISION_REQUESTED` work as `TERMINATED` once the database clock passes the accepted `operationalClosure`. The reason names the missing duty (`ACCESS_`, `SUBMISSION_`, `REVIEW_`, `REVISION_TIMEOUT`). No fault, refund or payout is decided; `financialResolution` is always `OPEN`. |
| AC23, I13                   | Release matches participant and engagement, the command carries the revision its scheduler observed, and an already-closed engagement is `ENGAGEMENT_STATE`. A participant-only cleanup that would take a newer engagement's reservation is refused by the deferred capacity guard.                                                                                                                        |
| R15/R16                     | Explicit `ClosureHost` (`allowNewWrites`, current operations `authorize`), strict version-one schemas, own-installed PostgreSQL consumer that reads its claim after acceptance and is refused a premature closure.                                                                                                                                                                                         |

## Public module interface

`closure-storage.ts` exports `closeOverdueEngagement(tx, WorkCommand, ClosureHost)` with strict input `{engagementId, expectedRevision}`, `readOwnEngagementClosure(tx, actor, engagementId)` `closeOverdueEngagementAsPrincipal(tx, {principal: 'work-closure', input, idempotencyKey, requestId}, ClosureHost)` for the scheduled worker (below), and the shared in-transaction `closeEngagement` used by review acceptance. `ClosureHost.authorize(tx, actor, {engagementId, guildId})` must prove current operations authority in the same transaction; a missing or unauthorized engagement is one indistinguishable `FORBIDDEN`. The actor still needs a current canonical Session. Errors add `DEADLINE_NOT_REACHED`; stale revisions report `REVISION_CONFLICT`. Replays of the original receipt return the first closure even with writes off. Event `work.engagement_closed.v1` carries only the engagement ID.

## State, locking and database enforcement

Lock order is receipt → actor identity (SHARE) → Engagement row `FOR UPDATE` → closure insert, state update, commitment delete. Reviewer decisions and operations closures serialize on the same row, so a late acceptance and a timeout cannot both close. Migration `202610260005_work_closure` adds the immutable `EngagementClosure` (one per engagement, RESTRICT FKs, `closedByAccountId` classified in the identity fence), extends the lifecycle guard with `* → TERMINATED` from the four active states only, and adds a closure insert guard (reason must match the prior state; timeout needs the accepted deadline passed in database time; acceptance needs an ACCEPT review of the latest submission) plus deferred guards requiring a terminal state and its matching closure to commit together. The existing capacity guard already requires closed engagements to hold no commitments. Closed work cannot be reactivated: no transition leaves `ACCEPTED` or `TERMINATED`. Reopening or replacing needs new consent, funding and capacity under later tasks.

## Operation and verification

Monitor `DEADLINE_NOT_REACHED`, stale-revision and retry volumes and overdue engagements still holding commitments after `operationalClosure`; a scheduler must call the command with the revision it read. Backup and restore keep closures with engagements and capacity; destructive down migration is unsupported once used. The closure insert guard always stamps `closedAt` with the database clock, so a restore or replication replay must load `EngagementClosure` rows with these triggers inactive (a default `pg_restore` loads data before it creates triggers; logical replication applies with `session_replication_role=replica`); replaying the rows through the guard would restamp every closure, and a later restore-aware guard would need a migration (#270). `tests/work-closure-db.test.ts` verifies acceptance release with visible unsettled claims (including after a newer engagement and for a stranger), refusal before the deadline and for wrong actor/stale revision/writes off, finite closure of all four active states with unchanged accepted-terms digest and filled source, replay, a reviewer-versus-operations race with one outcome, delayed closure against a newer commitment, and direct-SQL bypass attempts. Test names and genuine RED/GREEN results belong in the PR; independent review disposition is recorded there separately from SELF-EVALUATED author checks.

## Hardening (#241 residuals)

`202610270005_closure_guard_hardening` closes direct-writer gaps. A timeout closure now requires an operational deadline that exists and has passed (a missing one no longer passes); `EngagementClosure.closedAt` is always the database clock's; and the lifecycle guard requires, for every transition into `ACCEPTED` or `TERMINATED`, a closure whose reason names the state being left, so a same-transaction chain cannot borrow a closure meant for an earlier state. `closeOverdueEngagement` asks `host.authorize` before and again after the engagement lock on a fresh closure (two calls, the second in the same transaction as the write, so the read-back needs no third), and once on a replayed receipt before reading it back, so a closer who lost authority cannot read the closure back (#270). Acceptance already announces `work.engagement_closed.v1` (residual 3 was fixed earlier). Residual 6 (suspended or non-HUMAN members reading their own claim) is deliberately left: it is a restricted-claims access policy owned by the payout-recovery task, not a closure rule. Bare `toThrow()` assertions in `tests/work-closure-db.test.ts` now name the guard that must fire.

## Root composition (#66) — default off

`WORK_CLOSURE_ENABLED` (exact `true`, default `false`; `.env.example`, `workClosureEnabled()` in `src/lib/config.ts`) is the only write switch for both entries below; with it off the route answers `NOT_AVAILABLE` (503) for a new closure while still replaying an earlier receipt. Funds are simulated and no money moves.

| Entry                                                                                            | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/v1/work/engagements/{engagementId}/closure`                                           | Body `{"expectedRevision": n}` (strict), header `Idempotency-Key`, same-origin, rate limited (30/60 s), private no-store. Calls `closeOverdueEngagement` with the Root `ClosureHost` in one retried transaction and returns `{status, closure}` (`financialResolution` is always `OPEN`). Wrong actor and unknown engagement are the same `FORBIDDEN`; wrong state, stale revision and early deadline are `REVISION_CHANGED` (409).                                                                                                                                                                                                                                                                                                              |
| `closeOverdueBatch` (`src/work-loop/closure-pass.ts`) via `runWorkClosureWorker` in `schedule()` | Selects overdue active engagements (oldest deadline first) whose accepted `operationalClosure` has passed in database time, up to 25 closed or settled per pass (ceiling 100), stepping over failing rows to the next candidate (at most `maxFailures`, default 100), and closes each as the `work-closure` service principal in its own whole-transaction retry, with the revision it read and a deterministic key `closure:{id}:{revision}`. `ENGAGEMENT_STATE`, `REVISION_CONFLICT`, `DEADLINE_NOT_REACHED` and replays are `skipped`; anything else is `failed` and thrown after the pass so the worker logs it. A stored deadline that is not a readable timestamp is `failed` as `TERMS_INVALID` without aborting selection of the others. |

Manual closes: authority is the existing synthetic operator allowlist `RAID_WORK_OPERATOR_ACCOUNT_IDS` (Guild id ignored), and the caller needs a current canonical Session. It is not Guild or production authority; wiring `hasGuildAuthority` is a separate, owner-confirmed change.

Worker closes act as the named service principal `work-closure` (implemented, [DEC-2026-11-14-08](../RAID_AGENT_BLUEPRINT.md#0223-owner-delegated-defaults--14-november-2026), extending [DEC-2026-11-13-06](../RAID_AGENT_BLUEPRINT.md#0222-owner-delegated-decisions--13-november-2026) b; #352 item 5). It is not a `User` row, so it can hold no Session, wallet or X link, Guild grant, participant capacity or operator-allowlist membership, and it has no credential in the database or environment. Migration `202611140001_work_closure_service_principal` makes `EngagementClosure.closedByAccountId` nullable, adds `closedByPrincipal`, and adds the CHECKs `EngagementClosure_closer_check` (exactly one of the two is set) and `EngagementClosure_principal_check` (the only principal is `work-closure` and it cannot record `ACCEPTED`), plus `User_service_principal_check` so no account can ever carry that name. Past closures keep their recorded human actor. `closeOverdueEngagementAsPrincipal` is the only command the principal can present: it runs the same flow as the operator command (switch, `host.authorize`, revision, database-clock deadline, release of the engagement's own commitments, receipt under actor `work-closure`) without proving a Session or taking identity locks, because there is no identity to lock. Only the worker composition calls it (no HTTP route does); the storage command hands the host a human only as `{accountId, sessionHash}` (extra keys dropped) and the Root host tests `accountId` first, so an actor that also carries a `principal` key is still checked against the allowlist, and it authorizes the principal only by that field, never by an account id or the allowlist, and the command refuses any other principal name (`UNAUTHENTICATED`). Manual closes still need a human operator session and record the account. `WORK_CLOSURE_WORKER_ACCOUNT_ID` is retired: the worker needs only `WORK_CLOSURE_ENABLED`, the setting is ignored, and configuration validation warns (`RETIRED_SETTING`, name only) while it is still set. With no worker Session there is no missing-session outage to alarm on, so the former `UNAUTHENTICATED` once-per-outage handling is removed; a pass that throws is logged every tick. Candidate selection evaluates `raid_effective_terms` once per active engagement (migration `202611050003_closure_candidate_index` adds partial indexes on active engagements and accepted amendments with plain `CREATE INDEX`, which blocks writes to those tables while it builds; the deadline itself is JSON text cast in `raid_try_timestamptz`, so it cannot be indexed without a denormalized column).

My Raid's engagement card shows, for a closed Raid, the closure reason, `Financial resolution: open — no payout, refund or fault has been decided`, `Capacity released.` only when the server reports `capacityHeld: false`, and each claim as unsettled simulated funds.

`tests/work-closure-http.test.ts` (route contract and error mapping), `tests/work-closure-host.test.ts` (flag default off, allowlist authority, principal authority, no pass without the flag, retired worker-account setting ignored) and `tests/work-closure-principal-db.test.ts` (real PostgreSQL: a worker close records the principal with no User or Session, a human close records the account, the principal cannot authenticate, close early, close with writes off or a denying host, or record an acceptance, CHECKs refuse both or neither closers, the account name is refused) and `tests/work-closure-root-db.test.ts` (real PostgreSQL: bounded batch, release exactly once, a reviewer accepting between read and close, a newer commitment preserved, two workers racing, a submission racing the worker, denying-host/writes-off worker, operator command replay/wrong actor/stale revision/flag off) cover it; Root UAT and any browser preview remain NOT VERIFIED.

The effective terms are read in a statement of their own after the engagement row lock (#352): an accepted amendment takes the lock but writes no Engagement row, so terms read inside the locking statement came from its pre-wait snapshot and a pass racing a deadline-extending amendment would fail on the closure trigger instead of answering `DEADLINE_NOT_REACHED`. Candidate starvation is mitigated twice: failing rows are stepped over within the pass (at most `maxFailures`), and a failure is also recorded durably per engagement (migration `202611130005_work_closure_backoff`, table `EngagementClosureBackoff`: consecutive failures, last failure code, `nextAttemptAt` and `alertedAt`, all by the database clock). Candidate selection skips an engagement until its `nextAttemptAt`; the delay is 60 s doubling per consecutive failure up to 3600 s (DEC-2026-11-13-06 a, provisional). A closure deletes the record in the same transaction, and every pass first removes records of engagements no longer active; benign skips (`ENGAGEMENT_STATE`, `REVISION_CONFLICT`, `DEADLINE_NOT_REACHED`) are not failures, and the systemic refusals `FORBIDDEN` and `WRITES_DISABLED` (wrong operator or switch for every engagement) are reported as `failed` but never recorded, so they neither back off every engagement for an hour nor raise one stuck alert each; the worker's single summary line (codes only) is their log line (#460). The upsert only advances a record whose `nextAttemptAt` is due, so two workers failing the same engagement concurrently count one failure. At the 10th consecutive failure the pass returns the engagement in `stuck` exactly once and logs one `work-closure-stuck` line through the `log` port right after the stuck flag commits (engagement id, failure code, count; no error text), so a pass that fails afterwards cannot lose it; a failure that cannot be recorded logs a value-free `work-closure-backoff-unrecorded` line (id and code only); retrying continues at the cap. Worker health reports `commitments.backingOff` and `commitments.stuck` and adds the reason `closure-stuck` while the closure worker is on and any stuck record remains. Recording a failure is best effort and never closes work or releases capacity. With the switch off, a caller without closure authority (or for a missing engagement) now gets `FORBIDDEN`, not `WRITES_DISABLED`; only an authorized caller learns the switch is off (#352 item 7). Worker closes record the `work-closure` principal, not an operator account (#352 item 5, above).
