# Public Raid feed

The public feed (`/raids`, `GET /api/v1/work/feed`) lets any visitor see live, funded, open work as safe cards, with structured filters and honest ordering. It is read only: it takes no actor, grants no permission and decides nothing about the viewer's eligibility. It runs on simulated funding behind a default-off flag.

## Raid detail

`/raids/work/{listingId}` and `GET /api/v1/work/feed/{listingId}` show the full public brief of one live Raid (blueprint §10.1 `PUBLIC`, §23.2): outcome, deliverables, acceptance criteria, exclusions, dependencies, skills and tools policy, all five deadlines, review evidence and revision rounds, and the rights, portfolio, withdrawal, termination, dispute and finality policies, plus the exact reward legs. It omits the reviewer's account, funding references and creator. A missing, unlisted, filled, expired or non-public listing is one `NOT_FOUND`; a malformed id is `422`. For an `APPLICATION` Raid the page offers **Apply to this Raid** to a signed-in person while `WORK_WORKSPACE_READS_ENABLED` and `WORK_APPLICATIONS_ENABLED` are on; otherwise it says to sign in or that applications are not open yet. An `INSTANT` Raid offers **Accept this Raid** to a signed-in person while `WORK_WORKSPACE_READS_ENABLED` and `WORK_ACCEPTANCE_ENABLED` (with `WORK_ACCEPTANCE_TAXONOMY_ID`) are on; an `APPLICATION` Raid offers it only when the viewer holds their own pending, unexpired offer for these exact terms and an open slot, in place of the apply form. Accepting first needs the person to tick that they have read the terms, then the browser records consent to the brief's `termsDigest` (`POST /api/v1/work/consents`) and accepts (`POST /api/v1/work/engagements`, with `offerId` for an offer), one idempotency key per step. The page shows no eligibility state: the server rechecks the session, skills, capacity, funding and offer when the person acts. No state claims eligibility, and the brief lists the open slot ids (`openSlotIds`, opaque, never a permission) and the `termsDigest` of the exact terms shown (public data; a brief whose stored digest does not match its terms is not shown).

### Applying

`POST /api/v1/work/applications` (the existing protected workspace boundary: origin check, authentication, rate limit, `Idempotency-Key`, bounded strict JSON `{slotId, termsVersionId, evidenceRefs}`) runs the existing `submitApplication` command with the host's explicit application limit (`WORK_APPLICATION_LIMIT`, default five); the response must match the requested slot and terms version. For a signed-in viewer the brief reads their own My Raid data: a submitted application for these terms replaces the form with "You already applied", and applicants are spread over the open slots by a stable per-person choice (not all on the lowest-numbered slot). A changed input never reuses a request key. The sign-in link has no return path yet (the sign-in flow does not carry one). The browser action is nonbinding: it sends no evidence yet (selecting evidence is later work), keeps one request key across a retryable failure so a retry cannot create a second application, drops it after a definite answer, and links to My Raid. Withdrawing stays in My Raid; the Founder's offer path is unchanged. The legacy campaign page keeps `/raids/{id}`; the new brief lives under `/raids/work/` so neither route changes.

## Guild link and "Eligible for me" (T097)

**Guild name.** A card and brief show the Guild's public name linking to `/guilds/{slug}` instead of an internal id. The host (`work-feed-host`) adds `guild: {slug, name}` through `readPublicGuildLabels` — the same approved projection as `GET /api/v1/guilds/{slug}` — and only while `GUILD_PUBLIC_READS_ENABLED` is on. A Guild without an active public page, or public Guild reads being off, leaves the card exactly as before: no link, the neutral label "Posted by a Guild" and no id on the page. The strict card schema allows only `slug` and `name` there (no id, founder, description or token). The public `GET /api/v1/work/feed` therefore also carries those two fields when they are public; it never carries any viewer data.

**Eligible for me.** `WORK_FEED_ELIGIBILITY_ENABLED` (exact `true`, default off, closed until `WORK_ACCEPTANCE_TAXONOMY_ID` is set; it also needs `WORK_FEED_READS_ENABLED`) adds, on the server-rendered `/raids` page only, a per-card label and an **Eligible for me** checkbox (`?eligible=1`) for a signed-in person. `createViewerEvaluator` reads the person's own current assessment facts once at database time and evaluates each Raid with the same `buildSkillRequirement` and `explainSkillEligibility` rules acceptance uses: `MET` → _Eligible for me_, `UNMET` (rank too low, missing skill, revoked, reassessment due, other assessment policy) → _Not eligible yet_, `UNKNOWN` (and modes skills cannot decide) → _Eligibility unknown_. Labels are words plus a symbol, never colour alone. The filter runs before paging so a cursor never lands on a page of hidden Raids; the API query, the cursor and organic ordering are unchanged, and there is no Sponsored placement or paid boost in this feed. A signed-out visitor sees a sign-in prompt and the filter is ignored; if the check fails the plain feed is shown with a status message. It is informational only: it grants nothing, takes no lock and reserves no place. Acceptance reads and authorizes its own facts again under its locks when the person acts, so a label that has gone stale can never admit anyone.

## Host contract

`WORK_FEED_READS_ENABLED` is an exact-string `true` flag and defaults off; while off the page and API answer as if they did not exist (404) and `workEntryLinks()` advertises nothing. When on, the main navigation (desktop and mobile, for every visitor) lists **Live Raids**.

`GET /api/v1/work/feed` accepts only `category, skillId, difficulty, participantKind, execution, admission, assetKey, closesBefore, sort, limit, cursor`. Unknown or repeated parameters, a non-integer `limit` (1–50, default 20), an over-long value or `sort=reward` without `assetKey` are `422 INVALID_COMMAND`. Responses are re-parsed with the strict `FeedPageSchema` (a host result that does not match is `503`, never forwarded), are `Cache-Control: no-store` and carry `X-Content-Type-Options: nosniff`. The shared host limits requests per client address (120 per minute, with a shared fallback bucket when no trusted proxy header is configured). No session, cookie or origin check is involved because nothing is written.

`cursor` is opaque and bound to its ordering and asset; a cursor from another ordering or a tampered one is `INVALID_INPUT`. Paging is stable within a 500-listing window of the newest live work; the window is a deliberate bound, not a full scan. Deeper search, full-text search and relevance ranking are later work.

## Verification

`tests/work-feed-db.test.ts` (real PostgreSQL: visibility, funded/open/expired/filled exclusion, no private fields, every filter, three orderings, asset-scoped reward order, cursor paging and tampering), `-http` (strict parsing, headers, flag, throttling, contract drift, safe errors), `-page` (typed query, date handling, hidden failures), `-ui` (cards, escaping, GET form, asset labels, honest funding and eligibility text), `work-feed-viewer-ui` / `-page` / `-db` (Guild link and no-id fallback, Eligible for me labels, filter, signed-out/unavailable states, and real-PostgreSQL facts including a revoked assessment on the next read) and `work-entry-links`. The example host exercises the same read model. A development preview rendered four seeded Raids on desktop and mobile with no horizontal scroll and a working asset-plus-reward-order filter.
