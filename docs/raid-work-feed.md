# Public Raid feed

The public feed (`/raids`, `GET /api/v1/work/feed`) lets any visitor see live, funded, open work as safe cards, with structured filters and honest ordering. It is read only: it takes no actor, grants no permission and decides nothing about the viewer's eligibility. It runs on simulated funding behind a default-off flag.

## Contract and requirements

| Requirement                 | Behavior / verification                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R08, blueprint §18.1, §23.2 | A listing appears only while it is `OPEN`, its current terms are `PUBLIC`, its commitment deadline has not passed (database clock) and at least one current-version slot is `AVAILABLE` with a simulated funding reference. Filled, closed, edited-to-draft, expired and non-public work is absent. A corrupt stored version is skipped, never exposed, and never takes the feed down.                    |
| I06, R11, §10.1             | Cards carry only title, public summary, Guild id, category, rank, skills, participant kinds, format, admission, exact reward legs, commitment and submission deadlines, open-slot count and a funding label. No reviewer, outcome, deliverables, policies, funding reference, creator or private annex. Tests assert the serialized page omits them. Non-public visibility is also filtered by the query. |
| I03, §18.2                  | Rewards keep their full asset identity (`assetKey`, asset id, verified decimals, base-unit string). `sort=reward` requires one `assetKey`; amounts in different assets are never ranked against each other and the page says so (`rewardComparable`). No cross-asset valuation is invented.                                                                                                               |
| §18.1 filters, §23.4        | Category, skill, rank, participant kind, format (solo/party), admission, reward asset and apply-before. There is no "Eligible for me" filter: the server does not evaluate it here, and the page says eligibility is checked when you apply. Nothing in the feed grants access or an offer.                                                                                                               |
| §18.2 ordering              | Newest (default), soonest deadline, or largest reward within one asset. Funded and open work only. Organic ordering is separate from any future Sponsored inventory, which this slice does not add.                                                                                                                                                                                                       |

## Host contract

`WORK_FEED_READS_ENABLED` is an exact-string `true` flag and defaults off; while off the page and API answer as if they did not exist (404) and `workEntryLinks()` advertises nothing. When on, the main navigation (desktop and mobile, for every visitor) lists **Live Raids**.

`GET /api/v1/work/feed` accepts only `category, skillId, difficulty, participantKind, execution, admission, assetKey, closesBefore, sort, limit, cursor`. Unknown or repeated parameters, a non-integer `limit` (1–50, default 20), an over-long value or `sort=reward` without `assetKey` are `422 INVALID_COMMAND`. Responses are re-parsed with the strict `FeedPageSchema` (a host result that does not match is `503`, never forwarded), are `Cache-Control: no-store` and carry `X-Content-Type-Options: nosniff`. The shared host limits requests per client address (120 per minute, with a shared fallback bucket when no trusted proxy header is configured). No session, cookie or origin check is involved because nothing is written.

`cursor` is opaque and bound to its ordering and asset; a cursor from another ordering or a tampered one is `INVALID_INPUT`. Paging is stable within a 500-listing window of the newest live work; the window is a deliberate bound, not a full scan. Deeper search, full-text search and relevance ranking are later work.

## Verification

`tests/work-feed-db.test.ts` (real PostgreSQL: visibility, funded/open/expired/filled exclusion, no private fields, every filter, three orderings, asset-scoped reward order, cursor paging and tampering), `-http` (strict parsing, headers, flag, throttling, contract drift, safe errors), `-page` (typed query, date handling, hidden failures), `-ui` (cards, escaping, GET form, asset labels, honest funding and eligibility text) and `work-entry-links`. The example host exercises the same read model. A development preview rendered four seeded Raids on desktop and mobile with no horizontal scroll and a working asset-plus-reward-order filter.
