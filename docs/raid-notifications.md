# Safe lifecycle notifications and preferences

T042 tells the people involved in a Raid what changed, without ever putting the work's content in the message. A system dispatcher turns work events from the outbox into in-app notifications; a second pass reminds people of approaching deadlines. Messages are fixed text with an in-product path, never a title, scope, criterion, reviewer reason, artifact or link with a token. People can opt in to optional promotional notices; notices about their own work are not preferences. Only in-app notifications exist: no email, social or push provider is configured, and payment, dispute and access-readiness notices wait for those events to exist. All of it is behind default-off flags.

## Host contract

Flags are exact-string `true` and default off: `NOTIFICATIONS_READS_ENABLED` (page, list, mark read, preferences) and `NOTIFICATIONS_DISPATCH_ENABLED` (the worker's `notifications` step each minute: up to 100 outbox events and up to 100 reminders within 24 hours). HTTP (`/api/v1/notifications`, `private, no-store`): `GET` (own list, unread count, preferences), `POST {id}/read`, `POST preferences {promotional}`; origin, session and rate limit are checked before writes, queries and foreign methods are refused and every response is re-parsed. The page `/notifications` shows readable server-rendered state without scripts, marks as read and toggles the preference immediately, undoing it with a message if the server did not keep it.

## Data and database enforcement

Migration `202610260008_notifications` adds `Notification` (append-only apart from its first read, a closed list of kinds, the payload CHECK, a unique dedupe key, RESTRICT FK to `User`), `NotificationPreference` and `NotificationDispatch` (the processed marker). Backup and restore keep them with their events; destructive down migration is unsupported once used. Lock order for the member and reviewer reads is the existing current-Session proof only; the dispatcher takes no identity locks.

Migration `202610260009_notification_safety` adds a persistent, immutable `NotificationDispatchInitialization` singleton, identifier/deadline value checks and `readAt >= createdAt`. Invalid existing notification rows cause migration failure for operator reconciliation; the migration never rewrites historical facts. Existing dispatch markers establish that dispatch was already active, so the migration initializes the singleton without suppressing its outstanding backlog.

When no initialization exists, the first enabled event pass atomically creates the singleton and marks all work outbox events visible to its initialization snapshot as handled, without sending historical notices. The unique singleton serializes concurrent initializers; after initialization, workers retain disjoint `SKIP LOCKED` batches. No timestamp watermark is used: an older transaction committing after that snapshot remains eligible. Later disable/enable cycles do not reseed or discard pending work. Preserve the singleton, dispatch markers and notifications together during backup/restore. A previously active installation with no surviving dispatch markers needs operator reconciliation before enablement; absence of evidence cannot prove whether an old dispatcher ran.

Event payloads must contain a canonical UUID string before any recipient UUID cast; malformed or unsupported events still receive their handled marker and cannot jam later batches. The reusable mark-read function independently rejects malformed UUID input with `INVALID_INPUT`. Genuine database failures remain errors and roll back their transaction. The worker runs events and reminders in separate transactions, attempts both, waits for both outcomes and reports a failure if either fails. A failing reminder cannot undo committed event notices, and the next pass safely retries through the existing dedupe keys.

Follow-up dispositions from #248: retain notification rows for suspended recipients (reads stay restricted), the 50-row list cap, generic “closed” wording for terminal work and the repository's existing TRUNCATE policy. Pagination and a dispatch-query/index redesign remain follow-ups pending measured need; no unsafe watermark is introduced to avoid rescanning.

## Verification

`tests/notifications-db.test.ts` (real PostgreSQL: lifecycle recipients, repeated/racing/lost-marker jobs, late commit, privacy scan, deadline reminder windows, passed deadlines and amended versions, read/idempotency/isolation, preferences, append-only database guards), `-http` and `-host` unit tests (strict schemas, authority order, flags), and Playwright `playwright.notifications.config.ts` (synthetic PostgreSQL, desktop and mobile, development and production servers: safe notice, mark read across reload, preference choice, per-person isolation, signed-out and API access). All are mutation-checked; test names and genuine results belong in the PR. Limitations: no external delivery, no independent UAT, flags stay off in deployed environments.

`tests/notifications-safety-db.test.ts` covers first-enable history, pending backlog across subsequent runs and upgrades, an older uncommitted event crossing initialization, poison-event progress, direct mark-read validation, disjoint locked batches and database value/read-time guards. Lifecycle tests also assert amendment proposal/accept/decline/withdrawal audiences, exact revision-deadline dedupe and database-observed deadline expiry.

Entry point: the account menu lists **Notifications** only while `NOTIFICATIONS_READS_ENABLED` is exactly `true`.
