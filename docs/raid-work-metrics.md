# Work-loop metrics (operator)

`GET /api/v1/admin/work/metrics` gives an authorized operator an honest view of the useful work loop on simulated funding: how many listings, slots, applications, offers, engagements and reviews exist by state, why work closed, how long matching and review take, and how much reward volume sits at each stage **per asset**. It is read only, private and default off.

## Contract and requirements

| Requirement                     | Behavior / verification                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blueprint §31.2 reporting       | Drafted, open, funded, accepted and work-accepted stay separate: counts by state, `volumes[].openFunded` (rewards reserved on open available slots), `committed` (accepted, unfinished engagements, using the effective amended terms) and `workAccepted`. Accepting work is not paying: `paid` is always `null` and `notMeasured` names what is absent (paid volume, settlement, disputes, private access, repeats). |
| §31.2 assets, I03               | Quantities are reported per full asset identity (`assetKey`, asset id, verified decimals, base-unit string). Nothing is summed across assets, valued in dollars or given a price; the strict schema rejects any extra valuation field a host might add.                                                                                                                                                               |
| §31.1 matching and review delay | `timings.matching` is slot publication → engagement; `timings.review` is submission → review decision. Both use database timestamps, count their `samples`, and report `null` median/p90 when there are none, never zero.                                                                                                                                                                                             |
| I10, I06, blueprint §28         | Operator only: the shared administrator rule (`requireUser(true)`, an X-signed-in administrator), a per-operator rate limit, `private, no-store`, query strings and non-GET refused, flag exactly `WORK_METRICS_READS_ENABLED=true` (else 404). Output has counts, amounts and timings only: no accounts, handles, brief text or evidence.                                                                            |
| R15/R16                         | `metrics-contracts`, `metrics-storage` and `metrics-http` are portable; hosts inject the flag, operator authority, rate limit and transaction. The independent [raid-terms host](../examples/raid-terms/README.md) reads the metrics after the full loop and checks the honesty rules.                                                                                                                                |

Requirement mapping: T043 (loop metrics part), AG03/M2, blueprint §§16 (no money moves), 24.6–24.7, 28, 31.1–31.3. Test fixtures are **not** excluded (there is no fixture marker yet), so these numbers are for operators and must not be quoted as public success claims. Product-level metrics that need data this milestone does not have (Guild activation, launch conversion, repeat participation, settlement, disputes, private access, AI and promotion measures), analytics events, fairness inspection and surveys remain NOT VERIFIED/unbuilt. Full numbered task criteria, UAT and business/release approval remain NOT VERIFIED.

## Host contract

`WORK_METRICS_READS_ENABLED` is an exact-string `true` flag, default off. `authorize` must resolve only for an authorized operator and return their account id (it rejects with `WorkHttpError` 401/403); `rateLimit(operatorAccountId)` rejects with 429. A response outside the strict `WorkMetricsSchema` is `503` and never forwarded.

## Verification

`tests/work-metrics-db.test.ts` (real PostgreSQL: empty loop, per-asset separation of open/committed/work-accepted volume, `paid: null`, matching and review timings over real samples), `-http` (flag, authority and throttling before reading, query/method/contract drift, hidden failures, per-operator throttle identity) and `-host` (exact flag).
