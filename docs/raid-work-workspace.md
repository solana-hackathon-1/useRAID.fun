# My Raid and review/applicant workspaces

T022 gives a signed-in person a browser view over the work loop: **My Raid** (`/raider/work`) for the member's accepted work, review feedback, closure, unsettled claim, applications and offers, and **Review and applicants** (`/creator/work`) for the exact terms reviewer and for a listing operator. Everything runs on simulated funds behind default-off flags. It adds read models, a protected HTTP boundary, a portable client, components and pages; it adds no acceptance, start, dispute, settlement or Guild-recognition behavior.

## Host contract

All flags are exact-string `true` and default off: `WORK_WORKSPACE_READS_ENABLED` (required for every read and write), `WORK_SUBMISSIONS_ENABLED`, `WORK_REVIEWS_ENABLED`, `WORK_APPLICATIONS_ENABLED` (apply **and** withdraw: one flag opens or closes both, so closing new applications also blocks withdrawing until an owner decides the withdrawal policy) and `WORK_ADMISSION_MANAGEMENT_ENABLED` (offer issue/revoke and the applicant queue). `RAID_WORK_OPERATOR_ACCOUNT_IDS` is a **synthetic-only** allowlist standing in for listing authority because the shared Root has no recognized Guild role: empty denies everyone, and it is not production or Guild authority. `WORK_APPLICATION_LIMIT` (1–100, default 5) caps open applications. The UI is not authority: every command re-checks the real session, origin, rate limit and current authority server-side, and a disabled write still allows original-receipt replay and reads.

HTTP (`/api/v1/work/…`, all `private, no-store`, bounded JSON, `Idempotency-Key` on writes): `GET me`, `GET reviews`, `GET applicants`; `POST submissions`, `POST reviews` (decision), `POST applications` (apply; same flag as withdrawal), `POST offers`, `POST offers/{id}/revocation`, `POST applications/{id}/withdrawal`. Responses are re-parsed with the strict schemas and must match the request (engagement, submission, application or offer) or the call fails closed as `SERVICE_UNAVAILABLE`. Domain conflicts (state, round, deadline, duplicate review, expired offer) map to stable safe codes (`REVISION_CHANGED`, `OFFER_EXPIRED`, `CAPACITY_CONFLICT`, …) without internal detail.

## Behavior and adverse states

- **Unconfirmed result:** a network or 5xx failure keeps the same request key; pressing the same button again retries it without duplicating the submission or decision.
- **Conflict:** a stale form (for example a decision recorded on another device) shows "This changed while you were working" with a Refresh control; it never shows success.
- **Unavailable:** a closed flag shows a plain notice instead of an enabled control; no JavaScript still shows readable server-rendered state.
- **Closure:** timeout closures explain which duty was missing and that closing does not decide payment or fault; the claim stays "unsettled".
- Saved text is escaped. Mobile has no horizontal scroll.

## Verification

`tests/work-workspace-db.test.ts` (real PostgreSQL read models: member progress/feedback/claims, isolation, offer expiry, reviewer queue filtering, applicant authority), `-http`, `-host`, `-client`, `-page`, `-ui` (mutation-checked) and `-consumer` unit/render tests; Playwright `playwright.work-workspace.config.ts` (synthetic PostgreSQL, desktop + mobile, development and production servers) covers submit → revision → resubmit → accept with the unsettled claim, a stale-decision conflict, issue/revoke offer, withdraw, and signed-out/foreign access. Limitations: no independent review, UAT or hosted CI at the time of writing; no real wallet or provider; flags stay off in deployed environments.

Entry points: the account menu lists **My Raid** and **Review and applicants** only while `WORK_WORKSPACE_READS_ENABLED` is exactly `true` (`src/lib/work-entry-links.ts`); a disabled feature advertises no link.
