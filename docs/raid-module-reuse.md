# RAID reusable features and replaceable integrations

[Canonical architecture](../RAID_AGENT_BLUEPRINT.md#24-system-architecture) · [Detailed task criteria](raid-agent-task-contracts.md) · [Project](https://github.com/orgs/solana-hackathon-1/projects/1)

R15/R16 apply to internal features as well as external providers. This document defines delivery and consuming-host requirements; it does not claim the existing repository has already been modularized. Inventory actual code first and record implementation gaps. Preserve the modular monolith and shared transactional constraints; a reusable boundary does not require a separately deployed service or published package.

## Owned feature modules

Every delivered feature has a public interface, invariant owner, injected host dependencies, contract tests, documented usage and a consuming example. Pure helpers need only their relevant API/behavior documentation and tests; they do not need invented provider abstractions. Keep cohesive feature boundaries rather than creating one package per function.

## Definition of a swappable boundary

Domain commands import owned ports and DTOs, not vendor SDK types. A reviewed composition root supplies adapters through explicit configuration. Each adapter declares capability, schema/version, typed errors, timeout/cancellation, retry/rate-limit policy, semantic operation identity, observation/finality, secret/data policy and health signals. A shared contract suite runs against each supported implementation; a deterministic fake demonstrates test substitution and stays forbidden for live enablement. Unsupported capabilities return typed failure rather than pretending success.

Switching a configured default affects only explicitly authorized new operations. Existing accepted work, signed transactions, grants, publications and usage receipts retain their original provider/network/asset/terms/generation bindings until reconciled. Record inventory, capability differences, migration/drain, rollback limits and renewed feature-specific gates. Never reroute a pending claim or reissue an unknown successful operation automatically.

## Documentation delivered with every module

1. Purpose, user outcome, non-goals, canonical requirement IDs and actual implementation status.
2. Owned entities/states/invariants and the public API/DTO/event/error schema.
3. Dependency diagram, permitted imports, injected host capabilities and transaction ownership.
4. Installation/build/runtime requirements; approved configuration names and secret ownership without values.
5. Minimal consuming-host setup and runnable example, including every dependency, fixture and command.
6. Authentication/authorization/tenant assumptions, allowed and rejected actors and private-data boundary.
7. Genuine RED/GREEN/REFACTOR results, shared contract/negative tests and observed consuming example.
8. Provider/module substitution instructions, capability limits, version compatibility and migration/backfill.
9. Operational health signals, failures, retries, cancellation, restore and rollback restrictions.
10. Limitations, unresolved OPEN decisions/gates, maintainer/reviewer and next task.

Documentation and example belong in the same reviewed change as behavior. A README claiming reuse while importing hidden app state is a failed contract. Existing code is reusable only after these boundaries and tests actually pass. Publishing packages or copying private customer material is outside this documentation task.

## Authentication consuming example contract

An auth feature’s example host supplies a session/nonce store, test clock, domain/origin policy, signature verifier, identity-link repository and audit sink. The example consumes public commands for challenge, proof, session resolution, verified linking and revocation. It wires a protected resource through the verified account/permission result; it does not trust client role flags or treat login as a Guild admin grant.

The runnable example must reject reused/expired/wrong-domain challenges, incorrect link intent, duplicate conflicting subject links, revoked sessions and cross-tenant access. A wallet/provider adapter replacement retains the same canonical account/participant and existing capacity/history/claims. A storage implementation used in production must preserve atomic nonce consumption and identity uniqueness; an in-memory example proves interface use only. Record which tests use real storage and which use deterministic fixtures.

This is a required future consuming example, not a claim that an auth package or alternate implementation already exists. E02/T006/T007/T008/T090 own the auth slice; E01/T002/T004/T089 own shared boundaries and contract evidence. Every other feature uses the same documentation and test-driven completion rules at its own boundary.

## Existing-project signed control proof

T010A owns [the informational control-proof contract](raid-project-control.md) and [independent crypto host](../examples/project-control/README.md). Inject trusted current account/draft/origin/clock and approved versioned project authority/public evidence, plus local Ed25519 verification.
