# Engagement acceptance and capacity

T020 supplies the PostgreSQL acceptance boundary for a current canonical HUMAN accepting a published PUBLIC/SOLO/INSTANT Raid with simulated funding. [T021 admission](raid-work-admission.md) extends the same command with exact-version offers for APPLICATION terms. Acceptance atomically creates one `ACCESS_PENDING` engagement, immutable accepted terms, participant membership, global participant capacity, a filled source slot, command receipt, audit and outbox. Work does not start here. Root routes and production enablement are absent.

## Stable interface and host contract

`src/work-loop/engagement-storage.ts` exports `commitEngagement(tx, command, host)`. Its strict input is `{slotId, termsVersionId}`; UUIDs are required. The trusted actor is `{accountId, sessionHash}` and command identity also includes `idempotencyKey` and `requestId`. The result schema in `engagement-contracts.ts` contains `status: EXECUTED | REPLAYED`, `fundingMode: SIMULATED`, `generation` and the existing shared `EngagementSchema`. Additive fields are compatible; changing accepted meaning or command identity requires a versioned contract/migration. Domain imports are limited to owned work-loop, shared contracts, command receipts and identity locks; no app auth, Prisma, framework or provider singleton is imported.

The host owns a real PostgreSQL READ COMMITTED transaction, parameterized query port, commit/rollback and bounded whole-transaction retry. Retry deadlocks/serialization with the original semantic identity; never retry just the capacity insert. Apply `202610260001_raid_terms` and `202610260002_engagement_capacity` after their receipt/identity dependencies. The independent consumer declares a minimal identity layout; the application adapter supplies the full repository layout.

`AcceptanceHost` requires all capabilities explicitly:

- `allowNewWrites`: trusted server configuration, default off at composition. A missing capability fails closed; replay still requires current session/ownership when writes are off.
- `assess(tx, context)`: current exact-slot/version eligibility, restrictions and explicit consent, returning immutable consent/beneficiary/eligibility-policy references or null. Hold current authority through commit using this transaction. The beneficiary reference denotes an explicitly approved destination; this command does not verify a live wallet or asset transfer. The module itself verifies actual current canonical HUMAN/session and rejects managed operators. The fixture's unconditional assessor is test-only.
- `fundingAvailable(tx, binding)`: verify the still-current distinct simulated reservation for this exact slot/version/full reward vector, under transactional authority. An aggregate balance, caller boolean or arbitrary reference string is insufficient. No network calls or provider waits belong in either callback.
- `authorizeOfferIssuer` (optional in the type, required for APPLICATION admission): answers, as an account and never a session, whether the offer's issuing Founder still holds current Guild authority. Acceptance with an offer fails closed with `STORAGE_CONTRACT` when a host omits it. See [applications and offers](raid-work-admission.md).
- Optional `identityLocks`: a trusted capability already acquired on this exact port/transaction, validated for the actor root and Session/Participant children. HTTP callers cannot supply it.

Lock order is receipt → WorkListing → RaidSlot → identity helper's sorted canonical advisories/account roots/Session and Participant children → ActiveCommitment primary key. All competing writers must preserve that order and the helper's identity-writer fence. The prepared identity capability holds authority through commit. Session expiry and finite commitment deadlines are rechecked after callbacks and the capacity insert wait. Mutating callback inputs fails closed. The accepted snapshot preserves the original deliverables, criteria, required skills, deadlines, reward policy/amounts and explicit consent/beneficiary. Policy references of form `termsVersionId:key` resolve to the immutable definition's tools, revisions, withdrawal, termination, rights, review, dispute and finality fields.

## Authority, privacy and state

| Actor/state                                                                                               | Result                                                                                               |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Current unrestricted canonical HUMAN; current available source; exact consent/eligibility/reservation     | One pending engagement and capacity reservation                                                      |
| Missing/expired/revoked/foreign Session, suspended account, non-HUMAN                                     | Denied before accepting work                                                                         |
| Stale terms, filled/unpublished source, expired acceptance window, failed eligibility/funding, writes off | Rejected; all tentative state rolls back                                                             |
| Already committed own participant                                                                         | `CAPACITY_CONFLICT` with its own current engagement reference                                        |
| Same slot assigned to someone else                                                                        | `SLOT_FILLED`; no other participant's engagement reference                                           |
| Original command replay with current own Session                                                          | Returns original immutable engagement; no new eligibility/funding assessment or capacity acquisition |

Membership reads are internal to receipt recovery and require the actor's actual canonical participant. No public DTO, private download, HTTP endpoint, role or token-holder authority is introduced. The event `work.engagement_committed.v1` carries only engagement/version/slot identifiers, guild scope and version 1 through the existing audited receipt/outbox envelope. Private terms and session bytes never enter its payload. Host callbacks must enforce any Guild-specific eligibility; login alone supplies no Guild role.

Typed `WorkError` codes include `INVALID_INPUT`, `UNAUTHENTICATED`, `ACCOUNT_RESTRICTED`, `FORBIDDEN`, `NOT_FOUND`, `WRITES_DISABLED`, `PUBLICATION_BLOCKED`, `TERMS_VERSION_CHANGED`, `ADMISSION_REQUIRED`, `DEADLINE_PASSED`, `ELIGIBILITY_REJECTED`, `FUNDING_REQUIRED`, `CAPACITY_CONFLICT`, `SLOT_FILLED` and `STORAGE_CONTRACT`. Receipt conflicts preserve `IDEMPOTENCY_KEY_REUSED`. A future HTTP adapter owns origin/CSRF/quota/status mapping; this internal command supplies no transport policy.

## Persistence, operations and verification

The additive migration creates Engagement/EngagementMember/ActiveCommitment and rejects orphan/phantom assignments, accepted-history mutation, mismatched source/version/reward and partial capacity. Participant FKs are RESTRICT: neither history nor capacity is rehomed on account/provider changes, and no identity writer is introduced. Existing accepted work survives session loss or disabling new writes. Generation stays fixed at 1. T020 froze state at the initial pending milestone; [T023](raid-work-submissions.md) adds only the guarded transitions it needs, and start, withdrawal, termination and deadline closure still need explicit guarded migrations. Never delete a commitment to repair capacity manually. Closure must eventually match both participant and engagement and preserve outstanding obligations.

Monitor typed conflicts, retry exhaustion, constraint failures and receipt/outbox health without logging private terms. Synthetic reservations do not establish live funding/finality. No worker starts from this event until its own current terms/generation/funding/access checks exist. Backup/restore must retain source, immutable snapshots, memberships, reservations and receipts together. Rolling application code back must preserve these tables/history; destructive down migration on accepted work is unsupported.

`tests/engagement-capacity-db.test.ts` covers acceptance/replay/revocation, disabled/restricted/foreign/expired cases, exact version, true database races, busy-member rollback, immutable history/deferred guards, current session after child-lock waits, retry, callback mutation and deadline expiry after capacity insertion. `tests/raid-terms-db.test.ts` now uses an actual engagement when verifying frozen assigned sources. Relevant receipt/identity/shared contract regressions and schema drift are checked with a fresh owned database. The separately installed consumer verifies actual stored consent/reservation, acceptance/replay/busy denial/session revocation using its own pg transaction host. Resource cleanup uses the verified task-owned runner. Test names and genuine RED/GREEN results belong in the PR; independent review disposition is recorded there separately from SELF-EVALUATED author checks.
