# Private administrator review-appointment management

This bounded T013 interface supplies an administrator screen for existing [appointment commands](raid-practice-review-assignments.md). A current allowlisted X administrator looks up one explicit submission, observes immutable appointments and their current expiry/revocation, and issues or revokes an appointment with a reason. It does not create a global private-submission directory, disclose submission answers or select a staffed operating policy. R04/R06/R11/R12/R15/R16, I05/I06/I10/I11/I13, D07/D08/D13 and AC04–07/AC42–43/AC69–70/AC73–75 apply. [Original task/evidence](tasks/2026-10-23-T013-assignment-management.md) preserves historical results. The [24 October reconciliation](tasks/2026-10-24-T013-current-review.md) records all seven hosted checks passing at `4cf7791`, dependency remediation and a fresh synthetic development preview. Independent review, full T013 criteria, UAT and release remain unverified obligations.

## Contracts and dependencies

Canonical immutable input/record/result schemas now live in `src/skills/practice-review-assignment-contracts.ts`, with the previous storage and HTTP exports retained. Existing schemas and receipt semantics are preserved. All seven consuming examples that use assignment storage declare the new pure contract and management-contract links. The new browser controller and React view import only these pure Zod/ID contracts, never Node crypto, SQL, Next or Root authentication.

`PracticeAssignmentManagementInputSchema` in `practice-review-assignment-management-contracts.ts` is strict `{version:'v1',submissionId:UUID|null,after:UUID|null}`. Cursors require an explicit submission and UUID case is normalized. The strict page carries own `actorAccountId`, `accessId`, `observedAt`, `submissionId`, `after`, up to20 `entries`, `nextCursor`, `version:'v1'`, `private:true`, `isAuthorizationToken:false`. Each entry contains the original assignment, optional immutable revocation and observed `ACTIVE|EXPIRED|REVOKED` state. An original assignment remains `ISSUED` after expiry/revocation; only the observation describes current effective lifetime. The schema binds all entries/revocations to their exact submission and appointment, validates time/order/cursor coherence and rejects extra private fields. Root's wire context adds `writesAvailable` and its coherent `unavailableReason:null|'DISABLED'`. Internal current manager X identity is never sent to the client.

`readPracticeAssignmentManagement(tx,actor,input,{canInspect,canManage})` is exported from the existing storage entry. The host supplies actual unrestricted X-admin identity, held current User/Session locks, prior PostgreSQL migrations/canonical HUMAN submission/definition facts, synchronous approved account-inspection and per-record scoped management policies, bounded READ_COMMITTED transaction, rollback/whole retry and commit-before-delivery. `canInspect({accountId,xId})` authorizes this restricted management-metadata operation, including blank/missing/empty lookup. `canManage` receives actual original subject/evaluator/submission/skill/domain/purpose/finite expiry and the acting administrator/X identity, as existing management commands do. Extra conflict/staffing eligibility belongs to the host's approved policy; this module does not invent it.

Dependency direction is host auth/SQL/policy → canonical management reader/transport → portable controller/view. The browser never supplies a trusted administrator, subject, approval or current state. Root injects its real current `adminXIds()` policy for both metadata callbacks; inspection is available when new writes are disabled. Existing issue/revoke commands alone mutate appointment/revocation history and continue to enforce their actual current authority, finite expiry, self-review denial and receipt rules.

## Read authority, audit and concurrency

Current X session, ADMIN role, connected `xId`, account restrictions and strict true inspection policy are checked before candidate metadata. Every authorized access attempts an identifier-only `ListPracticeReviewAssignmentsManagement` receipt and `skill.practice_review_assignment_management_access.v1` private audit before reason/appointment reads. The audit aggregate/actor is the current manager account; payload is empty on a blank screen or only `submissionId` for an explicit target. It records an authorized attempt, not successful delivery. Initial denial creates no access trace; audit failure prevents metadata selection; thrown failures roll back the operation. No public event/outbox, rank, reputation, capacity, financial or provider effect is created.

Lookup selects at most21 candidate IDs/evaluator/purpose/expiry rows for that exact submission, ordered by UUID. Before selecting reason/history, each candidate takes its existing namespace12017 appointment mutex in ascending ID order and passes the actual scoped policy. One denied row denies the whole page, so a cursor cannot disclose a withheld appointment. The list holds only the current caller User/Session plus ordered appointment locks: it does not acquire other User rows after its caller lock and does not reuse the multi-user write helper. Existing issue/revoke writes retain their sorted multi-user locks before appointment locking. A competing revocation committed first is observed; one blocked behind this appointment lock takes effect after the read commits. Current session and inspection/scoped policies are repeated after waits. A final database-clock/session check determines observed expiry, which cannot be frozen by row locks.

Known limitation (retained after Claude review): one historical subject-equals-evaluator row fails the whole lookup with STORAGE_CONTRACT (safe HTTP503), and one out-of-scope row fails it with FORBIDDEN (HTTP403). Both hide the submission’s entire requested history page. The reader fails closed rather than returning partial history or leaking a withheld row through pagination. Historical data repair or a different partial-history contract requires separate reviewed work.

The repository's existing non-identity advisory fence classifies this new reader by an exact AST hash in `planning/identity-writer-fence.json`, using the documented reserved-domain exception process in `docs/raid-identity-locks.md`. Its one acquisition shares existing appointment seed12017; it adds no identity resource or multi-user root acquisition. The scanner and seed-range rules are unchanged. The candidate entry is SELF-EVALUATED; Claude must independently review it and the reader. Standalone hosts do not load this Root static-check manifest. Initial unregistered-reader fence failure, current passing fence and three existing architecture regression checks are retained in task evidence.

The original public/synthetic definition is parsed internally only to verify saved canonical scope. Answer/explanation/tools/AI declarations and other case-body columns are never selected or returned by management lookup. Reasons and account identifiers in appointment/revocation records are private, authorized management metadata. Admin status does not grant evaluator access to private answers. Existing exact-purpose case readers independently require their current appointment and scoped use policy; management UI links supply no bypass.

Blank or nonexistent/unavailable submission lookup returns an empty observation without asserting whether a private submission exists. Twenty rows plus one lookahead determine `nextCursor`; it is the last returned ID when another authorized row exists. New random UUIDs below a cursor require refreshing the first page. Pagination is not a snapshot. Expired/revoked appointments stay in this historical list, and expired appointments may still be revoked under existing policy. An observation is never a permission lease; already disclosed bytes cannot be recalled.

The PostgreSQL-backed HEAD regression pins both writes and the empty response. The reader and its author-pinned identity-fence hash remain unchanged; independent review is still required.

## Stable pending recovery

`createPracticeAssignmentManager(context,transport,key?)` owns one immutable pending `ISSUE|REVOKE` kind/body/key, shared by both forms. The controller canonicalizes UUID/UTC expiry for the existing strict command/result bindings, accepts editable fields only and binds returned issuer/revoker/target/reason/purpose/expiry to the original request. HTTP200 with malformed/misbound output remains UNCERTAIN; a 5xx, network failure or unclassified response also retains the original intent. Busy/uncertain/key-collision states lock both forms, lookup, pagination and refresh. Retry resends only the same action/body/key; no automatic retry, persistent browser storage or reload recovery occurs. An UNCERTAIN or key-collision (BLOCKED) page also offers an explicit “Discard request and recheck” (`manager.discard()`): it abandons the pending command (its outcome stays unknown), then reloads the displayed submission and keeps a persistent notice that the discarded request may still apply; the issue/revoke form fields are cleared so the administrator must deliberately re-enter and compare the refreshed list before the next command, which gets a new key. Discard cannot prove the original request is not still in flight or already applied, so the new key can duplicate it: it deliberately gives up idempotency for that command by owner decision. It is ignored in every other phase. Keep an uncertain page open. Beforeunload warns while a command is pending; previously disclosed browser history/copies cannot be erased.

A valid EXECUTED/REPLAYED200 acknowledges the original saved receipt even if writes are now off. It is explicitly historical; pre-save rows are labeled observed-before-save and are not optimistically promoted to current authority. Refresh is required before another command. A known write401/403 clears visible private context (the 403 envelope is `FORBIDDEN` for both a lost admin session and a business denial such as self-review or an out-of-scope appointee, so a write403 uses neutral wording about the current account or selected appointee; the 401 and fresh-read denial keep the sign-in wording). A write404 means a missing target: it clears the pending command, retains the observed context in STALE, and requires “Refresh current appointments” before another command; that control reloads the submission currently displayed (`manager.refresh()`), never the editable lookup text. A read/load404 still enters DENIED and clears context; known invalid-command413/415/422 allows correction; already-revoked409 requires a fresh observation; key-reuse409 retains the locked original intent until the administrator discards it and rechecks. Request-key generation/transport diagnostics are never displayed. Failed fresh lookup also clears obsolete metadata. Recovery requires the same actual authorized account/session; changing the client account identifier supplies no authority.
